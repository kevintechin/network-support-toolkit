## Network errors classified by their code · 2026-09-04 — backlog #14 (a `Cause:` line in the report language)

**The defect, reproduced on the reference machine.** Windows PowerShell 5.1 reports `Get-UICulture` as en-US and `Get-Culture` as zh-TW here, and the two disagree in a way that matters: a `SocketException` **constructed** in the session carries .NET's own English text ("No such host is known"), while a **real** DNS failure carries the operating system's text — `System.Net.Sockets.SocketException: '無法識別這台主機。' SocketErrorCode=HostNotFound`. .NET resource strings follow the UI culture; Winsock messages come from the operating system and follow its locale. So the message text can appear in either language on the same machine, cannot be matched against, and must not be the thing the report explains. The code does not move: `SocketException.SocketErrorCode` and `WebException.Status` are enumerations.

**Change.** `Get-NetworkErrorCauseText` walks the exception chain — a failed method call arrives as a `MethodInvocationException`, a task as an `AggregateException`, a ping as a `PingException`, so the socket error sits two or three levels down — and returns one sentence in the report's language followed by the code: `The name could not be resolved (no DNS record). [SocketError HostNotFound]`. `Add-NetworkErrorCause` puts that line above the original text, never instead of it. 23 codes are mapped in both languages: 12 `SocketError` (HostNotFound, TryAgain, NoData, TimedOut, ConnectionRefused, NetworkUnreachable, HostUnreachable, ConnectionReset, ConnectionAborted, NetworkDown, AddressNotAvailable, AccessDenied) and 11 `WebExceptionStatus` (Timeout, NameResolutionFailure, ProxyNameResolutionFailure, ConnectFailure, TrustFailure, SecureChannelFailure, ReceiveFailure, SendFailure, ConnectionClosed, ServerProtocolViolation, RequestProhibitedByProxy). An unmapped code yields `[SocketError <Code>]` on its own — no invented sentence, but a locale-independent name the reader can look up. `WebExceptionStatus.ProtocolError` is deliberately not mapped: a non-success HTTP status is not a failure path here, and the script already reports it through the response.

Six call sites carry the line: the exception details of every check (`Get-ExceptionDetails`, so a failed DNS lookup, a step error and the emergency report all gain it), the per-attempt ping log, the TCP failure text, both HTTP failure paths and a traceroute hop status. Errors raised by cmdlets, CIM/WMI or the file system have no such code, keep the operating system's wording unchanged, and §5 of both technical guides now says so.

## Guards on the PowerShell AST · 2026-09-04 — backlog #17 (`tests/`; the packaged validator drops from 66 to 62 checks)

**Change** (closes backlog #17). The two guards that keep the v1.2.0 GUI regressions out of the shipped scripts were regular expressions over the comment-free logical lines of the file, inside the packaged `tools/validate_release.py`. They now run on the PowerShell AST in the test chain: `tests/ast_guards.ps1`, with `tests/selftest_guards.ps1` as the acceptance set. Nineteen of the twenty-one Codex rounds on PR #4 had gone into teaching the patterns another spelling of the same two mistakes; the parser answers all of them at once.

- **`Find-UnparenthesizedArithmetic`** — the comma binds tighter than every arithmetic operator, so `New-Object System.Drawing.Point(22, 84 + $offset)` really is `Point(@(22, 84) + $offset)`: one three-element argument, the runtime's "argument count 3", and in v1.2.0 an `Initialize-Gui` that threw and sent both entry points to console mode. Two signatures, one per spelling. A parenthesized or `@( )` argument list whose top-level expression is an arithmetic `BinaryExpressionAst` over the `ArrayLiteralAst` the commas built — `(22, (84 + $offset))` is an array literal, `(780, [math]::Min(560 + $offset, $h))` keeps its arithmetic inside a method call, and `(1 + 2)` or `(@($a) + $b)` have no comma-built array on the left, so none of them matches. And, for `-ArgumentList 22, 84 + $offset`, a bare-word arithmetic operator among the command's elements on a call `StaticParameterBinder` cannot satisfy: the comma ends the array and the operator reaches New-Object as a positional argument it has no parameter for.
- **`Find-OverwrittenParameter`** — a script's top-level scope and its `$script:` scope are the same variable table, so v1.2.0's `$script:Interactive = $false` overwrote the bound `-Interactive` and the IT launcher opened the user layout. Every write that reaches that table is read from the AST: assignments (compound and multiple ones included), `++` / `--`, a `foreach` loop variable, `Set-Variable` / `New-Variable` / `Clear-Variable` / `Remove-Variable`, and the item cmdlets on the `Variable:` drive. `$script:` / `$global:` counts anywhere, unqualified / `$local:` / `$private:` only outside a function (`VariablePath` and the parent chain say which), and the only accepted initializer is the parameter's own value — `$Interactive`, `[bool]$Interactive`, `@($PingTarget)`, `$Interactive.IsPresent` and nestings of those — because a transformed value belongs in a variable of its own. `StaticParameterBinder` resolves abbreviated parameter names, positional and quoted arguments and the cmdlets' aliases, which the session itself supplies (`Get-Alias -Definition`), so `sv`, `set`, `nv`, `clv`, `rv`, `si`, `sc`, `ni`, `cli`, `ri`, `rm`, `del`, `erase`, `rd` and `rmdir` need no pattern each.

The rewrite closes the three findings assessed and deferred in round 21 of PR #4 — the multiple assignment `$tmp, $script:Interactive = 1, $false`, `Clear-Variable` / `Remove-Variable`, and an alias of `New-Object` (Windows PowerShell 5.1 defines none, but one defined in the session resolves like any other) — and adds what the AST makes free: a `foreach` loop variable, a module-qualified call, `@(22, 84 + $offset)` as an argument list, an arithmetic spine longer than one operator, and here-strings, comments and string data that the text stripper had to recognise by hand and the parser simply knows. `$env:` and other drive-qualified names are excluded as a different store, `[System.Drawing.Point]::new(22, 84 + $offset)` is not flagged because a method call splits its own arguments on the commas, and the comma mistake outside a `New-Object` argument list stays out of scope: there it is legitimate array concatenation. Out of scope by design in both guards, as before: code the parser cannot see through — `Invoke-Expression`, a command name or a variable path built at runtime, splatting. A `-Scope` passed as a variable is now flagged rather than trusted, and a script block passed to a command (`& { }`, `ForEach-Object { }`) is treated as its enclosing scope, since `ForEach-Object` really does write the caller's variables and flagging is a guard's safe direction.

### From the enterprise-readiness review (2026-09-05)

22. The two shipped scripts are not signed.
