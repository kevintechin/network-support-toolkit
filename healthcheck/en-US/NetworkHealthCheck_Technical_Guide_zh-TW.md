# NetworkHealthCheck Portable 1.2.12：功能、設計、驗證與限制

## 1. 文件目的

本文件說明 `NetworkHealthCheck` 免安裝工具的功能、架構、判定方式、錯誤處理、驗證方法、已知限制與原始碼註解策略。文件對應版本 **1.2.12**，適用於套件中的繁體中文版與英文版；兩者的執行邏輯相同，只有使用者可見文字、預設測試名稱與註解語言不同。

## 2. 程式定位

這是一個 Windows PowerShell 可攜式診斷工具，不需要安裝服務、驅動程式或封包擷取元件。它的主要目的不是取代 Wireshark、網路監控平台或交換器管理系統，而是讓一般使用者按一次即可收集一致的網路資訊，並把無法執行的原因保留在報告中供 IT 判讀。

程式採唯讀設計：不修改 IP、DNS、路由、防火牆、代理伺服器或網卡啟停狀態。主動行為只有 Ping、DNS 查詢、TCP 連線與 HTTP/HTTPS GET 測試。

## 4. 功能與判定方式

### 4.1 設定檔載入

程式先建立內建安全預設值，再讀取 JSON 設定並遞迴合併。設定檔不存在或 JSON 無法解析時，不會直接終止；程式改用內建預設值，將原因記成 `ERROR / 無法檢查`，並繼續能執行的項目。

語意驗證包含：IPv4、CIDR、前綴長度、閘道、DNS、DHCP 布林值、TCP 主機/連接埠、HTTP/HTTPS URL、DNS 目標及主要逾時值。部分不合理門檻會列為警告。自 1.1.4 起，所有數值門檻改用不受地區設定影響、不會拋出例外的轉換器：非數值（含布林值、NaN 與無限大）會列入設定警告並改用內建預設值，小數門檻（例如 `2.5`）照原值使用，不再四捨五入成整數。計數類設定，即網卡錯誤／丟棄增量、`TcpRetransmissionCriticalCount`、`MinimumTcpSegmentsForRate`、`PingCount` 與各逾時值，必須是 32 位元整數範圍內的整數；填小數或超出範圍的值會被列入警告並改用預設值，不再被靜默改動。語意錯誤目前不會把相關設定自動全部刪除，因此錯誤設定仍可能使部分結果失去判斷意義；報告會明確提示。

### 4.2 網卡與 IP 資料來源

優先使用 `Get-NetIPConfiguration`、`Get-NetIPInterface` 及 NetAdapter/NetTCPIP 物件。若不可用或無法取得資料，改用 `Win32_NetworkAdapterConfiguration` 與 `Win32_NetworkAdapter` 的 CIM/WMI 資料。

收集欄位包括介面名稱、描述、介面索引、連線速度、MAC、網路設定檔、IPv4/IPv6、前綴、閘道、DNS、DHCP 與資料來源。具有 IPv4 且有閘道的介面優先視為主要介面；若沒有，退而使用具有 IPv4 的介面。CIM/WMI 備援路徑（1.1.4）只把 `DefaultIPGateway` 中的 IPv4 下一跳視為閘道；`DHCPEnabled` 缺值時列為未知，而不是靜態 IP。自 1.2.12 起，每張網卡的詳細資料也會寫出回應它租約的 **DHCP 伺服器**（backlog #32），兩條路徑都讀自 `Win32_NetworkAdapterConfiguration.DHCPServer`——NetTCPIP 路徑多一次 CIM 查詢、以介面索引為鍵，因為那些指令帶的是模式而不是伺服器。固定位址不論類別裡放著什麼都不點名伺服器；類別讀不到時，那一行說資料無法取得，而不是留一個會被讀成「沒有伺服器」的空白；設定裡沒有伺服器位址時照實說。這個查詢不會嘗試第二次：它不是效能計數器的讀取，1.2.8 記錄了網卡設定查詢為什麼維持單次嘗試。

基本異常規則：

| 條件 | 結果 |
|---|---|
| 找不到已連線且有 IP 的網卡 | `FAIL` |
| 偵測到 `169.254.x.x` | `FAIL`，通常表示 DHCP 未取得位址 |
| 網卡沒有 IPv4、但仍有其他 IP 資料 | `WARN` |
| 沒有 IPv4 預設閘道 | `FAIL` |
| 沒有 DNS 伺服器 | `FAIL` |

### 4.3 公司標準比對

只有 `Expected` 至少設定一項規則時才會判定合規；全部留空時僅顯示目前設定，不會宣稱正確或錯誤。

- IP：目前主要介面的任一 IPv4，只要精確符合允許 IP 或落在任一允許 CIDR 即通過。
- 前綴：目前主要介面的任一前綴符合允許清單即通過。
- 閘道：目前主要介面的任一閘道符合允許清單即通過。
- DNS：設定檔列出的每一個必要 DNS，都必須出現在主要介面彙整後的 DNS 清單中。
- DHCP：所有可取得 DHCP 狀態的主要介面都必須符合預期；完全無法取得時列為 `ERROR`。

這種「多介面彙整」設計方便一般情境，但 VPN、虛擬交換器或同時連接有線/無線時，可能需要公司客製介面篩選規則。

### 4.4 Ping、封包遺失與延遲

每個目標使用 .NET `Ping` 類別送出設定次數的 ICMP。計算公式：

```text
封包遺失率 = (送出數 - 成功數) / 送出數 × 100%
```

延遲以成功回覆計算平均、最低與最高值。判定依序考慮：完全無回覆、嚴重遺失、警告遺失、嚴重平均延遲、警告平均延遲。`Required=true` 的目標在嚴重情況會成為 `FAIL`；非必要目標完全不回覆通常為 `INFO`，因為 ICMP 可能被防火牆封鎖。

**必要的閘道目標是由閘道自己的 stack 回應的（1.2.11、backlog #58）。** `AUTO_GATEWAY` 是唯一以 `Required` 出貨的目標，而送到設備自己位址的 echo 是由該設備的控制平面回應的，網路設備通常會對這種流量限速或降低優先權。所以閘道爽快回應是「近端路徑正常」的好證據；閘道不回應、或回應得很慢，卻不是「它壞了」或「它轉送得慢」的證明——控制平面回應的優先權低於它轉送的流量，所以失敗那一列的句子會點名發生的是哪一種。自 1.2.12 起 fingerprint 讀的是哪一種量測決定了那一列——`Rule` 欄位，`loss` 或 `latency`（backlog #67）——所以「閘道沒有回應」只會由回覆沒有回來的閘道列選出，而每次探測都回應、只是回應得慢的閘道是品質問題：沒有別的東西警告或失敗時是 `quality`，否則是 `mixed`。2026-09-12 決定：有回應但很慢的閘道是品質 fingerprint 而不是連線 fingerprint，因為閘道是到得了的，而 `ping-gateway` 本來就是四個品質標籤之一；`gateway-up-internet-dead` 仍然要求有一列通過的閘道列，所以慢的閘道旁邊有失敗的群組時是 `mixed`——它兩者都不點名，而這是對的。這項檢查維持必要——連自己閘道都到不了的機器通常真的有問題值得回報，而另一個選項（不計權重的列）會讓純 Wi-Fi 機器唯一的近端量測什麼都推不動（2026-09-10 決定）——而 1.2.11 起，失敗那一列的詳細資料與「要告訴 IT 的話」會用支援工程師現場手冊的說法說明這個失敗能說明什麼、不能說明什麼：嫌疑，不是定罪。

**近端那一階（1.2.12、backlog #60）。** 出廠的階梯——閘道，再來 `1.1.1.1`——是累積的：每一階都包含前一階的路徑，所以兩階之間的延遲差很弱，遺失差則完全不成立，因為兩階是不同瞬間送出的不同流量。`Tests.NearEndTarget` 加上閘道之前的那一階：主要網卡子網段上、不是閘道的一個 IPv4 位址，出廠時不存在，第一個被 Ping，並且用其他目標一模一樣的路徑量測（`Invoke-PingMeasurement`、探測前後的路由查詢、自適應取樣），帶自己的標籤 `ping-near-end`。它在探測之前先被放到位（`Test-NearEndTargetPlacement`）：等於主要網卡某個閘道的位址、這台電腦自己的位址之一（送給它的探測由這個堆疊自己回應，什麼都沒經過）、或它所在子網段的網路位址或廣播位址，都被當成設定錯誤拒絕；不在任何主要子網段上的位址報成「沒有探測」——一列不計權重的 `INFO`，是關於機器在哪裡、而不是關於網路的事實，目標為必要時再加一列有權重的「沒有執行」——只有子網段內的位址才會被量——即使如此，這一階也只在能主張時才主張（審查第 3 輪）：探測沒有綁定，在子網段內只說明主機在哪裡，不說明探測從哪張網卡出去，所以只有 `Get-RouteSelection` 在探測前後都回傳目標子網段上、下一跳為直連（`0.0.0.0`）的來源位址——也就是連接路由，因為一條經預設閘道往那台主機的 `/32` 路由來源與網卡都相同、卻仍經過路由器（第 5 輪）——這一列才主張本地路徑；否則它保留標題與量測，說明為什麼不能主張這一階，並標成 `ping-target`，讓 fingerprint 永遠不會把它當成近端的證人，而延續取樣的第二輪也可以收回第一輪的主張。閘道那一列用同一條件主張它那一階（第 4 輪）：只有探測前後選到的都是提供這個閘道的某張網卡所在子網段上的來源時才主張；否則它的階梯句說它不能主張路徑，但標籤維持 `ping-gateway`，因為閘道仍然是它量測的目標。而摘要只透過 `Path`——近端列或閘道列在主張了自己那一階之後才寫上的那張網卡，主張不了的列和從不主張的遠端列都是空的（第 6 輪：原本是兩次查詢一致的那個介面，而經過路由器到達的閘道列也有那個）——把近端列和失敗的閘道列配對，因為經由一張網卡到達的近端主機說明不了另一張網卡的本地路徑：`Path` 不同或沒有的失敗閘道，或不全在近端列那張網卡上的多個失敗閘道，都維持中性的那一行。標記為必要卻沒有位址的近端目標是兩列——不計權重的提示與有權重的「沒有執行」列——而不是默默跳過的檢查；空白且選用是出廠的停用狀態。名稱、佔位符，以及點分十進位以外的任何寫法——`3221225994`、`0xC0.0.2.10`、`192.0.2.010`，.NET 的解析器都接受，分別讀成十進位、十六進位和八進位，最後一個讀成 192.0.2.8——都過不了設定檢查對這個鍵較窄的規則（`Test-NearEndAddressSyntax`），因為這一階必須在送出任何東西之前就放到位，名稱會讓它落在解析器之後，而設定檔寫的和探測送去的必須是同一個字串；放置本身比較的是解析後的形式（`Get-CanonicalIPv4Text`），所以沒有任何寫法能不經正規化就進到自身位址、閘道或子網段的測試。近端那一列和閘道那一列各帶一行**階梯句**，說它們的探測經過了哪些路段、沒有經過哪些——只有本地路徑、由普通主機回應；本地路徑、由閘道的控制平面回應——而近端那一列帶著讀法規則：通過的一階說明它經過的路段在那一刻是通的，第一個失敗的一階把問題放在最後一個通過的階之外、但不會更近，兩階的數字不能相減成兩階之間那一段的遺失率。遠端目標的列不主張自己是哪一階，因為額外目標在閘道的哪一邊不是那一列量過的東西。近端這一項是執行時組出來的，從來不從 `PingTargets` 讀，所以清單裡的項目不能把自己升格成這一階，而 traceroute——它在清單裡找目標——永遠不會往它追蹤（把子網段內的主機列在 `PingTargets` 第一個的站點，一向會追蹤那台主機，現在也一樣）。沒有東西會用 TTL 限制的探測算逐跳遺失率，也不該有：中間節點的回覆是它限速的控制平面發出的 ICMP 錯誤。`gateway-unreachable` 的「要告訴 IT 的話」會讀這一階：近端列通過時，第二行把問題放在閘道本身；近端列丟了回覆時，指向閘道之前的本地路徑，另一個可能是那台主機本身；其他情況——沒有近端主機，或它回應得慢——就是摘要一向有的那一行。代價：多一個 ping 目標，`PingCount` 次探測，有回覆遺失時和其他目標一樣延續；主機完全不回應時最多 `PingCount × PingTimeoutMs`。

**`PingCount` 是一個目標「開始」的次數，不是它停下來的次數（1.2.10、backlog #51）。** 4 次探測對上出貨的 5% 警告門檻，遺失 1 次就是 25% —— 連嚴重門檻都越過了 —— 而工具在這個次數下根本無法表達「有一點點遺失」。因此設定的次數只是第一輪，接下來怎麼做由第一輪量到什麼決定：

- **全部都有回覆。** 沒有什麼模稜兩可的事，不會再送出任何東西，健康的一次執行不會比這個版本之前更慢。
- **完全沒有回覆。** 4 次就足以斷定 100% 遺失，再多次也不會更確定，而這正是每多一次都要付一整個逾時的情況。這裡同樣不會再送。
- **有回覆但有遺失。** 這才是模稜兩可的情況。取樣會繼續加到「單一個封包再也決定不了分類」的次數；若 `PingCountMaximum` 更低，就加到上限為止。那個次數是「單一次遺失**以這一列印出來的樣子**仍低於警告百分比」的最小 *n* —— 數字會四捨五入到小數第一位，而分類讀的是印出來的數字，所以決定結果的並不是精確的 `100/n`。在出貨的 5% 下是 **21**：20 剛好等於 5%，而 4.7619% 印出來是 4.8%。在校準成 **4.8%** 時則是 **22**，因為 21 印出來同樣是 4.8%，而 4.8 達到了 4.8% 的門檻 —— 精確算術會停在 21，讓一個封包繼續決定結果，那正是本節自己的缺陷再往裡一層。工具會自己算出需要的次數；`PingCountMaximum` 只是不讓它再往上，並不需要被設成那個次數。

多出來的探測會**分散在本次執行剩下的時間裡，而不是連續送出**。這裡用的 .NET `Ping` 類別在 echo 之間沒有延遲，二十次會全部落在不到一秒之內，等於把同一個瞬間量了二十次；而使用者通常想抓的 —— 時好時壞的連線 —— 需要的是時間跨度而不是次數。它們就在重傳取樣窗把剩餘秒數睡掉之前送出，所以這段跨度花的是本次執行本來就要花的實際時間；若那段預算已經用完，探測就連續送出，執行時間會多出它們所花的時間。這一列在第一輪結束時就寫在它該在的位置，取樣完成後再改寫，所以延續的取樣絕不會把自己那一列擠出 ping 的段落 —— 而且數字、檢測方式那一行與手動驗證那一行，算的都是實際送出的探測次數，不是設定的次數。

**當一個判定會靠單一個封包撐著時，就把它收回來。** 這一列保留量到的每一個數字、並停止決定整體結果，條件是下面兩件事**同時**成立：取樣數小於警告門檻所需的次數，也就是在那裡一個封包就值一整級；**而且**少遺失一次的話分類就會不一樣，也就是這個判定「就是」那一個封包。只成立一件，判定仍然成立 —— 4 次遺失 3 次是 75%，少一次還有 50%，沒有任何東西是靠那一個封包撐著的；21 次遺失 2 次確實會因一個封包而改變級別，但 21 次是 5% 門檻撐得住的取樣數，9.5% 是一次量測。完全沒有回覆的目標也會走到這條規則，而在出貨的次數下它會通過：4 次掉 3 次仍然是嚴重，判定照樣算數。只有整個取樣就只有一次探測時才會被收回，因為在那裡「100 % 遺失」和「掉了一個封包」是同一件事 —— 而 `PingCount` 設成 1 是設定允許的值。兩種情況都不會多送。而被收回的遺失判定不會蓋掉延遲的判定：這一列會交給延遲規則，若達到其中一個門檻就保有權重。

**探測是從哪一張網路卡送出的（1.2.9、backlog #59；這一段在 1.2.11 依 backlog #64 修正）。** 以**位址**給定的目標，它那一列 ping 的詳細資料會寫出路由表為該目標選出的來源位址與介面——自 1.2.12 起還有下一跳：直連代表連接的網路，否則是它經過的路由器——以 `Find-NetRoute -RemoteIPAddress <目標>` 在該目標的探測前後各讀一次，所以兩次之間下一跳變了就讀成改變，階梯句的拒絕就是建立在這上面。這是位址目標的規則；以**名稱**給定的目標在有東西回應之前沒有位址可問，由下一段說明。另外有三種 ping 列完全沒有路由那一行，因為什麼都沒送出、沒有量測可以歸屬：設定值無法成為目標（*設定的位址無法當成 ping 目標*）、佔位符在這台機器上展開不出東西（*找不到可測試的目標*——沒有預設路由時的 `AUTO_GATEWAY`、主要網卡沒有 DNS 伺服器時的 `AUTO_DNS`）、以及嘗試時拋出例外（*Ping 測試無法執行*）。這是「**選擇**」而不是「**觀察**」：查詢回答的是查詢當下系統會選哪一條，而探測隨後是未綁定來源送出的，所以在多網卡機器上 —— 接上 dock、Wi-Fi 漫遊、VPN 剛連上 —— 路由可能在兩次查詢之間改變。因此這一列從不宣稱回應實際走的就是查詢回傳的那一條。兩次查詢不一致時 —— 包含一次查到、另一次沒查到 —— 這一列會報告這個改變，並說明它無法判斷實際是哪一個承載了探測。若 `Find-NetRoute` 不存在、沒有回傳路由或查詢失敗，這個資料會標示為無法取得並附上原因，ping 的量測不受影響 —— 這是本工具每一個 NetTCPIP 呼叫都適用的處理方式。要讓它成為「觀察」就必須綁定來源，那需要 `ping.exe -S`，本工具刻意不這麼做。

**以名稱給定的目標，是用它回應所來的位址去查的。** 路由表是用位址問的 —— `Find-NetRoute` 會直接拒絕名稱 —— 所以對名稱而言，探測之前根本沒有東西可以問，也就不會取得前後兩次的對照；這一列會把這件事說出來，並寫出它實際查的是哪個位址。若根本沒有回應，就連位址都沒有，這一列改而說明這件事。**工具不自己去解析名稱**，那會讓 ping 檢查變成依賴解析器，而正在被診斷的機器往往就是解析器壞掉的那一台。查詢回來是空的三種情況，是用錯誤的識別碼而不是訊息文字區分的（訊息會隨機器的語系而變）：無法到達的位址、不是位址的值、以及查詢本身失敗，各自說明是哪一種。

### 4.5 DNS

使用 `System.Net.Dns.GetHostAddressesAsync()` 並套用逾時。必要 DNS 名稱解析失敗為 `FAIL`，非必要目標為 `WARN`。這個測試驗證作業系統實際解析結果，不會逐台指定 DNS 伺服器送查詢。

### 4.6 TCP 與 HTTP/HTTPS

TCP 測試使用 `TcpClient.BeginConnect()`、逾時等待及 `EndConnect()`，確認主機與連接埠是否可建立 TCP 連線。

**連線時間，以及各個 socket 不得不重送的 SYN（1.2.12、backlog #52）。** 有回應的目標會被連線 `PingCount` 次——決定這一列的那一次，再對它到達的位址連 `PingCount` − 1 次，一次接一次，每一次都是一次獨立計時的新三向交握——這一列的訊息會列出各次時間，以及每一次連線的 socket 不得不重送 SYN 幾次。每次交握之後，工具經 `SIO_TCP_INFO` 向 socket 索取它自己的統計：一個 `TCP_INFO_v0`，其 `SynRetrans` 是「重傳的 SYN 總數」、`RttUs` 是目前的往返時間估計，文件記載自 Windows 10 1703 版與 Windows Server 2016 起支援，而且照微軟的原話「不需要提升的權限」——不像 closed item #57 拒絕採用的逐連線 ESTATS（`SIO_TCP_INFO` 與 `TCP_INFO_v0` 參考文件，2026-09-12 讀取）。參考機在未提權下回傳 88 位元組的結構：對 `1.1.1.1:443` 的一次 7 ms 交握，`SynRetrans` 為 0、往返時間估計 6.3 ms。問不到 socket 時——比 1703 舊的版本、或拒絕回答的 socket——這一列會寫明，改由各次時間代替：每一次都拿來和作業系統的**初始重傳逾時**比較，`Set-NetTCPSetting` 把它記載為「connect（即 SYN）重送之前的時間（毫秒）」（300–3000 ms；2026-09-12 讀取），cmdlet 有回報時取自 Internet 範本，沒有時假設為 1000 ms——參考機的 Windows 11 版本，物件上根本沒有 `InitialRtoMs` 這個屬性，而 `netsh int tcp show global` 回報唯一的全域值 1000；詳細資料會寫明這一列拿到的是哪一種，並以那個 `netsh` 命令作為手動驗證，訊息裡也會把假設值標明為假設值。這種讀法是代理指標，這一列也這麼稱呼它：達到逾時的連線是重傳的 SYN 會顯現的地方，但那段時間也包含 SYN 之前與回覆之後所發生的事，所以它不是計數；而低於逾時的連線，只有在那個逾時值正是該連線所用的那一個時才排除得了重傳，這一點工具無法確認——這正是 socket 自己的計數優先的原因。三條規則讓這個數字站得住。*它是工具自己的流量*：自己的 SYN、對單一具名目標、從詳細資料寫出的本機位址、在這一刻——正是第 4.8 節的系統級計數器無法歸屬的數字，而那些列在該次執行有取樣時也會這麼說。*名稱只解析一次*：`TcpClient` 先解析名稱再送 SYN，所以名稱目標的第一次連線列出時間與它的 socket 自己的計數，之後的連線連的是第一次到達的位址；在代理指標下，第一次的時間只列出、不拿來和逾時比較，因為它含那次查詢。*它不做判定*：這一列的狀態和以前一樣由第一次連線決定；後續連線在第一次失敗處停止，訊息會以序號指出那一次，所以停止回應的目標最多多花一個 `TcpTimeoutMs`，不是 `PingCount` 個；從未回應的目標則是一次連線、不讀逾時值、沒有取樣。在參考機上量到：對 `1.1.1.1:443` 的四次交握 23 / 7 / 7 / 7 ms——一次執行的第一次比後面幾次慢幾毫秒——向 socket 查詢在一個程序裡第一次用時 29 ms，讀取逾時值在網卡探索已載入 NetTCPIP 模組時 41 ms（未載入的新 shell 裡是 468 ms）。沒有新增 JSON 欄位，也沒有門檻。

HTTP/HTTPS 使用 `HttpWebRequest`：

- 方法為 GET，允許重新導向。
- 使用 Windows 系統代理伺服器及預設代理認證。
- 嘗試啟用 TLS 1.2。
- 讀取回應資料流的 1 byte，以確認回應可讀。
- 即使伺服器回傳 4xx/5xx，只要取得 HTTP 回應，也視為「網路路徑可達」；報告仍保留狀態碼。

`RequiredConnectivityGroups` 的邏輯是「群組內至少一種方式成功即通過」，不是所有成員都必須成功。預設 Internet 群組因此可由 TCP 或 HTTP/HTTPS 任一成功證明基本連線。

### 4.7 網卡錯誤與丟棄

使用 `Get-NetAdapterStatistics` 在檢測前後取樣。計算：

```text
錯誤增量 = ΔReceivedPacketErrors + ΔOutboundPacketErrors
丟棄增量 = ΔReceivedDiscardedPackets + ΔOutboundDiscardedPackets
```

若結束累積值小於起始值，視為網卡重連、計數器重設或溢位，列為 `WARN`，不硬算錯誤增量。門檻分別由 AdapterError* 與 AdapterDiscard* 控制。

### 4.8 TCP 重傳

程式以 CIM/WMI 讀取：

- `Win32_PerfRawData_Tcpip_TCPv4`
- `Win32_PerfRawData_Tcpip_TCPv6`
- `SegmentsSentPersec`
- `SegmentsRetransmittedPersec`

這些 RawData 欄位名稱雖含 `Persec`，程式把它們當作前後累積值使用並計算增量：

```text
近似重傳率 = ΔRetransmittedSegments / ΔSentSegments × 100%
```

**分母算的是什麼（1.2.11、backlog #57）。** `Segments Sent/sec` 算的是這台電腦送出的每一個 segment——純 ACK 也算——但不含「只帶重傳位元組」的 segment；`Segments Retransmitted/sec` 算的是每一個「帶有一個以上先前傳過的位元組」的 segment，所以新位元組和重傳位元組同在一個 segment 裡時，兩個計數都會算到它（作業系統自己的計數器說明文字，以及 Microsoft 的 *TCP Object* 計數器參考，皆於 2026-09-10 讀取）。因此上面這個比值是本工具自己的數字，不能和公開發表的重傳率比較：它不是 RFC 4898 刻意與 segment 總數分開的資料 segment 比例（`tcpEStatsPerfSegsOut` 對 `tcpEStatsPerfDataSegsOut`），也不是 RFC 6349 的 TCP Efficiency——那是以位元組計、而且把重傳位元組放在分母裡的。這一列會說明它除的是什麼（每一個印出這個數字的列都帶著這句），但不說數字偏向哪一邊：裡面的 ACK 把它拉得比資料 segment 比例低，被排除的純重傳把它拉得比位元組比值高，兩個偏差都沒有在本工具的任何一次執行上量化過。不計算資料 segment 比例是一個決定（2026-09-10）：能算出它的逐連線計數器是 TCP extended statistics，預設不收集、要由 Administrators 群組成員開啟，而且 Microsoft 建議開了以後不要再關——那是由提權使用者對機器做的寫入，而本工具出貨的承諾是*不需要系統管理員權限*與*不改動任何設定*。`Segments/sec` 也不能當替代分母，它是 Received 加 Sent。

判定規則：

1. 前後任一資料缺少：`ERROR`。
2. 結束值小於起始值：計數器重設/溢位，`ERROR`。
3. 傳送與重傳增量都為 0：樣本不足，`INFO`。窗內**沒有任何** segment 被算成送出時就沒有比值，不論重傳增量是多少：這一列會說比例無法計算而不是印 0%，不帶分母那句，而且——因為 sent 計數器不含只帶先前傳過位元組的 segment——仍可能帶著重傳次數，由下面的小樣本規則報告（1.2.11）。
4. 傳送 segment 少於 `MinimumTcpSegmentsForRate`：不對這個樣本評分。帶著重傳的樣本是 `INFO`，不決定任何事 —— 在 1.2.10 之前是 `WARN`，而自 1.2.8 起它就是 weightless 的，於是留下一個寫著「需要注意」的徽章，旁邊卻是一句「這一列不是證據」；沒有重傳的樣本同樣是 `INFO`。**取樣窗會延長一次（1.2.10、backlog #51）**，條件是樣本結束時低於這個下限、而窗內至少有一次重傳 —— 那是唯一一種「等久一點真的能定案」的情況。什麼都沒重傳的機器不會被延長，因為等久一點只會換來更多的「什麼都沒有」；已經有比例的樣本也不會。第二次讀數是逐通訊協定合併的，所以讀取失敗絕不會弄丟第一次已經讀到的結果，而這一列會說明自己的窗被延長過。
5. 流量足夠時，由**比例**下判定，**次數**只做修飾：
   - **一個比例要有足夠多的事件撐著（1.2.10、backlog #51）。** 比例達到或超過警告門檻、但重傳次數少於 `MinimumTcpRetransmissionsForVerdict` 時，會以 `INFO` 報出它的數字，不決定任何事。在這個工具願意評分的最小樣本上 —— 出貨值是 50 個傳送 segment —— 一次重傳就是 2%，剛好是警告門檻本身；三次是 6%，在這個版本之前光靠比例就會 FAIL。這個下限兩個分支都要過，因為只擋警告分支的下限，會讓最粗的樣本判得比它上面那一階更重。在出貨值下，超過 200 個傳送 segment 就不會有任何東西被壓下來：要被壓下來，必須比例達到門檻、同時事件數少於下限，也就是 `(下限 − 1) × 100 ÷ 警告百分比`。
   - `比例 ≥ TcpRetransmissionCriticalPercent` → `FAIL`。
   - `比例 ≥ TcpRetransmissionWarningPercent` **且** `重傳次數 ≥ TcpRetransmissionCriticalCount` → `FAIL`。次數把比例已經下出來的判定加重。
   - `比例 ≥ TcpRetransmissionWarningPercent` → `WARN`。
   - **次數不再自己發出警告（1.2.10、backlog #63）。** 在這個版本之前，`重傳次數 ≥ TcpRetransmissionCriticalCount` 不管比例多少都會警告，所以夠大的樣本會在門檻表稱為健康的比例上達到它：3 832 個傳送 segment 中有 57 次重傳是 1.487%，卻被報成「需要注意」。界線是 `TcpRetransmissionCriticalCount ÷ TcpRetransmissionWarningPercent`，在出貨的 50 與 2% 下是 2 500 個傳送 segment —— 在那之下，要達到 50 次重傳，比例早就到警告門檻了，獨立觸發什麼也沒加；在那之上，它唯一加上的就是在比例低於本工具自己門檻的樣本上發出警告。它放棄掉的，是唯一一個會對「看似健康的窗裡的一段突發」有反應的訊號，第 8 節記下了這件事。
   - **每一個有評分的列都會寫出是哪一條規則決定的。** `PASS` 不寫，因為沒有任何一條決定了它。

讀取、嘗試次數，以及一列會如何交代它們：

- 每次計數器讀取有八秒時限，並且會嘗試**兩次**。第一次失敗會再讀一次，只有第二次也失敗才寫出 `ERROR`（*無法檢查*）那一列——該列的狀態、名稱與訊息維持第二次嘗試出現之前的樣子。兩次都失敗不會有第三次。
- **基準值**快照每個類別另外做一次會被丟棄的讀取，而且**自成一輪、排在兩個計數器都還沒被讀取之前**；讀數不採用，失敗既不是錯誤、也不算量測嘗試。效能計數器提供者第一次查詢要付的成本因此落在兩個基準時間戳之前，對它們的延後一視同仁，所以拉長不了任何通訊協定的窗——即使它只是慢、而不是失敗，也一樣。若把暖身和量測讀取交錯，TCPv6 的暖身就會落在 TCPv4 的基準時間戳之後，也就是落在 TCPv4 的窗內。結束快照則完全不做這件事：在窗內做，等於拉長它本來要保護的東西。
- 每一次失敗的嘗試都會連同耗時保留下來，**即使後續嘗試成功也一樣**。各列就是依這份紀錄寫出來的：讀不到的計數器那一列會寫出它背後試過幾次，而窗跑得比較久的那一列會寫出有幾秒花在失敗的讀取、以及是哪幾次讀取。
- 時間成本有上限，也明白寫出來：計數器正常的機器上，只多了兩次窗前讀取，成本是毫秒等級；每次讀取都會逾時的機器上，一次執行的六次讀取合計最多八十秒，而第二次嘗試出現之前是三十二秒。

取樣時間由**該通訊協定自己的兩個時間戳**計算，而不是由包住它們的快照時間戳計算。兩個通訊協定是循序讀取的，每個時間戳都在自己的讀取回來時取得，因此會拉長某個窗的，是那些延後了它的結束時間戳、卻沒有延後它的起始時間戳的讀取：在**結束**快照裡，是排在該通訊協定之前（含自己）的每次讀取；在**基準**快照裡，則是排在它*之後*的每次讀取——那些延遲會把後面的起始時間戳連同整段執行一起往後推。因此耗盡時限的 TCPv6 基準讀取會落在 TCPv4 的窗內，而不是它自己的窗內。窗前讀取則不落在任何窗內，因為它們全都在兩個基準時間戳之前完成。增量不受影響——每個增量都是該通訊協定自己兩次讀數的差——比例又是比值而不是時間，所以失敗的讀取一直以來只弄壞了時間長度這一個數字。該列會把量到的時間長度與設定的 `RetransmissionSampleSeconds` 並列，後者是最短時間，不是目標值。

這是整台電腦、整個取樣期間的系統級近似值，無法指出哪一個程式、遠端主機或 TCP stream 造成重傳——而自 1.2.12 起它不必獨撐：第 4.6 節的 TCP 連線列帶著這一列給不了的數字——工具自己對單一具名目標的交握，以及各 socket 不得不重送的 SYN——而這裡的列在該次執行有取樣時也會這麼說（backlog #52）。兩者永遠不是同一個數字：這一列保留它以前印出的每一個數字並寫明自己是系統級的；那一列寫出它的目標和樣本數。

### 4.9 整體結果

整體狀態採固定優先序：

```text
FAIL > ERROR > WARN > PASS
```

因此任何 `FAIL` 會顯示「偵測到異常」；沒有 FAIL 但有無法執行項目時顯示「檢測未完整」；再其次是警告；最後才是整體正常。**自 1.2.8 起，這個優先序只套用在這次執行量到的列上**（backlog #39）：被標記為 `Weightless` 的列——量不到的統計、對所套用門檻來說太粗的樣本、關於本次執行輸入的事實——不參與這個比較，也不參與指紋的任何判斷式；而 `Get-SummaryCounts` 與報告的提醒仍然讀頁面上的每一列，所以這種列保有徽章與對徽章的說明。標記是逐分支 opt-in：沒被點名的列一律保有權重，因此日後新增的檢查不會因為漏寫而失去權重。

### 4.10 網卡分類、IT 診斷資料與指紋（1.2）

每張網卡都會分類為實體或虛擬：以 NetAdapter 的 `Virtual`／`HardwareInterface` 旗標為準，CIM 備援用 `Win32_NetworkAdapter.PhysicalAdapter`，沒有旗標時以描述字串樣式判斷（VirtualBox、Hyper-V、VMware、TAP、tunnel、loopback、WAN Miniport、WireGuard、ZeroTier、Tailscale、Docker、VPN、ISATAP、Teredo）。虛擬網卡列為 `INFO`，不套用 APIPA 與無 IPv4 規則；「可用網卡」列出實體與虛擬數量，只有虛擬網卡承載閘道時（VPN 或虛擬化）為 `WARN`，完全沒有實體網卡時為 `FAIL`。取樣期間沒有流量的網卡或虛擬網卡，其錯誤計數列為 `INFO`，因為計數器只有在有流量時才能作證。公司標準比對的主要網卡選取方式不變。

IT 診斷資料每次都會執行（可在設定檔 `Checks` 區段或用 `-NoWifi`／`-NoTraceroute` 個別停用），產生 `INFO`（收集到的內容，或沒有東西可收集、來源不存在的說明），讀取來源發生錯誤時為 `ERROR`，帶 `Scope = "IT"`，顯示在 HTML 報告收合的 IT 區段：

| 檢查 | 來源 | 說明 |
|---|---|---|
| Wi-Fi 無線 | `netsh wlan show interfaces`，因標籤隨語系不同、Windows 10 與 11 順序不同，改依值的形狀解析（MAC、GHz、802.11x、百分比、數字） | SSID、BSSID、頻段（該版本未印出時由頻道推斷）、頻道、速率、訊號 %、RSSI（netsh 有印時用實際值，否則由百分比估算） |
| IPv4 預設路由 | `Get-NetRoute -DestinationPrefix 0.0.0.0/0`，依有效計量（路由計量＋介面計量，即 Windows 的選路順序）排序 | 多條路由分屬不同介面時在詳細資料提示；沒有預設路由的機器列為 `INFO` 並如實說明，不再是路由表錯誤（1.2.3） |
| 閘道鄰居（ARP） | `Get-NetNeighbor`（備援 `arp -a`） | MAC 缺少或不完整時提示；閘道 Ping 仍是權威判定 |
| Proxy 設定 | HKCU Internet Settings、`WebRequest.GetSystemWebProxy`、`netsh winhttp show proxy` | 解釋「TCP 443 通但 HTTPS 失敗」 |
| Traceroute（前幾跳） | .NET `Ping` 以 TTL 1..N（預設 3，最多 10），每跳 1000 ms | 目標為第一個非 AUTO 的 Ping 目標 |
| 網卡驅動程式 | NetAdapter 的 `DriverVersion`／`DriverDate`／`DriverProvider` | 只列實體網卡 |

IT 範圍的項目不影響整體結果與摘要計數：`Get-OverallStatus` 與 `Get-SummaryCounts` 排除 `Scope = "IT"`，IT 資料收集失敗只會在 IT 區段內顯示為「無法檢查」（整個 IT 步驟都在該範圍執行，即使發生非預期例外也不會翻轉整體結果）。虛擬網卡的計數器項目不論增量大小都只列為資訊。

每筆結果現在帶有語言中立的 `Tag`（例如 `ping-gateway`、`ping-near-end`、`dns`、`connectivity-group`、`tcp-retransmissions`、`wifi`、`wifi-retry`）與 `Scope`（`Main` 或 `IT`）；自 1.2.8 起又多一個 `Weightless` 布林值（backlog #39）：`true` 代表這一列保有徽章、訊息與統計數字，卻不決定整體結果、也不影響指紋。這個欄位是在 **`SchemaVersion: 2` 下新增**，而不是升到 3：依本文件自己的規則，使用者只讀有文件記載的欄位，沒讀的欄位影響不了它，而這份欄位清單就是新欄位成為契約的地方。自 1.2.12 起再依同一條規則附加一個 `Rule` 字串（backlog #67）：只在 ping 的列上有值，遺失級別決定狀態時是 `loss`，真的回來的回覆決定時是 `latency`，否則是空的；另外附加一個 `Path` 字串（backlog #60）：只在主張了自己那一階的近端列或閘道列上有值，是探測經證明走過的那張網卡的介面別名；主張不了的列和其他所有 ping 列都是空的。指紋由標籤計算：`local`、`gateway-unreachable`（回覆沒有回來的閘道列，且沒有任何閘道列通過；有設定近端主機時，它的第二行讀近端那一階）、`gateway-up-internet-dead`（閘道有回應、必要連線群組失敗且沒有任何群組通過）、`dns`（只在沒有任何 DNS 檢查通過時）、`quality`（遺失、延遲——包括每次探測都回應、只是回應得慢的閘道——重傳或網卡錯誤的警告或異常，且沒有其他項目失敗）、`attention`（其他只有警告的執行）、`mixed`、`incomplete`、`healthy`，驅動 HTML 與文字報告頂端的「要告訴 IT 的話」，JSON 存在 `Fingerprint`。

執行選項由入口決定：`Start-NetworkCheck-IT.cmd` 帶 `-Interactive -ExpandDetails`；`-PingTarget`、`-DnsName`、`-TcpTarget`（host:port）、`-HttpUrl`、`-PingCount`、`-PingCountMaximum`、`-SampleSeconds`、`-TracerouteHops`、`-NoTraceroute`、`-NoWifi` 只影響本次執行（在同一個值裡，多個 Ping／DNS／TCP 項目可用逗號、分號或空白分隔，例如 `-PingTarget 10.0.0.1,10.0.0.2`，多個 URL 只能用空白分隔，因為逗號與分號是 URL 的合法字元；從 shell 傳入時請把清單寫成一個逗號分隔或加引號的值：多出來的第二個值會被 PowerShell 在腳本開始之前直接拒絕（1.2.7 起不再有任何位置參數），而在 PowerShell 提示字元下沒加引號的分號會結束陳述式），並記錄在報告的執行設定行與 JSON 的 `RunOptions`（`EntryPoint`、`ExtraTargets` 為通過驗證的值、`RawTargets` 為原始輸入、`PingCount`、`PingCountMaximum`、`SampleSeconds`、`TracerouteHops`、`ChecksEnabled`）。IT 面板的**兩個** Ping 旋轉鈕 —— 起始次數與上限 —— 範圍都是設定的 `PingCountMaximum`（預設 21），取樣秒數旋轉鈕為 1–120 秒；設定值超過上限時會放寬旋轉鈕範圍，因此面板會顯示設定值，未更動就開始也會以設定值執行（1.2.1）。1.2.10 之前，Ping 旋轉鈕開在 20 —— 一個在這個儲存庫或套件裡都找不到理由的數字 —— 而設定檢查根本沒有任何上限。設定檔永遠不會被寫入。JSON 的 `SchemaVersion` 為 2。

### 4.11 Wi-Fi 802.11 重傳計數器（1.2.12、backlog #61）

**用途。** 只有 Wi-Fi 的機器做不了 SOP 描述的三方比較，而空氣在這支工具其他部分都看不到的一層留下它的簽名：802.11 MAC 會重送沒收到確認的框，重送成功的框被吸收成延遲。IP 與 TCP 看不到遺失，ping 列看到的是慢一點的回覆，TCP 重傳列則什麼都看不到。所以無線重傳率是唯一能把網卡與基地台之間的空氣、和基地台後面的一切分開的數字，也是這支工具唯一讀取的射頻數字（限制 6）。它以標籤 `wifi-retry` 寫在主報告裡，是一列不決定任何結果的「資訊」列。

**怎麼讀，以及背後的決定。** Windows 只透過 Native Wifi API 提供這些計數器——以 `wlan_intf_opcode_statistics` 呼叫 `WlanQueryInterface` 回傳 `WLAN_STATISTICS`，其中 `PhyCounters` 陣列帶著每個 PHY 的 MAC 框計數器——`netsh` 沒有對應項。所以讀取器（`Get-WifiRetrySnapshot`）是執行時由 `Add-Type` 在記憶體內編譯的幾行 P/Invoke：一支原本是純 PowerShell 的腳本裡的 unmanaged code。v1.2 設計筆記為射頻資料拒絕過這個選擇，因為 `netsh` 供得了；這一項採用它，因為別無他法（2026-09-12 決定；五點寫在 backlog 項目裡）。它不需要提權——2026-09-10 的探測與這次修改都在參考機上以未提權的程序量過——每個程序一次約 0.7 秒，磁碟上不留任何東西。計數器在 TCP 基準值之前讀，讓編譯在重傳視窗之外付掉；TCP 視窗結束（有延長就延長之後）再讀一次，所以兩個視窗涵蓋同一次執行。讀取器無法編譯或載入（應用程式控制規則拒絕 C# 編譯器或記憶體內組件）、WLAN 服務沒有回應、或機器沒有無線介面時，一列不計權重的列會說明是哪一種；只在兩次讀取的其中一次列出的介面——執行期間被啟用、停用或換掉——各自得到一列不計權重的「無法檢查」列，而每一列逐介面的列都寫出自己的介面 GUID；受限的 PowerShell 語言模式一如既往在任何檢測之前就擋下整支工具，所以這一列在那裡沒有自己的分支。`Checks.WifiRetryCounters` 只能在設定檔裡把讀取器關掉——沒有面板核取方塊、沒有參數——關掉後完全不寫任何列，和被停用的 IT 診斷資料一樣。

**PHY 陣列，以及為什麼項目絕不相加。** `WLAN_STATISTICS` 為網卡支援的每個 PHY 各放一個 `WLAN_PHY_FRAME_STATISTICS`——參考機上是六個——而文件沒有說驅動程式怎麼填。參考機的驅動程式（Intel Wi-Fi 6E AX211）把介面的總計寫進「每一個」項目：六列完全相同的計數器，同步變動，2026-09-12 量到。相加會把每一個框算六次。所以這一列取傳送框差值最大的項目當介面的數字，寫出視窗內有幾個項目變動、是否一致，不一致時逐一列出。逐 PHY 歸屬框的驅動程式在單一 PHY 的執行裡會給出同樣的答案，而換過 PHY 的執行會被少算，不會被算好幾次。某個驅動程式到底有沒有填這些計數器是驅動程式說了算：量過的只有一張網卡、一個驅動程式（限制 18）。

**數字、它的分母，以及不能怎麼讀。** 比率是重傳除以嘗試送出的框：`ullRetryCount`——重送一次以上後成功送出的框——除以 `ullTransmittedFrameCount` + `ullFailedCount`，因為傳送計數不含到達重傳上限後放棄的框，那些在 `ullFailedCount` 裡；`ullMultipleRetryCount` 是重傳計數的子集，照子集列出，兩個重傳計數器不相加、也不互除。計數器是這次關聯的累積值，所以這一列報告這次執行視窗內的前後差值、印出兩次讀數，計數倒退時（網卡重新連線，或驅動程式重設）沿用 TCP 列的分支。視窗內什麼都沒送的執行沒有比率，並且會說明。這一列沒有門檻，因為無線重傳率沒有任何有依據的門檻（已結案的 #56 立下的規則），而手冊寫明這個數字不是什麼：既不是算任何線路上 TCP segment 的 TCP 重傳率，也不是 ping 遺失率，因為重送的框通常會到，只是晚一點。參考機上一次 24 秒的執行讀到 211 個框中有 66 個重傳（31.3 %），其中 22 個重傳超過一次，沒有放棄——這是這個專案產出的第一個這種數字。

## 5. 錯誤處理設計

- 每個主要步驟經 `Invoke-CheckStep` 包裝；例外轉成 `ERROR` 結果並繼續後續檢測。
- `Get-ExceptionDetails` 記錄例外型別、訊息與最多五層內部例外。自 1.1.4 起，腳本位置與呼叫堆疊改由 `Get-ExceptionDiagnostics` 另外收集，只寫入 JSON 報告的 `Diagnostics` 欄位；HTML 與文字報告改為顯示一行提示，因此本機檔案路徑不會出現在給人看的報告中。緊急（`FATAL`）檔案仍保留完整內容。
- 網路類錯誤會在報告語言中附上一行 `原因：`，依據的是錯誤碼而不是作業系統的用字：`SocketException.SocketErrorCode` 與 `WebException.Status` 都是列舉，而訊息文字跟著機器的系統地區設定，因此可能以另一種語言出現在本報告中（待辦 #14）。該行同時附上代碼（`[SocketError HostNotFound]`），表中未收錄的代碼則只顯示代碼本身；作業系統的原始訊息一律保留，且一律排在原因之後——多行處在下一行，Ping 與 traceroute 的單行紀錄則接在同一行。此行會出現在例外細節、Ping 的逐次紀錄、TCP 與 HTTP 的失敗說明，以及 traceroute 的單一躍點狀態。cmdlet、CIM/WMI 或檔案系統產生的錯誤沒有這種代碼，維持作業系統的原始用字。本工具自己的 DNS 與 TCP 時限自 1.2.3 起也以同樣方式分類，代碼為 `[ToolTimeout]`：在設定的時限內沒有任何回覆、也沒有被拒絕，這正是防火牆默默丟棄封包或主機無法到達時的樣子（待辦 #27）。
- GUI 初始化失敗時改用 Console 模式。
- 報告資料夾不可寫時改到 `%TEMP%\NetworkHealthCheck\Reports`。
- HTML、TXT、JSON 分別嘗試寫入。自 1.1.5 起，單一格式失敗只會記錄並在 GUI 顯示警告，成功的格式仍可使用：「開啟報告」會開啟 HTML、TXT、JSON 中第一個可用的檔案，文字模式對缺少的格式顯示「（未寫入）」。三種格式全部失敗時才寫一份緊急 `FATAL` 文字報告（含三個寫入錯誤與呼叫堆疊）並顯示一次錯誤對話框，文字模式結束碼為 1。報告階段在 `Run-AllChecks` 內只處理一次、不再重新拋出，外層處理器不會再產生第二份 FATAL 檔或第二個對話框。
- 啟動器本身找不到檔案/PowerShell或收到非零結束碼時，顯示提示並寫 `LauncherError.txt`。1.2.3 起檔案中的建議依原因而定：找不到程式檔→完整解壓縮 ZIP；結束代碼 3（語言模式守門）→閱讀環境報告；其他非零代碼→閱讀錯誤上方 PowerShell 自己的訊息，若提到簽章或原則就請 IT 允許腳本（待辦 #28）。

機器上實走使用手冊，得到六項發現，全部都是手冊的問題，沒有一項是腳本的：重傳計數器讀不到時，工具自己的八秒逾時也列進原因；樣本偏少的三則訊息從只寫一則改成三則都寫，包含會把整體結果變成需要注意的那一則；`LauncherError.txt` 寫在啟動器旁邊時另外帶的 PowerShell 路徑補上；套件放在 OneDrive 會備份的資料夾裡時，報告一寫出就被複製上雲端，而解壓縮到 Windows 11 桌面正是這種情形；解壓縮出來的資料夾裡還有一層同名資料夾，在讀者遇到它的地方寫清楚；安全性警告說發行者無法確認，則以工具沒有數位簽章、以及 IT 可拿去和發行說明比對的雜湊值回答。工具本身同樣沒有變更，走查的工具面發現是待辦 #38 到 #47。 1.2.6 版（2026-09-09）同樣是文件版本，而且來自同一場走查的另一種語言：有人在繁體中文機器上走過繁體中文使用手冊，兩句話沒有通過 — 手冊引用的發行者字樣，不是那種機器上的對話框寫的字；而四本手冊都用面板顯示不出來的標籤稱呼 IT 面板的額外 TCP 欄位，因為「額外 TCP（host:port）」在面板給的 100 px 框裡要 153 px（英文套件 134 px），第二行被裁掉。格式現在寫在正文裡並附上範例值，不再放在一個沒有人讀得到的標籤上。工具本身同樣沒有變更，那場走查的工具面發現是待辦 #49 與 #50。 1.2.7 版（2026-09-09）是 1.2.3 之後第一個真正改動工具本身的版本，六個項目都關於「畫面在說話的那一刻說了什麼」。IT 面板的標籤各自帶著自己的寬度，於是兩種語言下都會換行、第二行被裁掉的那一個放得進去了，而 headless GUI 步驟會在兩種語言下量每個控制項的文字與它的框（#49）。面板在執行開始之前就用實際執行所用的規則檢查打進去的額外 TCP 目標：標記欄位、給出範例值，再按一次才不帶那個目標開始；四個自由輸入欄位滑鼠移上去都有範例（#45）。視窗和文字模式指名一個要交出去的檔案，而不是一個路徑和三個路徑，報告結語的最後一行指的也是同一個（#46）。那段結語現在宣稱的是判定真正做過的事 —— 所有必要檢查都通過 —— 並且點名沒有回應的選用目標（#35）。報告裡的說明，只在真的有列帶著「無法檢查」時才解釋那個徽章，也只在真的算出比例時才替重傳比例加註（#40）。而命令列上多出來的值會被 PowerShell 直接拒絕，不再繫結到 -ConfigPath、把一個目標無聲無息地弄丟（#36）。1.2.8 版（2026-09-09）談的是工具失去的量測，以及它從來沒有交代的那幾秒（backlog #38）。效能計數器讀取用完八秒時限後會再嘗試一次，只有第二次也失敗才寫出「無法檢查」那一列，而該列的狀態、名稱與訊息維持不變；基準值快照在取樣窗開始前，每個類別先做一次會丟棄的讀取，讓提供者第一次查詢的成本付在量測之外；每一次失敗的嘗試都連同耗時保留，即使後續嘗試成功也一樣，各列就是依這份紀錄寫出來的；每一列的取樣時間改由該通訊協定自己的兩個時間戳計算，而不是由外層快照的時間戳計算，並與設定的最短時間並列；窗跑得比較久的那一列會寫出是哪幾次讀取拉長了它。沒有任何讀取失敗時，狀態、訊息與每一個數字都與先前相同；詳細內容裡有兩件事不同，而那正是這次發行的重點：取樣時間是該通訊協定自己的窗，而不是包住它的快照之間的長度，並且旁邊會並列設定的最短時間。

### 7.3 建議 Windows 驗收矩陣

| 情境 | 預期結果 |
|---|---|
| Windows 11、一般使用者、正常 DHCP | GUI 自動完成；HTML/TXT/JSON 產生；核心連線項目通過。 |
| 關閉 Wi-Fi/拔除網線 | 無可用網卡、閘道或 DNS 顯示 FAIL；仍產生報告。 |
| DHCP 失敗取得 169.254.x.x | APIPA 項目顯示 FAIL。 |
| 無效 JSON | 畫面與報告記錄設定檔錯誤，改用預設值繼續。 |
| 報告目錄唯讀 | 改存 `%TEMP%` 並顯示提示。 |
| 公司政策封鎖 PowerShell | 啟動視窗顯示原因並嘗試寫 `LauncherError.txt`，建議依原因而定。 |
| GUI 元件不可用 | 自動切換文字模式，或手動執行 Console 啟動器。 |
| DNS 被阻擋 | DNS 必要目標 FAIL，但 IP/TCP 測試仍執行。 |
| TCP Port 關閉 | 必要 TCP 目標 FAIL；非必要目標 INFO；群組依其他成員判定。 |
| HTTP 回傳 403/500 | 視為路徑可達並保留狀態碼，不誤判為完全無網路。 |
| 網卡重連 | 計數器下降時報告重設警告，不產生負增量。 |
| 有足夠 TCP 流量 | 與 `Get-CimInstance Win32_PerfRawData_Tcpip_TCPv4/TCPv6` 前後差值比對。 |

驗收時應把報告值與 `Get-NetIPConfiguration`、`Get-NetAdapterStatistics`、CIM/WMI 原始計數器及公司網路規劃表交叉比對。

## 8. 已知限制

1. **只支援 Windows。** 目標為 Windows 10/11 與相容 Windows Server，需 PowerShell 5.1 或更新版本。
2. **不是封包分析器。** 不擷取封包、不分析 ACK/序號，也不能證明某一條 TCP 連線的重傳根因。
3. **TCP 重傳是系統級短樣本。** 背景更新、瀏覽器或其他程式都可能影響數字；無流量時結果只代表樣本不足。歸屬得了的對應數字——第 4.6 節的連線時間——是對單一目標的幾次交握，不是流量樣本，而且不做判定。
4. **Ping 可能被封鎖。** ICMP 失敗不等於 TCP/HTTPS 一定失敗，必須綜合判讀。
5. **多網卡/VPN 會彙整。** 任一介面符合部分規則可能使該項通過；複雜公司環境應增加介面名稱、類型或路由篩選。
6. **除了網卡自己的計數器，沒有 VLAN、交換器或 Wi-Fi 射頻資料。** 無法直接看到 VLAN ID、交換器 CRC、光模組、頻道壅塞或 AP 漫遊紀錄；它唯一讀取的射頻數字是網卡自己的 802.11 重傳計數器（第 4.11 節），那是空氣的用戶端這一側，僅此而已。
7. **無法確認未提供的公司標準。** Expected 留空時只顯示現況，不猜測正確 IP。
8. **HTTP GET 會接觸目標服務。** 應使用公司核准、無副作用的健康檢查 URL；部分網站可能記錄來源 IP、User-Agent 或代理認證流程。
9. **門檻需要校準，因為出廠的值沒有任何外部依據。** backlog #56 檢視過的門檻區塊十二個值，都是在沒有標準、沒有量測、也沒有記錄下理由的情況下選出的營運預設值——其中兩個是「有就值得顯示」這條政策（網卡錯誤與丟棄的警告增量 1），另外十個是某人挑的量值——而 1.2.10 新增的第十三個 `MinimumTcpRetransmissionsForVerdict` 有記錄下推理（backlog #51），同樣沒有外部依據。現有的公開標準也給不出依據：它們定義的是怎麼量測，或是對某一類服務、在某個範圍內設定目標值，從來不是「超過 X % 網路就有問題」這種通則。檢視了哪些文件、每一份實際定義的是什麼、以及各自對照來源查證的日期，只記錄在一個地方——repo 裡對應本文件版本的門檻頁面 <https://github.com/kevintechin/network-support-toolkit/blob/v1.2.12/docs/thresholds.md>（英文），最新版在 `main` 分支（2026-09-10 決定；IT 部署手冊的門檻表逐值註明）。預設值不保證適合 Wi-Fi、VPN、衛星、跨國 WAN、資料中心或高吞吐伺服器。
10. **權限/端點防護可能限制資料。** AppLocker、WDAC、EDR、WMI 政策或損壞的效能計數器會導致 `ERROR`，不代表已證實網路故障。
11. **報告含敏感資訊。** 可能包含電腦名稱、使用者、MAC、IP、DNS、內部服務名稱與例外堆疊（後者僅存在於 JSON 報告，含本機腳本路徑）；外傳前需依公司政策處理。
12. **沒有自動修復。** 工具只診斷，不變更設定；這是刻意的安全界線。

13. **Wi-Fi 資料來自用戶端且由文字解析。** `netsh` 輸出依值的形狀解析，特殊版本可能留空欄位；該版本未印出 RSSI 時為估算值。AP 的用戶端列表才是較強的證據。
14. **沒有 NetAdapter 旗標時的網卡分類是啟發式的**（描述字串樣式）。
15. **Traceroute 有上限**：最多 10 跳、每跳 1 秒；沒有回應的跳顯示為 `*`，預設 3 跳通常到不了公網目標，目的是看封包停在哪裡，而不是抵達。
16. **整個窗的平均值分不出突發與平均分布。** 重傳計數器只在窗的頭尾各讀一次，所以「窗裡某十秒內重傳了 50 次」與「50 次平均散布在整個窗」會產生一模一樣的兩個數字。在 1.2.10 之前，獨立的次數觸發條件對兩者都會有反應、卻說不出是哪一種，這正是它被移除的原因；真正能回答這個問題的是在窗內以固定間隔讀取計數器，目前沒有任何版本這麼做。
17. **階與階的差不是路段的數字。** ping 階梯——近端主機、閘道、遠端——是累積的：失敗的一階把問題放在最後一個通過的階之外，而兩階的遺失率不能相減成兩階之間那一段的數字，因為它們是不同時刻的不同流量。沒有東西會用 TTL 限制的探測算逐跳遺失率，也不該有：中間節點的回覆是它限速的控制平面發出的 ICMP 錯誤，逐跳百分比會在轉送得好好的節點上顯示遺失。

18. **無線重傳率是驅動程式說了算、不決定任何結果，而且需要編譯器。** 這些計數器來自 Native Wifi API，API 文件寫了它們是什麼，卻沒寫哪些驅動程式會填、怎麼填逐 PHY 的陣列——參考機的驅動程式把介面總計鏡射到每一個項目，所以項目絕不相加——把它們留在零的驅動程式會給出一列裡面沒有任何框的列。這一列沒有門檻，因為沒有任何有依據的門檻；它需要的幾行 P/Invoke 無法在記憶體內編譯時（應用程式控制規則拒絕 C# 編譯器或記憶體內組件）這一列會缺席並說明原因；受限的 PowerShell 語言模式則在任何檢測之前就擋下整支工具。量過的只有一張網卡、一個驅動程式。

## 9. 發行與維護建議

- 套件內的 IT 部署手冊（`NetworkHealthCheck_IT_Deployment_Manual_*.md`，1.2.4 起）是本節的操作版本：逐鍵說明的設定檔、部署、套件驗證，以及安全政策對工具的影響。
- IT 應先修改設定檔，把外部預設目標換成公司核准的內部/外部服務。
- 在代表性的有線、Wi-Fi、VPN 與無外網環境建立基準報告。
- 修改 `.ps1` 後重新執行靜態驗證與 Windows 驗收，並更新 SHA-256。
- 大量部署可用軟體派送系統散佈整個資料夾，但不要只派送單一啟動檔。
- 若需要精確定位重傳，將本工具的時間點與 Wireshark、pktmon、交換器介面計數器或集中監控資料對照。
