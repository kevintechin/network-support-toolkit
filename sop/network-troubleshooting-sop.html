Station 0 — Profile the Reporter 30 seconds, before any troubleshooting

We work through the person reporting the problem. Who they are decides what evidence you can trust and what actions you can delegate. Calibrate with one question — "Are you comfortable running a command in a terminal?" — and listen to their vocabulary ("the network is down" vs "DHCP isn't handing out leases").

Front Door — Four Isolation Questions cut the search space before touching anything

1Blast radius

One user or many? One VLAN / SSID / location, or all? Wired and wireless both? One user → endpoint. One switch → uplink. Everyone → gateway or ISP.

2What changed?

Config, firmware, new device, cabling work, power event — anything in the last 24–72 h?

3Failure fingerprint — pick the lane
No IP (169.254.x.x)DHCP path: port VLAN → uplink → relay → server
IP, but gateway unreachableLocal L1/L2: cable or RF, port, VLAN
Gateway OK, internet deadRouting / NAT / firewall / ISP
IP works, names failDNS
4Constant or intermittent?

Intermittent points at performance causes: RF interference, congestion, duplex mismatch, retransmissions.

Read State Before Config the network testifies before you open a single settings page

Config tells you what the network is supposed to do; state tells you what it is actually doing. Read state first — it needs no design document, it cannot lie, and it is read-only. Three families: tables (the network's memory — MAC, ARP, clients, leases, sessions), counters (always a delta: two samples, 30–60 s apart), and probes (differential tests — two pings that differ in exactly one thing: ping the IP vs ping the name; if one works and one fails, that one difference names the fault). Two discriminators, in order — counters first: climbing CRC/alignment errors mean physical (cable, SFP, duplex); discards mean congestion or policy, not physical. Then the VLAN probe: a fault that hits one VLAN but spares another on the same wire is config — physical faults are VLAN-blind; config faults are VLAN-selective — but mind the asymmetry: all-VLANs-dead proves nothing by itself (a whole-link config error looks just like a dead wire). The station cards above embody this order — every Read state block comes before Verify config.

Counter reference — read as deltas; absolute values are history, not evidence:

CounterClimbing meansWhich drawer next
CRC / FCS errorsFrames arriving corrupted — cable, connector, SFP, EMI, duplexPhysical — the reliable convict
Alignment / runts · late collisionsCollisions; the classic duplex-mismatch signaturePhysical / negotiation
Giants (oversize)MTU / jumbo-frame inconsistency between endsConfig
RX / TX discardsValid frames dropped — buffers, QoS, storm controlCongestion / policy
Broadcast share spikingLoop or stormConfig / loop
Link flaps (up/down count)Unstable link or far-end rebootsPhysical / power
RX near zeroFar end down, admin-down, or a broken pair — ambiguousNever convict alone — second witness (Rule 3)

Caveats: counters only testify when traffic flows — a dead link shows zero errors, which clears nothing. CRC counts at the receiver — the fault lies between the far-end transmitter and this port. Directional probe: send a known burst (ping -n 20 <gateway>) and read deltas at both ends — NIC TX up but switch RX flat = outbound leg broken; switch TX up but NIC RX flat = return leg. Three Rules That Keep You Honest

Fix one, test one.

State the expected outcome before you retest. If the result doesn't match the prediction, revert before trying the next idea.

Close the loop end-to-end.

Valid IP → ping gateway → ping external IP → resolve a name → open the app the user actually cares about. Confirm with the user, write it down.

A failed ping is a suspect, not a conviction.

ICMP is often blocked. A successful ping proves the path; a failed one needs a second witness — arp -a, tracert, or a TCP/HTTP test. (Why the companion tool tests TCP + HTTP alongside ICMP.)

Escalation — When, and With What rules for the hand-off · start L3 at your frontier, not from zero

When to escalate — rules, not feelings: the timebox expires without isolation · the fix needs access or authority you don't have · severity says so — big-impact cases go up early, by policy · your layers are excluded and the remaining suspects live in L3's domain.

  • Topology sketch of the affected path (hand-drawn is fine)
  • Blast radius, timeline, and what changed
  • What you excluded, with the evidence that excludes it
  • Raw outputs: ipconfig / ping / tracert, or the NetworkHealthCheck report
  • Relevant switch & AP status pages
  • Device logs (switch / AP / firewall) for the failure window + config exports of the path
  • Reproduction steps; current workaround if any
  • Business impact and severity
