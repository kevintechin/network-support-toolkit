Support Engineer's Field Manual

Running the SOP with NetworkHealthCheck — from the first call to the hand-off
v1.0 · Kevin (Te-Chin) Lin · September 2026 · companion to the Network Troubleshooting SOP v1.2 · written against NetworkHealthCheck 1.2.3
One endpoint, one moment The fingerprint names the station Healthy is a scope, not a verdict

The SOP is the map. NetworkHealthCheck is one instrument, and an unusual one: you can put it in the hands of a person you cannot see, on a machine you cannot touch, and get back evidence you can attach to a ticket. This manual is how that instrument is used inside the map — when it earns its place, how to get it run by whoever answered the phone, how to read what comes back in about a minute, which station the reading sends you to, and what travels with the hand-off.

It is not the tool's user manual and not its technical guide; both ship inside the package and describe the tool. This describes the work.

One sentence to keep throughout: the tool measures one Windows endpoint's view of the network at one moment. That is station 1 of the SOP, plus a probe up the ladder. It never reads a switch, an AP, or the firewall.

1 When the tool earns its place and when it does not

Send it when
  • The report is about one user or one machine and you need station 1's state without standing there.
  • The reporter cannot run commands — one double-click replaces a dictated ipconfig.
  • You will need evidence in the ticket: the reports drop straight into the escalation package, timestamped and machine-identified.
  • You want the ladder corroborated — ICMP, TCP and HTTP in one run is Rule 3's second witness, built in.
Do not send it when
  • The blast radius is already many users, a VLAN, or the site — go to stations 4–8 and read the devices you can reach.
  • You have access to the path: a switch's MAC table and port counters beat an endpoint's opinion of them.
  • Nobody can run it at all — no interactive session of any kind, or no one who can download and extract a file. A headless host or a remote shell is not an exclusion: the console launcher runs there, and the GUI falls back to console by itself.
  • The fault is already isolated — the tool cuts the search space, it does not decorate a conclusion.
Cost: about two minutes of the user's time, plus 40–120 seconds of run time depending on the options.

3 Reading the report in 60 seconds resist reading the rows first

1The verdict

At the top. Four values, below.

2"What to tell IT"

The summary block names the fingerprint — the tool's own reading of the lane. This decides your next station.

3Every highlighted row

FAIL, ERROR and WARN — an Attention Required report has no failed rows at all. Most rows carry a Method and a Manual check line; reproduce a row before disagreeing with it. Not all do — the connectivity group is derived from its members.

4IT diagnostics

Collapsed by default: Wi-Fi radio, routes, gateway ARP, proxy, traceroute, drivers.

VerdictCodeMeaning
Overall HealthyPASSEvery required check that could run, passed
Attention RequiredWARNNothing required failed; warnings or quality issues were raised
Test IncompleteERRORSomething could not be measured — permissions, missing components, an execution error
Problem DetectedFAILAt least one required check failed
IT diagnostics never change the verdict. It is computed from the user-scope rows alone — deliberately: an IT-only observation should never turn a user's report red. They are evidence, not judgement.
If you asked for a target, read its row whatever the verdict says. Everything added through the IT panel or the switches is optional, and what it does to the verdict depends on how it fails: no ping reply at all, or no TCP / HTTP connection → INFO, verdict unmoved, so the run can still be Overall Healthy; a reply that is degraded, or a DNS name that will not resolve → WARN, verdict moved to Attention Required. So the service you were asked about can be completely unreachable in a healthy-looking report — in an INFO row the four moves above would skip — while an added DNS name that fails turns the whole report amber. Measured on a real run: three added targets, all unreachable, all INFO, verdict Attention Required for an unrelated 50 % loss on a configured target.
Exit codes hold for console runs only (-ConsoleOnly, what the console launcher starts): there 0 means the run finished and wrote its reports — whatever the verdict — and anything else means no normal report — usually not no evidence: exit 3 attempts NetworkHealthCheck_ENVIRONMENT_*.txt (the script's folder first, then %TEMP%) and a run that could not write a single format attempts NetworkHealthCheck_FATAL_*.txt. Both are best effort and can come back with nothing — likeliest when the output folder is precisely what is broken — so collect the path only if the process printed one; otherwise the text on screen is all there is (section 6). A GUI run always exits 0: the entry point sets it after the window closes, so an IT window closed before Start was clicked, and a run whose report writing failed, exit 0 too. Never read a GUI exit code as evidence; look for the report.

4 The join from fingerprint to station

The fingerprint is the tool's answer to the front door's third question, computed from the rows rather than guessed. The nine rules are an ordered chain — the first match wins, so a fingerprint tells you as much by what it rules out as by what it names. A healthy report does not clear the network. It clears this endpoint's view, at that moment. Say that in the ticket rather than "the tool says it's fine". What gateway-config does and does not judge. It fails only when no IPv4 gateway is configured on any adapter. A gateway that is present but wrong passes it, and no fingerprint names that case: nothing answers → gateway-unreachable; it answers but nothing beyond it works → gateway-up-internet-dead; it answers and everything else works → mixed if the site configured AllowedDefaultGateways, because the expected-standard row for Default Gateway then fails — without that setting there is no gateway-specific diagnosis at all, and the chain falls through to its default, healthy / "Everything passed", unless something unrelated selects another key. That expected-standard row is the only place the tool judges a gateway's value.

The one thing the report cannot tell you on this lane. It says whether the address came from DHCP or is static, but not which server answered — so for the rogue-DHCP question (SOP station 1) you still need ipconfig /all's DHCP Server line from the user.

5 What each row testifies to by the SOP's three families of state

Tables — the network's memory

adapters, adapterMainThe connected and addressed adapters — status Up and holding an IPv4 or IPv6 address — physical vs virtual, with their addressesNot an inventory of the hardware. Probes — differential tests
RowScopeTestifies toLimit
ping-gateway, ping-targetMainThe ladder's rungs, with loss and latencyICMP may be filtered — which is why the next two rows exist. The status depends on whether the target is required, and the tests are an ordered chain — the first match decides. No reply at all → FAIL when required, INFO when not. Then loss ≥ critical → FAIL / WARN. Then loss ≥ warning → WARN. Then latency ≥ critical → FAIL / WARN. Then latency ≥ warning → WARN. Because loss is tested before latency, a required target with warning-level loss and critical latency is WARN, not FAIL — the chain stops at the first match, it does not pick the worst. Everything added at run time is optional
tcp, httpMainA real connection to a real port, and an HTTP responseRule 3's corroboration — but only between probes naming the same destination. Ping, TCP and HTTP targets are configured separately and the IT panel can add more, so read the row targets first: "ping fails, TCP succeeds" is a filtering finding when both went to the same host, and nothing at all when they did not
connectivity-groupMainWhether a group's targets are reachable at allA group is required only if the config lists it in RequiredConnectivityGroups. A group outside that list still gets a row, and its failure is a WARN, not a FAIL — check which kind you are reading before treating it as authoritative. Derived from its members; it carries no Manual-check line of its own
tracerouteITThe first hops toward the first configured non-AUTO ping target (1.1.1.1 unless the site changed it) — address, status and time, silent hops as *, and whether the destination was reached. It does not trace whatever failed, so compare its target with the failed row firstIt samples the first hops only — three by default (TracerouteHops), which is what the row's name says. Neither outcome gives you a boundary. A trace that reached its destination shows no break at all — its last hop is the destination. One that did not stops at the last hop that answered, which under a three-hop cap is simply the last hop sampled. Locating a boundary takes a trace toward the address that actually failed, run far enough to show where the replies stop, and even then a silent hop wants corroboration — routers commonly drop TTL-expired replies while forwarding normally. The row's Manual-check line carries the same cap (tracert -d -h 3 <target>), so ask for an uncapped tracert -d <the address that failed>
expected-standardMainMeasured values against this organization's configured expectationsOnly as good as the config file. On a site with its own baseline, set NetworkHealthCheck.config.json before believing a WARN
Since 1.2.3 a network error carries a Cause: line in the report's language above the operating system's own message, classified by error code; the tool's own DNS and TCP timeouts appear as [ToolTimeout] — nothing answered and nothing refused within the tool's limit, the shape of a firewall dropping packets or an unreachable host.

The SOP's package asks for eight things. The report fully covers none of them — it contributes to two, and the other six are yours to bring.

The passing rows are the exclusions — say in words what they exclude. Attach whichever of the three formats the run actually wrote — the HTML where it exists (readable by anyone) and the JSON (schema 2, carries the run options and the fingerprint); a run that wrote only TXT and JSON is a supported outcome, not a failed run. Name in the ticket, in this order: the machine, the time of the run, the verdict, the fingerprint, and one sentence on what the run excluded. The support report template beside this manual carries those five facts and the rest of the package in one skeleton — the hand-off and the delivery report are the same document with two fill patterns.

Personal data. The package's own privacy list (the user manual, §5 "Sending the report to IT", What the report contains) is the list to go by: it is longer than the four fields the report's summary names — it runs from the computer and user names through the adapters' MAC and IP data, the Wi-Fi SSID and BSSID, the proxy settings and the first-hop routers to the configuration and report paths — and it is maintained with the tool, so read it there rather than from memory. The package's instruction is unconditional — handle them according to company policy — so apply that policy before a report is stored or shared at all, and let the policy, not this manual, decide whether an internal ticket is treated differently from an external one. And a report is not the only thing you attach: a device configuration export carries credentials — SNMP communities, Wi-Fi PSKs, RADIUS shared secrets, VPN keys, and anything else in the file that would let someone in — and a device log or a screenshot can carry one too; the rule for taking them out is the SOP's, in Collecting the infrastructure evidence, not this manual's.

8 Traps

  • "Healthy" is a scope, not a verdict on the network. It means the endpoint's view was fine during that run.
  • Intermittent faults need a run during the fault. Two runs — one clean, one during — are worth more than either alone.
  • The quality rows measure the machine's own traffic. A download, a backup or a busy remote session during the sample moves the retransmission ratio. Ask what the machine was doing.
  • A machine with no wireless adapter still produces a wifi row — an INFO row saying no connected Wi-Fi interface was found (wired, radio off, or no adapter), with the interface count beneath it. Even a machine without netsh.exe gets a row saying that. In a run that reached the IT diagnostics at all, the absence of any wifi row means one thing: the optional WifiRf check is switched off. A report that stopped before them — an unsupported Windows version, or PowerShell below 5, each of which writes a normal report and returns early — has no wifi row either, so read the environment rows first. Never read a disabled or unreached diagnostic as evidence about the hardware.
  • Thresholds are generic until someone sets them. A WARN against defaults on a high-latency WAN link is a statement about the defaults.
  • A report is about one machine at one moment. Check the computer name and the timestamp before reasoning from it — reports get forwarded, renamed and re-sent.
  • Do not let the tool replace the front door. The four isolation questions cost nothing and cut more search space than any single endpoint reading.
