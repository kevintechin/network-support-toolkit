# tests/ — the NetworkHealthCheck validation chain

Backlog #16: the scripts that validate a NetworkHealthCheck release used to live in a session scratchpad. This folder commits them, so the whole chain — including the real-window run that caught the two 1.2.0 GUI regressions — is reproducible from a fresh checkout. Nothing here ships: the release asset is built from `healthcheck/` only (`build_asset.py` packages the tracked files under that folder and nothing else).

Backlog #17 (2026-09-04) moved the two PowerShell guards here as well: the checks that keep the two 1.2.0 GUI regressions out of the shipped scripts — arithmetic at the top level of a `New-Object` argument list, and a bound parameter overwritten where the write reaches the script scope — are `ast_guards.ps1`, on the PowerShell AST, instead of regular expressions over text inside the packaged validator (which is 62 checks since, down from 66).

## Run the chain

```
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Package -RequireHealthy     # release: + asset round trip, Overall Healthy required
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -SkipGui                     # no interactive desktop
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Steps parse,validator,guards,unit,report,envguard
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Steps parse,validator,guards,unit,report,envguard,gui-headless -Package -SkipGui   # what GitHub Actions runs
```

Steps, in the chain's order: `parse`, `validator`, `guards`, `unit`, `report`, `envguard`, `gui-headless`, `gui`, `acceptance`, `resultset`, and with `-Package` `package`.

Prerequisites: Windows 10 / 11 with Windows PowerShell 5.1 (the tool's own runtime), Python 3 on `PATH` for the release validator and the asset builder (`-Python` to point elsewhere), git (the guard self-test reads the v1.2.0 anchor files from history), and for the `gui` step an interactive desktop session: windows open, get clicked and close by themselves, so leave the desktop alone while they run. Without git or Python the header says so and every other step still runs (backlog #19). `-PackageDir` points the chain at another package — an extracted release asset — instead of the checkout's `healthcheck\`. The default chain takes about ten minutes; the two IT-entry window runs account for most of it because each samples TCP retransmissions for 125 s.

Everything the chain produces goes under `%TEMP%\nhc-tests\<timestamp>\` (`-WorkDir` to choose): staged copies of `healthcheck/<lang>/` with their `Reports/`, one `<step>_<case>.log` per run, and `summary.md` with the table the chain prints. The staged copies are refreshed from the checkout on every invocation, so a reused work dir always runs the current files (reports are selected by start time). The repository is never written to, and the exit code is the number of failed cases.

## On GitHub Actions

`.github/workflows/validation-chain.yml` (backlog #20) runs the deterministic part of the chain on `windows-latest` for every push to `main`, every pull request and on request (`workflow_dispatch`): the last command line above, in Windows PowerShell 5.1 (the tool's own runtime, started from `cmd` exactly as written — not the runner's `pwsh`), on a checkout with full history (`fetch-depth: 0`, because `selftest_guards.ps1` reads the v1.2.0 anchors from commit `f7c45a9`), with Python 3 from `actions/setup-python` for the validator and the asset builder. Those eight steps need neither a desktop nor a particular network, so their result depends on the files alone. `gui`, `acceptance` and `resultset` stay local, and `-SkipGui` drops the window part of `package`: the real-window runs need an interactive desktop, and the console runs assert every row of the report against the machine's own gateways, DNS servers, wireless interfaces and counter classes, which nobody controls on a hosted runner. The chain's exit code is the number of failed cases, so a red run is a failed case; the summary table is on the run's page, and `summary.md`, every `<step>_<case>.log` and the built ZIP are kept as an artifact for 30 days. There is no path filter: a required status check that is skipped for a docs-only commit blocks the merge, and the run costs a few minutes.

A green run means that everything a machine can check unattended still passes on a second, clean Windows machine. It is not the release record: that remains the local `-Package -RequireHealthy` run on the reference machine, pasted into `healthcheck/VALIDATION.md`.

## Package acceptance on another machine (backlog #19)

The chain needs Python and git for three steps only (`validator`, `guards`, `package`), and those run on every commit on GitHub Actions. Everything else is Windows PowerShell 5.1, which a clean Windows 10 / 11 machine already has — so a machine with nothing installed can accept a **released asset** along the path a user takes, with one command:

```
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-PackageAcceptance.ps1 -Zip "%USERPROFILE%\Downloads\NetworkHealthCheck-<version>.zip" -ExpectedSha256 <digest from the release notes> -Label <machine-scenario>
```

`Invoke-PackageAcceptance.ps1` checks the ZIP against the published digest, extracts it, checks the package against its own `SHA256SUMS.txt` and the CRLF rule, writes `environment_probe.ps1`'s description of the machine, runs the chain with `-PackageDir` pointed at the extracted package and `-Steps parse,unit,report,envguard,gui-headless,gui,acceptance,resultset`, then opens the package root's `Start-English.cmd` and `Start-Traditional-Chinese.cmd` through the real window (the launchers `README_BILINGUAL.md` sends people to). Cases the chain did not reach are listed as `NOT RUN`, so a gap is visible rather than silent, and a step dropped on purpose by `-SkipGui` as `SKIPPED`; the exit code is the number of failed and not-run cases. The result is one bundle next to the downloaded ZIP — `nhc-acceptance_<computer>_<label>_<time>.zip` with `acceptance_summary.md`, the chain's summary and logs, every report the runs wrote, the probe and a copy of the checklist — which is what goes into `healthcheck/VALIDATION.md`. `-SkipGui` for a session without a desktop; `-RequireHealthy` on a machine whose network is expected to be healthy; `-PackageDir` instead of `-Zip` for an already extracted package. On a machine restricted to a limited language mode the chain cannot run at all; the wrapper writes the probe, says so and exits 3, like the tool's own guard.

What the wrapper cannot do is in `package-acceptance-checklist.md`: the Windows prompts on a marked-of-the-web download, the run from inside the compressed-folder view, the IT window at a laptop resolution, a standard user's session, the machine put under `__PSLockdownPolicy`, a Group Policy execution policy or AppLocker — each an observation with an expected outcome and an evidence column, made after changing the machine and, where the chain applies, followed by the one command again under a new label. To get `tests\` onto such a machine, Code → Download ZIP of the repository is enough: these scripts do not care about line endings, and nothing else is needed.

**Result set.** Every end-to-end run (window and console) must carry exactly the rows its configuration, its launch and the machine call for. The extra targets the report recorded must first equal the launch exactly (none without switches). Then: one row per configured or extra ping / DNS / TCP / HTTP target, an `AUTO_DNS` ping target counting one row per DNS server of the primary adapters; one `ping-gateway` row per distinct IPv4 default gateway of the machine's connected adapters (what `AUTO_GATEWAY` resolves to; one "no target" row when there is none), each naming one of those gateways; one connectivity-group row per group named on a TCP or HTTP target or listed in `RequiredConnectivityGroups` (a required group without targets gets its own row); one row per IT diagnostic enabled in the configuration and not switched off at launch (`routes`, `proxy`, `traceroute`, `drivers`; `gateway-neighbor` one per resolved gateway and `wifi` one per connected wireless interface, or one each without), with the report's own `ChecksEnabled` required to agree; one `adapter` row per connected adapter with an address and one `adapter-errors` row per adapter row; one `expected-standard` row per rule category in the configuration's `Expected` section (one informational row without rules); one `tcp-retransmissions` row per TCP performance-counter class (TCPv4, TCPv6) readable at both samples, two per class readable at neither (an error row from each sample), one per class readable at one sample only, each protocol named, or with neither class readable at the baseline one `step-error` row for that step and one generic row; without adapter statistics (`Get-NetAdapterStatistics`) two `step-error` rows and one aggregate `adapter-errors` row instead of one per adapter, and when exactly one of the two samples failed on a machine where the cmdlet works, one `step-error` row and the aggregate row (the only `adapter-errors` row the script writes with status ERROR); any other `step-error` row is unexpected; the fixed rows (`config-file`, `config`, `environment`, `system`, `adapters`, `gateway-config`, `dns-config`), each in its scope (`IT` for the diagnostics, `Main` for the rest); and nothing else: an unknown tag, a missing row, or a row count that does not add up fails the case. Extra targets given as switches must have a row naming them. The machine facts (connected adapters with an address, the IPv4 default gateways and DNS servers of the primary adapters, the connected wireless interfaces in `netsh wlan show interfaces`, the readability of the two TCP counter classes, the availability of adapter statistics) are read before the launch and again after the report: the report must match the pre-launch facts, or, when the machine changed during the run, the post-run facts (the case then carries a note). They are read the way the script's own snapshot reads them: `Get-NetIPConfiguration` first, and the fallback (every IP-enabled `Win32_NetworkAdapterConfiguration`, through `Get-CimInstance` when it exists and `Get-WmiObject` otherwise) when that cmdlet is missing, throws or returns nothing; when it throws, the script also writes a `data-source` warning row, which is then expected, and when the fallback throws as well (or no CIM / WMI command exists) the snapshot step's `step-error` row is expected on top of the zero-adapter shape. On a machine without a connected adapter the aggregate `adapters` row fails and the adapter, gateway-config and dns-config rows are absent, which is accepted as that machine's legitimate shape. With the shipped configuration on a machine with three connected adapters and one gateway that is 28 rows, or 30 with one extra ping and one extra TCP target.

`-RequireHealthy` is off by default: on a machine with a real network problem a warning is the tool doing its job, not a failed test. The reference results above were produced on the author's machine (Windows 11, Windows PowerShell 5.1.26100), where the release record in `healthcheck/VALIDATION.md` expects Overall Healthy.

## Notes

- `unit_tests.ps1` and `report_stage_tests.ps1` carry a UTF-8 byte-order mark on purpose: Windows PowerShell 5.1 reads a script without one in the system code page, and these two contain zh-TW text in their assertions. `gui_check.ps1` spells its zh-TW button names as character codes for the same reason and stays ASCII.
- The test scripts load functions out of the language files by AST and `Invoke-Expression`, so the functions under test are the shipped ones; nothing is copied into the tests.
- `parse_check.ps1`, `unit_tests.ps1`, `report_stage_tests.ps1` and `gui_repro.ps1` are the scripts that produced the 1.2.1 record, committed as they ran (`report_stage_tests.ps1` was `report_stage_tests_v121.ps1`). `gui_check.ps1` is the 1.2.1 driver extended in the PR #5 review (launcher-driven, idle check before Start, exit codes propagated). `build_asset.py` differs from its scratchpad version only in resolving paths from the repository root.
- `selftest_guards.ps1` replaced `selftest_guards.py` in backlog #17: same corpus, same anchors, same exit contract, but it drives the AST guards in `ast_guards.ps1` instead of lifting the regular expressions out of the packaged validator by source. Every case recorded before the rewrite kept its classification; the cases added with it are marked in the file. A case is written on one line, where `\n` stands for a line break.
