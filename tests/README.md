# tests/ — the NetworkHealthCheck validation chain

Backlog #16: the scripts that validate a NetworkHealthCheck release used to live in a session scratchpad. This folder commits them, so the whole chain — including the real-window run that caught the two 1.2.0 GUI regressions — is reproducible from a fresh checkout. Nothing here ships: the release asset is built from `healthcheck/` only (`build_asset.py` packages the tracked files under that folder and nothing else).

## Run the chain

```
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Package -RequireHealthy     # release: + asset round trip, Overall Healthy required
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -SkipGui                     # no interactive desktop
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Steps parse,validator,guards,unit,report
```

Steps, in the chain's order: `parse`, `validator`, `guards`, `unit`, `report`, `gui-headless`, `gui`, `acceptance`, `resultset`, and with `-Package` `package`.

Prerequisites: Windows 10 / 11 with Windows PowerShell 5.1 (the tool's own runtime), Python 3 on `PATH` (`-Python` to point elsewhere), git (the guard self-test reads the v1.2.0 anchor files from history), and for the `gui` step an interactive desktop session: windows open, get clicked and close by themselves, so leave the desktop alone while they run. The default chain takes about ten minutes; the two IT-entry window runs account for most of it because each samples TCP retransmissions for 125 s.

Everything the chain produces goes under `%TEMP%\nhc-tests\<timestamp>\` (`-WorkDir` to choose): staged copies of `healthcheck/<lang>/` with their `Reports/`, one `<step>_<case>.log` per run, and `summary.md` with the table the chain prints. The staged copies are refreshed from the checkout on every invocation, so a reused work dir always runs the current files (reports are selected by start time). The repository is never written to, and the exit code is the number of failed cases.

**Result set.** Every end-to-end run (window and console) must carry exactly the rows its configuration, its launch and the machine call for. The extra targets the report recorded must first equal the launch exactly (none without switches). Then: one row per configured or extra ping / DNS / TCP / HTTP target, an `AUTO_DNS` ping target counting one row per DNS server of the primary adapters; one `ping-gateway` row per distinct IPv4 default gateway of the machine's connected adapters (what `AUTO_GATEWAY` resolves to; one "no target" row when there is none), each naming one of those gateways; one connectivity-group row per group named on a TCP or HTTP target or listed in `RequiredConnectivityGroups` (a required group without targets gets its own row); one row per IT diagnostic enabled in the configuration and not switched off at launch (`routes`, `proxy`, `traceroute`, `drivers`; `gateway-neighbor` one per resolved gateway and `wifi` one per connected wireless interface, or one each without), with the report's own `ChecksEnabled` required to agree; one `adapter` row per connected adapter with an address and one `adapter-errors` row per adapter row; one `expected-standard` row per rule category in the configuration's `Expected` section (one informational row without rules); one `tcp-retransmissions` row per readable TCP performance-counter class (TCPv4, TCPv6) and two per unreadable one (an error row from each sample), each protocol named, or with neither readable one `step-error` row for the baseline step and one generic row; without adapter statistics (`Get-NetAdapterStatistics`) two `step-error` rows and one aggregate `adapter-errors` row instead of one per adapter, and when exactly one of the two samples failed on a machine where the cmdlet works, one `step-error` row and the aggregate row (the only `adapter-errors` row the script writes with status ERROR); any other `step-error` row is unexpected; the fixed rows (`config-file`, `config`, `environment`, `system`, `adapters`, `gateway-config`, `dns-config`), each in its scope (`IT` for the diagnostics, `Main` for the rest); and nothing else: an unknown tag, a missing row, or a row count that does not add up fails the case. Extra targets given as switches must have a row naming them. The machine facts (connected adapters with an address, the IPv4 default gateways and DNS servers of the primary adapters, the connected wireless interfaces in `netsh wlan show interfaces`, the readability of the two TCP counter classes, the availability of adapter statistics) are read the way the script's own snapshot reads them: `Get-NetIPConfiguration` first, and the fallback (every IP-enabled `Win32_NetworkAdapterConfiguration`, through `Get-CimInstance` when it exists and `Get-WmiObject` otherwise) when that cmdlet is missing, throws or returns nothing; when it throws, the script also writes a `data-source` warning row, which is then expected, and when the fallback throws as well (or no CIM / WMI command exists) the snapshot step's `step-error` row is expected on top of the zero-adapter shape. On a machine without a connected adapter the aggregate `adapters` row fails and the adapter, gateway-config and dns-config rows are absent, which is accepted as that machine's legitimate shape. With the shipped configuration on a machine with three connected adapters and one gateway that is 28 rows, or 30 with one extra ping and one extra TCP target.

`-RequireHealthy` is off by default: on a machine with a real network problem a warning is the tool doing its job, not a failed test. The reference results above were produced on the author's machine (Windows 11, Windows PowerShell 5.1.26100), where the release record in `healthcheck/VALIDATION.md` expects Overall Healthy.

## The scripts on their own

| Script | What it does | Usage |
|---|---|---|
| `parse_check.ps1` | Parses one script with the Windows PowerShell 5.1 parser and lists the errors. | `-Path <NetworkHealthCheck.ps1>` |
| `unit_tests.ps1` | Loads the helper functions (parsing, conversion, classification, Wi-Fi output parsing) out of the script by AST and checks them against fixed inputs, including Windows 10 / 11 and localized `netsh wlan` samples. | `-ScriptPath <NetworkHealthCheck.ps1>` |
| `report_stage_tests.ps1` | Loads every function of the script, builds the minimal script state, and exercises the report stage: all formats succeed; one format fails; all fail (exactly one emergency report); fingerprint keys from tagged results; run options and profile text; IT-scoped results never change the verdict; adapter counter rows; route ordering; and the IT panel built from real WinForms controls headless, which keeps a configured 30 pings / 300 s instead of clamping them. | `-ScriptPath <NetworkHealthCheck.ps1> -WorkDir <existing folder>` |
| `gui_repro.ps1` | Headless smoke test of `Initialize-Gui`: runs the body of its main `try` block as a script block, so an exception surfaces with its position instead of being swallowed by the function's own `catch` (which silently falls back to console mode). | `-ScriptPath <NetworkHealthCheck.ps1> [-Interactive]` |
| `gui_check.ps1` | Drives the real window through UI Automation the way a person would: runs the shipped launcher for the entry (`-Via Launcher`, the default, or the launcher given as `-LauncherPath`, e.g. the package root's `Start-English.cmd`; `-Via Direct` calls `powershell.exe -File` for debugging), finds the window of the PowerShell process the launcher started (looked up through CIM or WMI, whichever exists, like the script's own queries) and prints the launcher's effective command line; for the user entry verifies that the run starts by itself; for the IT entry lists the panel's edit fields, verifies the window is idle (Start enabled, nothing changing for 3 s, no report), clicks Start with the panel untouched and verifies the click took effect; waits for the JSON report, prints the run options it recorded, closes the window with its Close button, and exits nonzero on any of those failing, on a nonzero exit code of the launched process, or on a `LauncherError.txt`. The folder must be named `en-US` or `zh-TW` (the button names are per language). WinForms controls surface as generic panes through UI Automation, but their names, enabled state and window classes are exact; the JSON report remains the evidence for the values. | `-PackageDir <copy of healthcheck\en-US or zh-TW> -Entry User|IT [-Via Launcher|Direct] [-LauncherPath <cmd>] [-TimeoutSeconds 300]` |
| `selftest_guards.py` | Self-test of the validator's two PowerShell guards (`unparenthesized_arithmetic`, `overwritten_parameters`): the v1.2.0 anchors, the current files, and the synthetic corpus from the PR #4 review rounds. Backlog #17 keeps this corpus as the acceptance set for the AST rewrite of the guards. | `python tests/selftest_guards.py [<v1.2.0 en-US .ps1> <v1.2.0 zh-TW .ps1>]` |
| `build_asset.py` | Builds the release asset by the packaging rule (tracked files under `healthcheck/` only, working-tree bytes, one `NetworkHealthCheck-<version>/` top folder, deflate) and prints its size and SHA256. | `python tests/build_asset.py [<out.zip>]` |
| `selftest_resultset.ps1` | Negative self-check of the runner's result-set assertion (also the `resultset` step). A real report from an earlier run must pass intact against the real machine facts (the positive control); a fixture normalised out of it (three adapter and counter rows, one gateway row naming a TEST-NET gateway, settings rows, one TCPv4 and one TCPv6 row, no data-source or step-error row) must pass against fixed synthetic facts and must be reported when tampered with (a row removed, a rogue tag, an IT row moved to the Main scope, a missing extra-target row, the counter rows removed, an empty set, a diagnostic dropped by the run and by `ChecksEnabled` alike, a gateway row naming another address, the zero-adapter shape on a machine with adapters, two configured standard rules against one row, a required connectivity group without targets, the data-source row missing after a cmdlet failure, three retransmission rows with both counter classes readable, a protocol never named, the neither-class and no-statistics shapes on a machine where both work, a step-error row the facts do not explain, an `AUTO_DNS` target against two DNS servers with one row, two gateways with one neighbour row, the failed-fallback shape with a fallback that worked, two wireless interfaces with one `wifi` row, the aggregate counter row with two step-error rows on a machine where the cmdlet works), while the zero-adapter shape on a machine without a connected adapter, a present data-source row, the TCPv6 error rows with TCPv6 unreadable, the step-error and generic rows with neither TCP class readable, and the step-error and aggregate rows without adapter statistics are accepted. | `-ReportPath <report.json> -ConfigDir <folder>` (or `-ReportDir <Reports folder>` for manual use: the newest user-entry report) |
| `Invoke-ValidationChain.ps1` | Runs the steps above in order on staged copies and prints the summary table. | see above |

## Notes

- `unit_tests.ps1` and `report_stage_tests.ps1` carry a UTF-8 byte-order mark on purpose: Windows PowerShell 5.1 reads a script without one in the system code page, and these two contain zh-TW text in their assertions. `gui_check.ps1` spells its zh-TW button names as character codes for the same reason and stays ASCII.
- The test scripts load functions out of the language files by AST and `Invoke-Expression`, so the functions under test are the shipped ones; nothing is copied into the tests.
- `parse_check.ps1`, `unit_tests.ps1`, `report_stage_tests.ps1` and `gui_repro.ps1` are the scripts that produced the 1.2.1 record, committed as they ran (`report_stage_tests.ps1` was `report_stage_tests_v121.ps1`). `gui_check.ps1` is the 1.2.1 driver extended in the PR #5 review (launcher-driven, idle check before Start, exit codes propagated). `selftest_guards.py` and `build_asset.py` differ from their scratchpad versions only in resolving paths from the repository root and reading the v1.2.0 anchors from git.
