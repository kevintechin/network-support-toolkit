# tests/ — the NetworkHealthCheck validation chain

Backlog #16: the scripts that validate a NetworkHealthCheck release used to live in a session scratchpad. This folder commits them, so the whole chain — including the real-window run that caught the two 1.2.0 GUI regressions — is reproducible from a fresh checkout. Nothing here ships: the release asset is built from `healthcheck/` only (`build_asset.py` packages the tracked files under that folder and nothing else).

Backlog #17 (2026-09-04) moved the two PowerShell guards here as well: the checks that keep the two 1.2.0 GUI regressions out of the shipped scripts — arithmetic at the top level of a `New-Object` argument list, and a bound parameter overwritten where the write reaches the script scope — are `ast_guards.ps1`, on the PowerShell AST, instead of regular expressions over text inside the packaged validator (62 checks from then to 1.2.3, down from 66; the document version checks joined in 1.2.4).

## Run the chain

```
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Package -RequireHealthy     # release: + asset round trip, Overall Healthy required
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -SkipGui                     # no interactive desktop
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Steps parse,validator,guards,docfacts,unit,report,envguard
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-ValidationChain.ps1 -Steps parse,validator,guards,docfacts,unit,report,envguard,launcher,campaign,gui-headless -Package -SkipGui   # what GitHub Actions runs
```

Steps, in the chain's order: `parse`, `validator`, `guards`, `docfacts`, `unit`, `report`, `envguard`, `launcher`, `campaign`, `gui-headless`, `gui`, `acceptance`, `resultset`, and with `-Package` `package`.

`docfacts` (backlog #33, tier 1) is the one step that reads the documents rather than the program: `doc_facts.ps1` takes the identifiers out of the two scripts and the two shipped configuration files — result tags **read off the AST, so that a tag reached through a variable counts** (`-Tag $pingTag` is `ping-target`, or `ping-gateway` for `AUTO_GATEWAY`) and only when *every* assignment to that variable is a literal, fingerprint keys and their titles, configuration keys including the ones inside a target list, exit codes read the same way (the entry points end on `exit $exitCode`, so the literals behind that variable are compared, the literals a called function returns are followed into it, and the shape of what is still not a literal is compared as well) — and asserts both directions against the manuals, the six guide copies and `sop/support-engineer-field-manual.*`. The two languages must define the same identifiers; every configuration key must be quoted in the IT deployment manual and every key in one of its examples must exist; every fingerprint key must be named in each guide copy and in the field manual; every result tag must be documented in **both** field-manual formats except the six named as internal in the step itself, so a new tag forces a decision; every launcher or program file name a document quotes must be in the package, whether it is quoted bare, with its folder, relative to the document itself (`../VALIDATION.md`), inside a command line the reader is meant to run, or inside a fenced block they copy whole; every local link has to resolve from the folder its document sits in and nowhere else, which is where a browser looks; every exit code a document quotes has to be one **its own producer** actually produces — the validator's paragraph is measured against the validator's codes and a sentence that says the launcher *exits* N against the launchers', not against everything the package can return; and every section number a document cites must exist in it — in the markdown **and** on the HTML page, written as `section N`, with the Chinese marker or with `§`, and every number of a compound reference. It reads identifiers only, as code spans — never prose, because `config` and `healthy` are ordinary words — so what it cannot check is what the review loop is for: a sentence that states a rule from one side only. `selftest_docfacts.ps1` is its negative self-test: a copy of the package, `sop/` and `docs/`, forty mutations, each of which must fail its own check by name, with the untouched copy passing before and after. `-PackageOnly` drops the `sop/` documents, which is what a run against an extracted release asset wants; the chain passes it by itself when `-PackageDir` points somewhere other than the checkout.

Prerequisites: Windows 10 / 11 with Windows PowerShell 5.1 (the tool's own runtime), Python 3 on `PATH` for the release validator and the asset builder (`-Python` to point elsewhere), git (the guard self-test reads the v1.2.0 anchor files from history), and for the `gui` step an interactive desktop session: windows open, get clicked and close by themselves, so leave the desktop alone while they run. Without git or Python the header says so and every other step still runs (backlog #19). `-PackageDir` points the chain at another package — an extracted release asset — instead of the checkout's `healthcheck\`. The default chain takes about ten minutes; the two IT-entry window runs account for most of it because each samples TCP retransmissions for 125 s.

Everything the chain produces goes under `%TEMP%\nhc-tests\<timestamp>\` (`-WorkDir` to choose): staged copies of `healthcheck/<lang>/` with their `Reports/`, one `<step>_<case>.log` per run, and `summary.md` with the table the chain prints. The staged copies are refreshed from the checkout on every invocation, so a reused work dir always runs the current files (reports are selected by start time). The repository is never written to, and the exit code is the number of failed cases.

## On GitHub Actions

`.github/workflows/validation-chain.yml` (backlog #20) runs the deterministic part of the chain on `windows-latest` for every push to `main`, every pull request and on request (`workflow_dispatch`): the last command line above, in Windows PowerShell 5.1 (the tool's own runtime, started from `cmd` exactly as written — not the runner's `pwsh`), on a checkout with full history (`fetch-depth: 0`, because `selftest_guards.ps1` reads the v1.2.0 anchors from commit `f7c45a9`), with Python 3 from `actions/setup-python` for the validator and the asset builder. Those nine steps need neither a desktop nor a particular network, so their result depends on the files alone. `gui`, `acceptance` and `resultset` stay local, and `-SkipGui` drops the window part of `package`: the real-window runs need an interactive desktop, and the console runs assert every row of the report against the machine's own gateways, DNS servers, wireless interfaces and counter classes, which nobody controls on a hosted runner. The chain's exit code is the number of failed cases, so a red run is a failed case; the summary table is on the run's page, and `summary.md`, every `<step>_<case>.log` and the built ZIP are kept as an artifact for 30 days. There is no path filter: a required status check that is skipped for a docs-only commit blocks the merge, and the run costs a few minutes.

A green run means that everything a machine can check unattended still passes on a second, clean Windows machine. It is not the release record: that remains the local `-Package -RequireHealthy` run on the reference machine, pasted into `healthcheck/VALIDATION.md`.

## Package acceptance on another machine (backlog #19)

The chain needs Python and git for three steps only (`validator`, `guards`, `package`), and those run on every commit on GitHub Actions. Everything else is Windows PowerShell 5.1, which a clean Windows 10 / 11 machine already has — so a machine with nothing installed can accept a **released asset** along the path a user takes, with one command:

```
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-PackageAcceptance.ps1 -Zip "%USERPROFILE%\Downloads\NetworkHealthCheck-<version>.zip" -ExpectedSha256 <digest from the release notes> -Label <machine-scenario>
```

`Invoke-PackageAcceptance.ps1` checks the ZIP against the published digest, extracts it, checks the package against its own `SHA256SUMS.txt` and the CRLF rule, writes `environment_probe.ps1`'s description of the machine, runs the chain with `-PackageDir` pointed at the extracted package and `-Steps parse,unit,report,envguard,launcher,gui-headless,gui,acceptance,resultset`, then opens the package root's `Start-English.cmd` and `Start-Traditional-Chinese.cmd` through the real window (the launchers `README_BILINGUAL.md` sends people to). Cases the chain did not reach are listed as `NOT RUN`, so a gap is visible rather than silent, and a step dropped on purpose by `-SkipGui` as `SKIPPED`; the exit code is the number of failed and not-run cases, and a bundle that cannot be written counts as a failed case, because the bundle is the evidence. The result is one bundle next to the downloaded ZIP — `nhc-acceptance_<computer>_<label>_<time>.zip` with `acceptance_summary.md`, the chain's summary and logs, every report the runs wrote, the probe and a copy of the checklist — which is what goes into `healthcheck/VALIDATION.md`. `-SkipGui` for a session without a desktop; `-RequireHealthy` on a machine whose network is expected to be healthy; `-PackageDir` instead of `-Zip` for an already extracted package. On a machine restricted to a limited language mode the chain cannot run at all; the wrapper writes the probe, says so and exits 3, like the tool's own guard.

What the wrapper cannot do is in `package-acceptance-checklist.md`: the Windows prompts on a marked-of-the-web download, the run from inside the compressed-folder view, the IT window at a laptop resolution, a standard user's session, the machine put under `__PSLockdownPolicy`, a Group Policy execution policy or AppLocker — each an observation with an expected outcome and an evidence column, made after changing the machine and, where the chain applies, followed by the one command again under a new label. To get `tests\` onto such a machine, Code → Download ZIP of the repository is enough: these scripts do not care about line endings, and nothing else is needed.

`user-manual-walk-checklist.md` is the other walk, and it reads the other way round: the end-user manual ships inside the package, so its sentences are claims a person can check by doing what they say. A row per claim over the manual's nine sections — the launcher messages of section 2, the window and its buttons in section 3, the verdict and the badges and the counters in section 4, the report files in section 5, an injected failure in section 6, the IT panel in section 7, the file table both ways in section 8, the shipped targets in section 9 — each with the manual's own words in its Expected column, plus a closing set of questions about whether the reader could actually follow it, which no assertion measures. It is walked on the released asset, downloaded with the browser of the machine under test so that the Mark of the Web is real; `Invoke-PackageAcceptance.ps1` above proves the package first, and the walk then follows the manual's own extraction instructions on a second, clean copy.

### The guided campaign (backlog #24)

`Invoke-AcceptanceCampaign.ps1` walks that checklist for one machine, so that the person at the desktop is told what to do and nothing is forgotten:

```
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Invoke-AcceptanceCampaign.ps1 -Zip "%USERPROFILE%\Downloads\NetworkHealthCheck-<version>.zip" -ExpectedSha256 <digest> -Campaign <machine>
```

The scenarios run in the plan's order — `A1` the baseline (the acceptance runner as above), `M4` the IT window at 1366 × 768, `M1` the run from inside the compressed-folder view, `M2` the extraction without Unblock, `M3` Unblock and both root launchers, `A3` host-only, `A4` the adapter disconnected, `M7` `__PSLockdownPolicy`, `M8` a Group Policy execution policy of AllSigned, `M9` AppLocker, `A2` the runner as a standard user. An automated scenario just runs. One that needs the machine changed prints the instruction (English and zh-TW), waits for `done`, and **checks the machine before anything runs** — the screen really is 1366 × 768, there really is no gateway, the machine environment really carries `__PSLockdownPolicy=4`, `MachinePolicy` really is `AllSigned` — and asks again, or lets the person skip, when it is not. One that needs a person's click (a double-click on the downloaded ZIP, an Unblock) never performs the click: it collects what the click left behind — the reports a compressed-folder view is about to delete, copied out before the view closes; a screenshot the moment a Windows prompt appears; the Mark of the Web on the download and on the extracted launcher; the reports under the extraction folders — and records the person's answers. Under `__PSLockdownPolicy`, AllSigned and AppLocker it starts the shipped console launcher the way a double-click does and asserts what a user would see: the exit code, `LauncherError_<stamp>.txt`, an environment report or its absence, no report — and for AllSigned the signature refusal itself in the captured output (`UnauthorizedAccess` / `SecurityError`), with no environment report, since one would mean the script started — which is the evidence backlog #23 was decided on — closed by #28 in 1.2.3, the launcher naming a suggested action per reason; what a refusal of the launcher itself leaves is backlog #37. A scenario that changes the machine ends with the instruction to put it back, verified before the next one starts — and its result is final only then: until the revert is verified it stays `PENDING` and counts, and a campaign stopped or killed at that prompt resumes at the revert rather than running the scenario again; a skip after the person has answered `done` once goes through the same revert check, because the change may already be on the machine — and that attempt is recorded, so a quit or a crash in between does not forget it. The AppLocker scenario records the Application Identity service's startup type and state before the change and asks for them back, its revert check requires the Script rules deleted, not merely unenforced, and its precondition asks AppLocker itself (`Test-AppLockerPolicy`) whether the rules restrict the account under test — the default rules exempt administrators, and an exempt account would run the script normally and record a failure that measures nothing. The compressed-folder scenario takes a screenshot of the window running from inside the view before it collects the reports and passes only on the compressed-folder warning itself (in either language), not on any startup notice; the extraction-without-Unblock scenario checks, before anyone is asked to act, that the download still carries the Mark of the Web of the Internet or Restricted zone (`ZoneId=3` or `4` — a stream without one, or a local zone, is not the mark whose warning it measures), and is skipped with the reason otherwise; `-SkipGui` drops the four desktop scenarios (M1–M4) as well as the real windows, since a person's clicks and the screenshots need a desktop; the Unblock scenario takes one of the zh-TW window after its run and one of the browser showing the report. The policy scenarios cut the branch the campaign sits on — under `__PSLockdownPolicy` every new PowerShell is ConstrainedLanguage and the driver cannot resume, under AllSigned the unsigned driver does not start — so before any of them is applied the driver has written `RECOVER.txt` (the way back without PowerShell: `reg delete`, gpedit, secpol, and the resume command) and `undo-M7.cmd` into the state folder, names them in the instruction, and a driver started in ConstrainedLanguage stops at the door with exit code 3 pointing at them instead of failing on its first `New-Object`. The display scenario records the size it found (once — a resume keeps that record) and asks for that size back; host-only ends with the adapter back on NAT, verified. A manual observation certifies an item only with an explicit yes and an evidence file: the layout at 1366 × 768 has its screenshot and passes only on `yes`; Open Report is a screenshot of the browser showing the HTML report, taken when the person says it is on screen.

Every result goes to `campaign.json` the moment it is known — written to a temporary file and swapped in atomically, the previous version kept as `campaign.json.bak` — so a logoff or a reboot costs nothing: run the same command again and the campaign continues (`-Resume` is implied). A scenario left with its change possibly on the machine is handled first in every invocation, whatever `-Scenarios` says; in a standard-user session such a revert cannot be made, so nothing runs there until the administrator has resumed. The standard-user scenario is left `PENDING` with the exact command to run in that session; the state, the asset, the extracted package and a copy of `tests\` live under `C:\Users\Public\NetworkHealthCheck-acceptance\<campaign>`, which every account can reach. Every invocation ends by writing `nhc-campaign_<computer>_<campaign>_<time>.zip` — `campaign_summary.md`, `campaign.json`, `answers.log` and one folder per scenario with its evidence; the summary names it, earlier bundles of the campaign are removed, and when the bundle cannot be written the summary says `NOT WRITTEN` so that an older one cannot pass for it — and the exit code is the number of failed scenarios plus the scenarios this invocation selected and could not finish (quit, not reached, left for another session); a skip by the person, a precondition the machine did not meet, or `-SkipGui`, is `SKIPPED` and not counted. `-Answers <file>` replays a campaign without a person (`<Id>=done|skip|quit`, `<Id>/<question>=text`), which is how `selftest_campaign.ps1` drives the state machine in the chain's `campaign` step; `-Scenarios A3,A4` runs a subset. Answers are matched case-insensitively against their choices; at the console a value outside them is asked again, and in an answers file it leaves the scenario `PENDING` with the value named — a typo is never a skip. `gui_check.ps1 -Screenshot <png>` is what the driver uses for the layout scenario. The display size — `M4`'s precondition, the size it records to put back, the revert check, the driver's own screenshots — is measured live through `SystemInformation.PrimaryMonitorSize` (a `GetSystemMetrics` call on every access): `Screen.PrimaryScreen.Bounds`, used at first, is built once by Windows Forms and kept until a display-change message reaches its window, which never happens while the driver waits for an answer — the first campaign on a VM saw the size from before its `done` three times (2026-09-05). `M1` accepts the two outcomes that are the package behaving as designed: on stock Windows, Explorer extracts only the file clicked into the view folder (`Temp1_*.zip` on Windows 10, `<guid>_*.zip.<n>` on Windows 11), so the launcher stops with its own message and `LauncherError_<stamp>.txt`, which the driver copies out together with a listing of what the view held the moment the person answers - Windows 11 may delete that folder as soon as the program started from it exits, and its name ends in a few hex digits (`.684`, `.bc4`), not a number - and there is no report; where the whole folder was extracted, the report must carry the compressed-folder warning row. A launcher stopped for any other reason, or nothing in any view folder, fails. `-Redo M4,M1` runs scenarios with a result on record again: the record is cleared, the earlier evidence moved to `superseded\<id>_<time>` in the state folder (bundled) and the summary names what was superseded; a scenario pending with a change possibly still on the machine is refused until its revert is verified. The extraction scenarios go in two steps: `M2` and `M3` first ask for the Unblock (or not) and the extraction into the folder they name, and check that the launcher is really below it before anyone double-clicks anything — the Extract All dialog proposes another folder, and the first campaign's run left its reports where the scenario did not look; when a report is still missing, the failure names any report the run left elsewhere. `-WorkRoot <folder>` moves those folders off the Desktop (a local folder keeps OneDrive out of it; the self-test uses it). The summary names the edition (Home / Pro / Enterprise, with `gpedit.msc` and `secpol.msc` present or not): `M8` shows both ways to the same MachinePolicy — gpedit, or the two `reg add` lines where there is none — and says which one this machine takes, recording it in its facts and in `RECOVER.txt`; `M9` is skipped before anyone is asked on Windows Home, where AppLocker does not exist. The command for the standard-user session is also written to `run-as-standard-user.cmd` next to the state, so that nobody types it by hand. The extraction accepted is this scenario's and this campaign's only: the folder written after the scenario started (a tree left by an earlier campaign is refused - for `M2` its marks would be another download's; the folder, because Windows 11's extraction gives the files the archive's own timestamps) and a program file byte-identical to the asset's; the work root is recorded in the state and reused by every resume; `M8` records the MachinePolicy and the two registry values before the change, its revert says how to put them back as they were and is verified against that, not against a blank.

## Notes

- `unit_tests.ps1`, `report_stage_tests.ps1` and `Invoke-AcceptanceCampaign.ps1` carry a UTF-8 byte-order mark on purpose: Windows PowerShell 5.1 reads a script without one in the system code page, and these contain zh-TW text — assertions in the first two, the prompts a person reads in the third (without the mark, the parser reported 78 errors in it). `gui_check.ps1` spells its zh-TW button names as character codes for the same reason and stays ASCII.
- The test scripts load functions out of the language files by AST and `Invoke-Expression`, so the functions under test are the shipped ones; nothing is copied into the tests.
- `parse_check.ps1`, `unit_tests.ps1`, `report_stage_tests.ps1` and `gui_repro.ps1` are the scripts that produced the 1.2.1 record, committed as they ran (`report_stage_tests.ps1` was `report_stage_tests_v121.ps1`). `gui_check.ps1` is the 1.2.1 driver extended in the PR #5 review (launcher-driven, idle check before Start, exit codes propagated). `build_asset.py` differs from its scratchpad version only in resolving paths from the repository root.
- `selftest_guards.ps1` replaced `selftest_guards.py` in backlog #17: same corpus, same anchors, same exit contract, but it drives the AST guards in `ast_guards.ps1` instead of lifting the regular expressions out of the packaged validator by source. Every case recorded before the rewrite kept its classification; the cases added with it are marked in the file. A case is written on one line, where `\n` stands for a line break.
