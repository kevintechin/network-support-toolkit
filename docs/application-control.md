# NetworkHealthCheck under PowerShell policy and application control — what has been measured

This page is kept in the repository rather than in the package on purpose: what Windows does with an unsigned PowerShell script under policy depends on the build, the edition and the servicing state of the machine, and the answer has changed under this project's feet with the tool itself untouched. The IT deployment manual inside the package links here by the tag of its release; the current version of this page is on the `main` branch. The measurements are in `healthcheck/VALIDATION.md` (the two *Acceptance on a second machine* entries) and what is still open of them is on the [backlog page](backlog.md) beside this one (#22 and #31); the scenarios are specified in `tests/package-acceptance-checklist.md` and driven by `tests/Invoke-AcceptanceCampaign.ps1`.

## What the tool does, mechanism by mechanism

The launchers start Windows PowerShell with `-ExecutionPolicy Bypass`, which sets the execution policy for that process alone. Everything below is about what overrides or precedes that.

| Mechanism | What the tool does | Measured | Where |
|---|---|---|---|
| **Mark of the Web** on a downloaded ZIP (`Zone.Identifier`, `ZoneId=3`) | Nothing special: Windows shows *Open File - Security Warning* on the launcher, and after *Run* the tool runs and writes its report. Unblocking the ZIP before extraction leaves the extracted files unmarked | Yes, on both machines — on the Windows 11 machine with a real browser download, on the Windows 10 machine with a mark written by hand and treated by Windows exactly as a downloaded one (the record says so) | Scenarios M2 and M3 |
| **Execution policy set by Group Policy** — `MachinePolicy` or `UserPolicy` of *AllSigned* | The process-scope Bypass is overridden: the script does not start. PowerShell prints its own refusal (*…is not digitally signed. You cannot run this script on the current system…*, category `UnauthorizedAccess`), the launcher keeps that refusal in `PowerShellMessages_<stamp>.txt`, prints it back, reports the non-zero exit code, pauses and writes `LauncherError_<stamp>.txt` with the suggestion to send both files and ask IT to allow `NetworkHealthCheck.ps1` (since 1.2.14; until then the person was asked to read the message off the screen). No environment report can exist, because the script's guard never ran | Yes, on both machines — through the registry values on Windows 11 Home (no Group Policy editor there), through `gpedit.msc` on Windows 10 Pro | Scenario M8 |
| **A restricted PowerShell language mode** — `ConstrainedLanguage`, which `__PSLockdownPolicy=4` imposes on every new PowerShell and which an enforced WDAC policy imposes on scripts it does not allow | The guard ahead of every other line of the script (backlog #18, since 1.2.2) detects any mode other than `FullLanguage`, prints the reason, writes `NetworkHealthCheck_ENVIRONMENT_<time>.txt` beside the script (or in `%TEMP%`) with the mode, the tool version, the machine, the user, the script folder, the PowerShell version, the culture, the operating system and what IT can do, and exits with code 3. No check runs and no report is written. The launcher explains exit code 3 and points at the file | Yes, with `__PSLockdownPolicy` on both machines: exactly one environment report naming `ConstrainedLanguage`, no report, launcher exit 1. The chain's `envguard` step simulates the same mode on every run. **No machine with an enforced WDAC policy has been measured** | Scenario M7; `tests/env_guard_check.ps1` |
| **AppLocker script rules** enforced against the script | Unknown in practice — see below | **No.** The only machine that reported an enforcing policy ran the script unrestricted | Scenario M9; backlog #31 |
| **EDR / antivirus** blocking `powershell.exe` or the script | The launcher reports whatever exit code it gets and writes `LauncherError_<stamp>.txt`, unless the launcher itself is what was blocked, in which case nothing of the package runs and nothing is written | **No.** No machine with such a product was part of the acceptance runs | Backlog #37 |

## AppLocker: the facts as they stand

- **Which editions enforce a policy, and which can author one — two different requirements.** Microsoft's *Requirements to use AppLocker* (page dated 2024-09-11) states that as of [KB 5024351](https://support.microsoft.com/help/5024351), Windows 10 version 2004 (build 19041) and newer and all Windows 11 versions no longer require a specific edition of Windows to *enforce* AppLocker policies; its table says policies are supported on all editions there, and that on older builds policies deployed through Group Policy are supported on Enterprise and Server editions only while policies deployed through MDM are supported on all editions. Authoring is the other requirement — "a device running a supported operating system to create the rules" — and Windows Home ships neither the Local Group Policy Editor nor the Local Security Policy console (`gpedit.msc`, `secpol.msc`, both absent on the Windows 11 Home machine below), which is where the campaign's M9 creates and enforces its rules. So M9 as specified cannot run on Home and the driver skips it there ("AppLocker is not available on this edition"); that is a statement about authoring a policy locally, not about enforcing one — whether a Home machine enforces a policy delivered by MDM has not been measured by this project. This project first recorded the opposite of the KB's rule — that Pro configures AppLocker without enforcing it — and the Codex review of PR #16 overturned it on 2026-09-06; the driver's M9 prerequisite applies the build rule, and below the build floor admits Education with Enterprise and Server because Microsoft's licensing page lists AppLocker for Education at Enterprise's level, although the requirements page's own sentence names Enterprise and Server.
- **What has been observed.** On a Windows 10 Pro 22H2 virtual machine (build 19045.3803) with Script rules *Enabled*, the default rule for `BUILTIN\Administrators` deleted so that the account under test was not exempt, the Application Identity service running, `gpupdate /force` run, and `Test-AppLockerPolicy` answering `DeniedByDefault` for that account on the exact file — the launcher ran the script to completion in `FullLanguage`, exit 0, one report written, no environment report. The tool did the right thing for what it met: nothing restricted it, so it ran. Why the policy did not act is not settled: whether the servicing update is present on that image, whether a locally authored policy (`secpol.msc`, no GPO, no MDM) is deployed the way the KB covers, whether enforcement needs a reboot rather than a service start, and whether the AppID driver was filtering at all, are the open questions of backlog #31.
- **What has been observed since.** On the same virtual machine at build 19045.6456, on 2026-09-15, enforcement took effect: the script was refused and `M9` **passed**. The policy shape was the same — AppLocker's default script rules without the one for `BUILTIN\Administrators`, Script rules *Enabled*, the Application Identity service running, `gpupdate /force` run, `Test-AppLockerPolicy` answering `DeniedByDefault` for the account on the exact file — but it was applied by `Set-AppLockerPolicy -XmlPolicy` from `tests/applocker-m9.xml` rather than typed into `secpol.msc`. What was refused is not the `.ps1`: AppLocker's script rules cover `.cmd` as well, and the policy allows scripts under `%WINDIR%` and `%PROGRAMFILES%` alone while the package under test sits under `C:\Users\Public`, so `Start-NetworkCheck-Console.cmd` never started. cmd printed *This program is blocked by group policy. For more information, contact your system administrator.* and exited 1, and nothing of the tool's was written — no `LauncherError_<stamp>.txt`, no `PowerShellMessages_<stamp>.txt`, no environment report, no report. **Two things differ from the run above and this run separates neither**: the build (19045.3803 to 19045.6456, the servicing level [KB 5024351](https://support.microsoft.com/help/5024351) is about) and how the policy was deployed. What the project has that it did not have before is a recipe that reproduces the state, both halves of it in the repository. Backlog #31 is closed on this measurement; what the package should carry for a person who meets it is #37, still open. The evidence is the entry *The first campaigns to reach a machine* of 2026-09-15 in `healthcheck/VALIDATION.md`.
- **What that means for the manual's claims.** An enforced rule has three outcomes, and the third is the one nothing here had seen until 2026-09-15. It may refuse the script outright — then the person sees PowerShell's message through the launcher's pause, as under M8 — or run it in `ConstrainedLanguage`, where the guard writes its environment report, as under M7; the launcher's `LauncherError_<stamp>.txt` fits both of those, and the IT deployment manual says so and claims nothing more. Or it may refuse the launcher itself, and then nothing of ours runs: no error report can be written, because the file that would write it never started, and what the person has is the line Windows printed. That is backlog #37, whose measurement half the run above met and whose decision half — what the package carries for that person — is open.

## Allowing the tool under policy

- The two scripts are unsigned (backlog #22). A rule by publisher has nothing to match; a rule by hash does: `SHA256SUMS.txt` in the package carries the digest of each `NetworkHealthCheck.ps1`, and every release changes it.
- A rule by hash answers application control and nothing else. An *AllSigned* execution policy asks the separate question of the table's *Execution policy set by Group Policy* row above — whether the script carries a signature from a publisher the machine trusts — so allowing the hash leaves that row exactly as it is, and the two are separate gates. That is what the documentation says rather than what this project has measured: *about_Execution_Policies* (the Windows PowerShell 5.1 page, dated 2026-08-31) defines *AllSigned* that way and gives the Group Policy setting precedence over the execution policies set in PowerShell in all scopes, *How App Control for Business works with PowerShell* (dated 2026-08-17) has application control deciding how a file is handled and, in Windows PowerShell 5.1, running a file the policy enforces against in `ConstrainedLanguage`, and until 2026-09-15 no machine here had had AppLocker enforce anything at all; the machine that then did refused the launcher before PowerShell started, so the interaction of the two gates has still not been measured here. The one interaction the documentation does describe runs the other way: *Use App Control to secure PowerShell* (dated 2026-08-17) records that from PowerShell 7.2 AppLocker rules take precedence over a `Set-ExecutionPolicy -ExecutionPolicy Bypass` command — a runtime the launchers do not start, and the page says nothing about what Windows PowerShell 5.1 does with that corner case. Section 8 of the in-package IT deployment manual carries the one-sentence form of it, because that is where an IT department meets it (backlog #22's Status of 2026-09-14).
- Signing with an internal certificate authority satisfies *AllSigned* only when the signing certificate is also trusted on the machine — its chain, and the certificate in the Trusted Publishers store; PowerShell prompts before running a script from a publisher not yet classified as trusted (about_Execution_Policies) — and it allows rules by publisher; it appends a signature block to the script, so the signed file no longer matches the package manifest.
