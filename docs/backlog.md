# NetworkHealthCheck backlog — what is known and not yet done

This page is the project's working list: the items that are open, what would close each of them, and the numbers of the ones already closed. It was the last section of `healthcheck/VALIDATION.md` until 2026-09-08, under a heading that still said *backlog for v1.1.1*, grouped by the review that raised each item rather than by number and with the closed ones struck through in place — so the question "what is still open?" was answered by reading a thousand-line record to its end and looking for the lines without strike-through. The record keeps what it is for: what was run, on which machine, what it measured and what shipped. This page keeps what is left.

It is in the repository and not in the package, like [`application-control.md`](application-control.md) beside it, because it changes between releases while a shipped document may not; it carries no version of its own, and the in-package IT deployment manual links to it by the tag of its release.

## How to read an item

- **The number is permanent.** Items are numbered in the order they were raised and are never renumbered or reused; a closed item keeps its number. Every `backlog #N` in the validation record, the manuals, the technical guides, `docs/` and `tests/` means the number on this page. The order below is numeric, which is *not* the order the items were raised in — the review or the run that produced each one is named in its own origin note instead, which is what the old grouping carried.
- **Acceptance.** Most items end with a sentence naming what would have to be true for the item to be closed. An item without one is a decision that has not been taken, not a task waiting for a machine.
- **Kind** says where the work would land: **tool** — the two shipped scripts or the six launchers, so a release; **tests** — the validation chain, its self-tests or the campaign driver, which ship nothing; **build** — the asset builder; **measurement** — a machine this project has not had; **decision** — a cost or a policy, where the missing thing is a choice rather than a change.
- **The item text is the statement**, moved here word for word from the record. It was written beside the entry of the run that raised it, so where it says "this machine" or "the entry above" the origin note says which machine and which entry. Where an item has moved on since it was written without being closed, the change is a **Status** line dated at its end, so that the original wording stays readable beside it.

### 21 — The asset build is not reproducible byte for byte

The asset build is not reproducible byte for byte: `build_asset.py` stamps every ZIP entry with the build time (`zipfile.writestr` with a name takes the current local time), so the same tracked files give a different SHA256 on every build — 223 590 bytes both on the reference machine and on the runner, digests `38056e15…` and `c7d52700…`. With the entries stamped from the commit date instead and the deflate settings unchanged, the digest would identify the content: the asset CI built for the tagged commit could be compared byte for byte with the one released, and anyone could verify the release notes' digest from the tag. Acceptance: two builds of the same commit on the reference machine yield one SHA256, the runner's build of that commit yields the same one (or the difference is explained by the runner's zlib and recorded), and the validator inside the extracted ZIP still passes. — *raised by the first run on GitHub Actions, 2026-09-05.*

**Status, 2026-09-10 — the build clock is isolated from the runner's zlib, and `windows-latest` turns out not to be one machine.** Four CI builds inside eighty minutes, of a package whose content did not change: run-299 on `531b9b2`, run-300 on `4d50150`, run-301 on `af5824b` and run-302 on `4349481`, the three later commits being PR #42's, which touch `docs/backlog.md` and `README.md` and nothing under `healthcheck/` (`git diff 531b9b2..4349481 -- healthcheck/` is empty). All four produced **484 148 bytes** and four different digests: `b4fdc1d4…`, `3df7eb87…`, `afbf10a9…`, `6cf41401…`. **Two pairs of them need no inference at all.** `windows-latest` served two runner image versions inside that hour — `20260907.229.1` for run-299 and run-302, `20260824.214.3` for run-300 and run-301 — so each version built the same content twice, with the same interpreter (`actions/setup-python@v5` resolved the workflow's `3.x` to CPython 3.14.7 in all four runs), and gave a different digest each time. The parenthesis in the acceptance sentence above — *or the difference is explained by the runner's zlib* — accounts for neither pair, and what is left is the entry timestamps this item names. **The second fact is about that parenthesis itself:** the runner is not one machine, so a difference explained away rather than removed has to name the image version as well as the zlib. Nothing else about this item changes, the fix it asks for included. — *measured by PR #42's CI runs, which were built for something else; the fourth is the run of the commit that recorded the first three.*

### 22 — The two shipped scripts are not signed

The two shipped scripts are not signed. The launchers pass `-ExecutionPolicy Bypass` at process scope, and a Group Policy execution policy (`MachinePolicy` / `UserPolicy`) overrides that scope: under `AllSigned` the script does not start, and what the user sees is PowerShell's own "not digitally signed" message through the launcher's pause — the language-mode guard of #18 is inside the script and cannot reach that case (checklist item M8 measures it). An Authenticode signature would satisfy `AllSigned`, let WDAC / AppLocker allow the tool by publisher instead of by a hash per version (`SHA256SUMS.txt` is what an IT department has today), and give SmartScreen something to build a reputation on. An enterprise deployment can sign with an internal CA certificate; general distribution needs a public code-signing certificate, which is a cost and a decision, not a fix. Acceptance: the signed scripts pass the chain unchanged (the packaged manifest is regenerated after signing, since a signature block changes the file), M8 under `AllSigned` runs, and `Get-AuthenticodeSignature` reports `Valid` on a clean machine that trusts the chain. — *raised by the enterprise-readiness review, 2026-09-05.*

### 25 — Two campaign refinements: `M8`'s refusal message, and the bundle name's resolution

Two refinements of the acceptance campaign's round-15 fixes, accepted in round 16 and deferred when the loop was closed: `M8` should require the signature-specific refusal message (`is not digitally signed` / `未經數位簽署`, plus each further display language the campaign meets) rather than PowerShell's generic `SecurityError` / `UnauthorizedAccess` classification, which an AppLocker or Software Restriction Policy block emits as well, and re-read `MachinePolicy` after the run so that the refusal is tied to the policy in force; and the campaign bundle's name should carry milliseconds and the process id, so that two invocations within one second do not collide on `nhc-campaign_<computer>_<campaign>_<time>.zip` and record a bundle failure. Acceptance: a self-test case for each (a captured output with the generic classification only fails `M8`; two bundles written in the same second both exist), the `campaign` step green. — **The bundle half stopped being hypothetical on 2026-09-06.** The `campaign` step failed on GitHub Actions (run 34011079895, PR #17, a documentation-only change that touches nothing the step reads): 124 passed, 1 failed, the failure being case 20's `exit code 0 -> exit code 1` while the scenario assertion beside it passed — the shape a recorded bundle failure produces, since a skip counts nothing and only a failure on record can raise that exit code. What separates the runs is speed, not code: the failing run finished the step in **60.8 s**, and the same self-test passed at **101.5 s** on the runner (the next commit) and at **106.3 s** on the reference machine, both 125 / 125. Cases 19 and 20 invoke the campaign back to back on the same state directory, and each invocation ends by rebuilding `nhc-campaign_<computer>_<campaign>_<time>.zip`; on a runner fast enough to put both in one second the second collides. Not proven — no bundle row was captured from the failing run — but the fix this item already names (milliseconds and the process id in the name) is what would settle it, and until then the `campaign` step is known to be flaky on a fast machine. — *raised by the PR #11 review loop, 2026-09-05.*

**Status, 2026-09-09 — it happened again, and the timing now cuts against the explanation above.** The `campaign` step failed the same way on GitHub Actions run 236 (`34328879764`, commit `1c09b71` of PR #37, documents only again): 124 passed, 1 failed, case 20's `exit code 0 -> exit code 1` with the scenario assertion beside it passing. **The step took 115.8 s** — slower than both runs the note above cites as passing (101.5 s on the runner, 106.3 s on the reference machine) and nearly twice the 60.8 s of the failing run it was drawn from. The collision explanation turns on a runner fast enough to put two invocations in the same second, and the slowest of the four runs is now one of the two that failed. **That does not refute it** — the step's total duration is not the gap between cases 19 and 20, and a slow run can still hold a fast pair — but the timing no longer supports it either, and it was the only evidence the explanation had. **Two further candidates fit the same shape**: `M2` counted `PENDING` at exit while the record said `SKIPPED`, which would break the invariant PR #11 round 14 exists to hold; and the driver ending before its own `exit` line, since `$ErrorActionPreference` is `Stop` and `Save-State` at `:1183` and the first `Write-CampaignSummary` at `:1231` run outside every `try` — PowerShell then exits 1 by itself, with no row added and the state already correct on disk. (The `Save-State` at `:1175` cannot be it: it runs before the scenario loop, so a death there would have left the crafted `M2 = PENDING` on disk and failed the assertion that passed.) **Nothing separates the three, and nothing will, until [#53](#53--the-campaign-self-test-keeps-no-record-of-what-the-driver-did-so-its-failures-cannot-be-diagnosed) makes the driver's own output survive a failing run** — which is why the second occurrence taught nothing the first had not. **Status, 2026-09-09 (later the same day) — #53's harness half shipped, so the next occurrence is readable.** `campaign.log` now carries every invocation's driver output. What to look for when the step next fails: a `bundle not written:` line naming the campaign ZIP confirms the collision this item describes; the same line naming another file points at something else holding a handle; **no** `bundle not written:` line at all, with the driver's output stopping mid-invocation, means the script ended before its own `exit` and the answer is the third candidate rather than either of the first two.

### 29 — The campaign asks a person to type what a script could do

The campaign asks a person to type what a script could do, and the typing is where the run goes wrong. Of the eleven scenarios, four are `reconfigure`, and three of those four change nothing but software configuration: `M7` is one registry value, `M8` is two registry values (or the same setting through `gpedit.msc`), and `M9` is an AppLocker policy plus a service — `Set-AppLockerPolicy -XmlPolicy` writes exactly what `secpol.msc` writes, so the whole console sequence (create the default rules, delete the one for `BUILTIN\Administrators`, tick rule enforcement, start the service, `gpupdate`) is one XML document and two service calls, and the same again reversed. `A2` needs an interactive standard-user desktop, which a script cannot conjure, but the account it needs (`net user`) is one line. Measured cost of leaving this manual: on this machine `M9` alone took 31 minutes of a 105-minute campaign, produced a literally-typed `<auto|demand|disabled>` placeholder, and ended in a revert that `sc config` refused. What must stay with the person is what only a person can do — the VM's network and display settings (`A3`, `A4`, `M4`), the double-click inside the compressed-folder view (`M1`), and the judgement calls (`Windows showed: 1`, `Open Report: shown`, `panel usable`). Two things to settle in the design rather than in passing: the campaign runs unelevated on purpose, because `A1` measures what an ordinary user gets, so an automated policy change needs an elevated helper rather than an elevated campaign; and `M8` through the registry is not the same evidence as `M8` through a real Group Policy, so where `gpedit.msc` exists the GPO path should stay available and the record must keep naming which path a run took (it already records `PolicyWay`). Acceptance: `M7`, `M8` and `M9` change and revert themselves with no console step, their reverts verified as now, the `PolicyWay` fact still recorded, `RECOVER.txt` still written for the case where an automated revert cannot finish, the self-test covering the automated path for each, and a campaign on a machine with none of these editions still refusing what it cannot measure. Raised by the owner after this campaign: "人為操作盡量限制在必要的動作上". — *raised by the second campaign, on the Windows 10 Pro VM, 2026-09-06; "this machine" is that VM.*

### 30 — A campaign run from a CI artifact cannot measure `M2`

A campaign run from a CI artifact cannot measure `M2`. The asset that `main` builds arrives as `validation-chain-<run>.<attempt>.zip`, and neither that ZIP nor the package ZIP inside it carries a Mark of the Web unless the artifact itself was downloaded by a browser on the machine under test and unpacked with Explorer. On this machine the artifact came from the host, so `M2` was skipped for its missing prerequisite and only passed after the mark was written by hand. The prerequisite message already says to download it with the browser of this machine; it could also name the one-line way to write the mark deliberately, and the record should then say the mark was applied rather than downloaded — which is what the entry above does by hand today. Acceptance: the message names both routes, the campaign records which one this run took, and the summary carries it. — *raised by the second campaign, on the Windows 10 Pro VM, 2026-09-06; "this machine" is that VM and "the entry above" its entry in the validation record.*

### 31 — AppLocker enforcement has never taken effect on a measured machine

AppLocker enforcement has never taken effect on any machine this project has measured, and one machine says it should have. On the Windows 10 Pro VM of `win10-zhTW` the effective policy had Script rules `Enabled` with two rules, `AppIDSvc` was running, `gpupdate /force` had been run and `Test-AppLockerPolicy` answered `DeniedByDefault` for the account on the exact file — and the launcher ran that file to completion in `FullLanguage`. Microsoft's "Requirements to use AppLocker" says the edition stopped mattering for enforcement in Windows 10 2004 and newer with [KB 5024351](https://support.microsoft.com/help/5024351), and this machine is 22H2 build 19045.3803, so the edition is not the explanation. What is left to check: whether that servicing update is actually present on the image, whether a locally-authored policy (`secpol.msc`, no GPO and no MDM) is deployed the way the KB covers, whether enforcement needs a reboot rather than a service start, and whether the AppID driver was filtering at all. Until one machine is made to enforce, `M9` cannot pass anywhere and the tool's behaviour under application control is asserted only by `M7`'s language-mode guard, which is a different mechanism. Acceptance: one machine where a denied script is actually refused, `M9` PASS there, and the record naming what made the difference. — *found by the second campaign, 2026-09-06; the first reading of it as an edition limitation was wrong (Codex round 1 on PR #16). What has been measured mechanism by mechanism is on [`application-control.md`](application-control.md).*

### 32 — The report records the DHCP mode but not the DHCP server

The report records the DHCP *mode* but not the DHCP *server*. Each adapter row says whether the address came from DHCP or is static, and the expected-standard comparison checks that mode against the configured expectation — but nothing in the report names **which server answered the lease**. `ipconfig /all`'s `DHCP Server` line is what the SOP calls the rogue-DHCP detector at station 1 ("Who actually answered"), and it is on the `local` fingerprint's lane — the DHCP lane, the one where the tool exists precisely to save the support engineer a round trip to the user. As it stands the engineer must still ask for `ipconfig /all` by hand, which the field manual now says in as many words. The datum sits on the CIM path the tool already reads (`Win32_NetworkAdapterConfiguration.DHCPServer`); the `Net*` cmdlets the tool prefers have no equivalent, so the row would be CIM-only and must say so when that path is unavailable, the way the data-source row already does. IT-scoped, so no verdict moves. Acceptance: one row per adapter holding a lease, naming the server's address; a row saying the address is static where it is; the row reporting the datum as unavailable when only the cmdlet path answered; unit tests for the three shapes in both languages; and `tests/environment_probe.ps1` recording the same fact, so a campaign can compare what the tool reports against the machine. — *found while writing the support-engineer field manual, 2026-09-06.*

### 33 — Tiers 2 and 3 of the document-fact step

Nothing checks that the documents still describe the tool. `sop/` now holds three documents making specific, checkable claims about the shipped code — the SOP's tool section, the support-engineer field manual, the report template — and `healthcheck/` will hold two more when the user manual and the IT deployment manual of #32's release go inside the package. The validation chain does not read `sop/` at all, and the packaged validator checks one string per script (`$script:ToolVersion`, `validate_release.py:70`); no documented fact is tied to the code that makes it true. Three ways this has already gone wrong, every one caught by a review round rather than by a test: a fact corrected in the manual was copied into the template in its **pre-correction** form (an added target that fails is `INFO`, except a DNS name that will not resolve, which is `WARN` and moves the verdict); the same item had to be corrected in **three** places (raw command output and the switch and AP status pages — the manual's coverage table, then its prose, then the template's checklist); and a fix reintroduced something an earlier document already had right (the launcher's `%TEMP%` fallback carries a different file name, `NetworkHealthCheck_LauncherError.txt`). The fourth way is the one no review round can catch, because a review only runs when somebody touches the document: **the code changes and every document goes quietly stale.** Acceptance: a chain step that asserts a small set of load-bearing facts twice — once against the source that makes them true, once against each document that states them — and names the document to update when the source moves. Starting candidates: the language-mode guard's exit code 3; the launcher error file's two names and locations; `TracerouteHops` defaulting to 3; `DHCP: Unknown` as the default of the adapter's mode field; the required/optional status chain for ping targets, including that it stops at the first match; and the CIM fallback hard-coding an adapter as `Up`. Assert on the fact token rather than on a sentence, so that rewording a document does not fail the step. What such a step cannot do is judge a document's *reasoning*: "the link is up and the adapter is healthy" was a wrong inference from correct measurements, and only a review round found it. Best done when the two manuals go inside the package, since the validator's version check has to be extended at the same time. — *raised by the owner while the report template was in review, 2026-09-06: "有可能會出現不一致的問題嗎？"*

**Status, 2026-09-07.** Tier 1 is done and closed: `tests/doc_facts.ps1` with `tests/selftest_docfacts.ps1`, the chain's `docfacts` step, 96 assertions and 40 mutations — the identifiers the documents quote (result tags, fingerprint keys, configuration keys, exit codes, file names, local links, section numbers) against the identifiers the two scripts and the two shipped configuration files define. What it reads is code spans only, never prose. Two tiers remain, as its entry in the validation record says: **tier 2**, the manuals' quoted report strings against a real report of that language, which the chain's `acceptance` step already produces; and **tier 3**, the fingerprint chain's rule order against the field manual's table.

### 34 — The user launcher closes its window over a console-mode fallback

The user launcher closes its window over a console-mode fallback. `Start-NetworkCheck.cmd` (and the IT launcher) exit 0 without a pause when the program exits 0, which is right for a GUI run — the window would otherwise linger after the person closed the tool — but when `Initialize-Gui` fails, the tool runs the same checks in console mode inside that window, prints the three report paths, and the launcher closes the window on them. The reports are written and the report carries a startup-notice row saying what happened, so nothing is lost but the paths; the user manual (§6) sends the person to the `Reports` folder, and to the console launcher — which pauses — for a run whose text should stay on screen. A fix needs the launcher to know the run was a fallback: for example the script pausing itself, in console mode, when it was not started with `-ConsoleOnly` and its console is interactive, weighed against the GUI case it must not touch and against the chain's console runs, which must not wait for a key. Acceptance: a GUI-fallback run through `Start-NetworkCheck.cmd` leaves the paths on screen; a normal GUI run still closes the window when the tool is closed; the console launcher and the chain are unchanged; the launcher self-test covers the fallback. — *found walking real reports through the user manual, 2026-09-06.*

### 37 — When the launcher itself is refused, nothing of ours writes anything

Every refusal this project has measured happens after `Start-NetworkCheck.cmd` has started: PowerShell refuses the script under an `AllSigned` policy (`M8`), or runs it in `ConstrainedLanguage` and the guard of #18 writes its environment report (`M7`). Since 1.2.3 the launcher turns each of those into a suggested action in `LauncherError.txt` and on the screen — the ZIP for a missing program file, the machine for a missing PowerShell, the environment report for exit code 3, and for any other non-zero exit the message PowerShell printed above it, with "ask IT to allow `NetworkHealthCheck.ps1`" when that message names a signature or a policy (#28; `tests/launcher_check.ps1` runs the six launchers through every reason, 114 assertions). The case that leaves the person with nothing is the one where the launcher is what is refused: AppLocker's script rules cover `.cmd` as well as `.ps1`, and a product that blocks the `.cmd` file itself — or `cmd.exe` — stops the package before its first line, so Windows shows its own message, no file of ours is written, and there is nothing to send with the support request. A block on `powershell.exe` is **not** this case: the launcher has already started, its call to `%PS_EXE%` returns a non-zero `ERRORLEVEL`, and the reason branch below it writes `LauncherError.txt` with the suggestion to send the message printed in that window — which is exactly what #28 covers, and what the `exit code 1` case of `tests/launcher_check.ps1` exercises. Nothing inside the package can fix that from inside — what can be decided is what the package carries for it. It has not been measured: no machine with an EDR product has been part of an acceptance run, and #31 says AppLocker enforcement has never taken effect on any machine this project has looked at, so the state itself has never been produced. Acceptance: one machine where the launcher itself is refused, with the record naming what the person saw and where Windows said it; and a decision, recorded either way, between a one-page printed note in the package — the "it will not start" page an IT department can hand out with the ZIP — and the statement that section 8 of the IT deployment manual is where this belongs and the package carries nothing further. — *split out of #23 when that item was closed, 2026-09-08; #23's own question — whether the launcher should say in plain language what IT can do — was answered by #28 in 1.2.3.*

### 38 — The retransmission counter read fails intermittently, and takes the verdict and the run's length with it

`Get-TcpCounterSnapshot` reads `Win32_PerfRawData_Tcpip_TCPv4` and `Win32_PerfRawData_Tcpip_TCPv6` with `Get-CimInstance -OperationTimeoutSec 8`, once before the sample window and once after; a read that fails is collected per protocol, and `Compare-TcpCounters` writes one *Unable to Check* row per failed read. Measured on `win11-enUS` during the 1.2.4 user-manual walk, 2026-09-08: **the first run of the session lost TCPv4** — `Microsoft.Management.Infrastructure.CimException`, *Timed out* — while every connectivity check passed, and the timeout inside the same pass stretched the window TCPv6 actually measured from the configured 8 seconds to **13.3**; a second run minutes later read both protocols and sampled **9.1**. Exactly one row appeared, so one of the two reads timed out, not both. The likely cause is the WMI performance-counter provider starting cold on a machine where nothing has touched performance counters yet — a normal condition, not a fault — and what makes it worth fixing is *which* run pays for it: the first one, which is the run a person makes when they have a problem, and the measurement it loses is the one that would have shown packet-level trouble. Two candidate fixes, independent and cheap: a throwaway query **before** the sample window, so the provider's start-up cost falls outside the measurement and cannot stretch the other protocol's window; and one retry of a read that timed out. Acceptance: on a machine in the state that reproduces this — a run started in a copy extracted moments earlier, better still with the machine under load — both protocols are read, or *Unable to Check* is written only after a further attempt has also failed; each protocol's reported duration is derived from its own stamps, and **a sample that ran longer than the configured length because another read failed says so in the row** rather than printing a figure that contradicts what the person was told — the serial reads make the delay itself unavoidable, so what the fix owes is an honest number with its reason, not a number that pretends nothing happened; unit tests cover the further attempt, the pre-window query and both duration cases; the rest of the chain is unchanged. — *found by the user-manual walk on `win11-enUS`, 2026-09-08; the manual half of the same observation is a 1.2.5 documents fix, since section 9 lists a permission, a policy and a broken performance counter as the causes and not the timeout the tool itself imposes.*

**Status, 2026-09-08 — the walk falsified the hypothesis above, and the item is better for it.** The timeout recurred at 12:47, on the **sixth** run of the day on that machine (09:31, 10:15, 11:22, 11:33, 11:46, 12:47), so a provider that starts cold cannot be the explanation: it was warm five runs earlier. What is established is narrower and worse than the first reading: **the read fails intermittently on a machine where nothing is wrong**, it costs the retransmission measurement, and it takes the verdict to *Test Incomplete* with it (#39). What is not established is the mechanism. Idle time does not predict it either: the six runs of that day were 09:31 (**timeout**), 10:15, 11:22, 11:33, 11:46 and 12:47 (**timeout**), and the gap before the clean 11:22 run was 67 minutes while the gap before the failing 12:47 run was 61 — so a provider host recycled after idle does not separate them, and neither does a boot or a resume, since the machine did neither. One correlation does hold across all six, and is recorded because it was observed rather than because it is proven: **both failures followed an Explorer extraction of the package into a OneDrive-synced folder within minutes** (the first extraction before the 09:31 run; `NHC-blocked` extracted at 12:40, run at 12:47), and none of the four clean runs followed an extraction at all. Thirty-one files landing in a synced folder means the sync client is reading and uploading them, and `Win32_PerfRawData_*` queries are sensitive to disk and CPU load. Two failures out of two, none out of four: a lead, not a mechanism. **Third occurrence, same day, and the condition is now stated better.** The 13:03 run — the first run inside the freshly extracted `NHC-unblocked` copy — lost TCPv4 as well, making it **three failures in three runs that followed an extraction, and none in the four that did not** (09:31 fail, 10:15 clean, 11:22 clean, 11:33 clean, 11:46 clean, 12:47 fail, 13:03 fail). What that sharpens is the condition, and it also narrows my earlier reading: **the failing runs are the first run inside a freshly extracted copy**, which is not the same claim as “OneDrive was busy”. Two mechanisms fit the same evidence and neither is established — a sync client uploading thirty-one new files, and the antivirus scanning thirty-one newly created files and a script executing from a path it has not seen before. Both produce the disk and CPU load that `Win32_PerfRawData_*` is sensitive to; only the second needs no cloud folder at all. So the condition to reproduce is *a run started in a copy extracted moments earlier*, on a synced folder and on a plain local one, which separates the two. **The control arrived seven minutes later and the cost is now measured.** A *Run Again* in the same window, with no extraction before it, read both protocols cleanly — three failures in three runs that followed an extraction, none in five that did not. The two runs are otherwise the same work on the same machine, and they differ like this: the failing run took **25.9 seconds** and reported a sample window of **14.5** against the configured 8; the clean one took **11.7** and reported **8.8**. So the timeout costs the measurement, stretches the other protocol's window by its own eight seconds, and **more than doubles the run** — against a manual that tells the person to expect about ten seconds. That is a third thing the retry buys, beside the measurement and the verdict.

**How it gets verified, decided 2026-09-08 — two levels, and only one of them belongs in the chain.**

*Deterministic, and this is what guards the fix.* Every performance-counter read passes through one named helper, `Get-CimOrWmiInstance` (`NetworkHealthCheck.ps1:2802`), which the unit tests can load by AST the way they load the other helpers. Three cases, no machine state required: a stub that throws a `CimException` “Timed out” on the first call and returns a counter object on the second must produce a normal reading, not an *Unable to Check* row; a stub that throws on both calls must produce exactly today's row, because a retry that swallows a real failure is worse than no retry; and a failure on one protocol must leave the other protocol reporting **its own** interval, taken from its own stamps, together with the sentence that says the sample ran long because another read failed — not an unstretched window, which the serial reads make impossible, but an honest one with its reason. These run in the chain, in both languages, and they cost nothing.

*Statistical, and it must never gate a build.* Whether the failure happens at all is a property of a machine under load, so the harness that measures it — N reads with the machine idle, N with it under deliberate local file I/O (a large tree copied by the harness itself; no sync client, because CI has none) — reports a **failure rate per condition** and is run on demand, not by the chain. A step that fails one run in twenty teaches nothing and erodes trust in every other step: this project already owns one such case, the campaign self-test's bundle-name collision on a fast runner (#25), and recorded it as a measurement rather than hiding it behind a re-run. The harness is how the lead above gets settled and how the fix is shown to move the rate; the three unit cases are how the fix stays fixed.

*Where the retry goes.* `Get-CimOrWmiInstance` is the one place the counter reads pass through, but the operating-system query (`:996`) and the adapter-configuration queries (`:1196`) call `Get-CimInstance` directly with the same eight-second timeout and do not use the helper. A retry inside the helper therefore leaves them out — which is a decision to state in the change, not to discover afterwards: either route them through the helper too, or record why they stay as they are. The consequence for the fix: what the evidence rules out is the **diagnosis**, not the **mechanism**. A throwaway query before the sample window is itself an extra attempt: if load makes one call time out and the next succeed, it can absorb the transient exactly as a retry does, and it has an advantage a retry cannot have — it spends its attempt **outside** the measured window, so it cannot stretch the sample the way the failing call did (14.5 s against a configured 8). What only a retry covers is a call that fails on the measured attempt itself. Both stay in the fix, for those two different reasons. **And the stretch has its own fix, smaller than it looked.** `Get-TcpCounterSnapshot` reads the two protocols serially and stamps each with its own `Timestamp`, but `Compare-TcpCounters` derives the duration from the **enclosing** snapshot's stamps (`NetworkHealthCheck.ps1:2901`), which are taken after both reads — so a timeout in one protocol's read is reported as part of the other protocol's sample window. The deltas are unaffected, because each is the difference between that protocol's own two readings, and the rate is a ratio and not a time; **only the reported duration is wrong**. Computing it from the per-protocol stamps that already exist gets most of the way, **and not all of it**: each stamp is taken *after* that protocol's query returns and TCPv4 is queried first, so a timeout on the ending TCPv4 read still delays the ending TCPv6 read and its stamp. The interval it then reports is TCPv6's **true** window — the sample really did span that long, and the delta really is over that span — so the number is not wrong; what is wrong is showing it without a word while the person was told the sample lasts eight seconds. So the fix has two halves: derive each duration from that protocol's own stamps, and **say when a sample ran long because another read failed**, rather than printing a figure that silently contradicts the configured length. Both have to land before a retry does, since a retry on the ending TCPv4 read would push the TCPv6 stamp further still — **and the retry has to leave a trace when it succeeds**, or the explanation cannot be written at all: today a failed attempt reaches `Compare-TcpCounters` only as an error that made it into the snapshot, so a read that timed out and then succeeded would hand back a clean counter and no record, and the row for the *other* protocol would have nothing to say about why its sample ran long. The snapshot has to carry attempts that failed even where a later one worked. The acceptance above stands, with a machine under deliberate load as the condition worth reproducing, and with both halves kept: the pre-window query for the attempt that costs the measurement nothing, the retry for the failure that lands on the measured call.

**Status, 2026-09-09 — the verdict half of this item is no longer this item's to fix.** The decision recorded under [#39](#39--a-measurement-that-could-not-be-taken-outranks-a-measurement-that-failed) takes the verdict away from quality rows: a counter read that failed still writes its *Unable to Check* row, and is now named in the summary, but it no longer turns a run in which every required check passed into *Test Incomplete*. That is the first half of this item's title. The second half is untouched and is what remains here — the run's length, and the window the other protocol actually measured: eight seconds configured, 13.3 measured, because one read waited out its timeout inside the sample. The retry, the one place it goes, the queries that do not pass through that place, and the per-protocol stamps all stand exactly as written above, and so does the acceptance sentence.

**Status, 2026-09-09 (1.2.8) — everything but the first clause is done and measured; that one waits for a machine.** Four changes, and each answers a sentence of the item above.

**The second attempt.** `Get-CimOrWmiInstance` takes `-Attempts` and a list to record what failed in; the two counter reads of a snapshot ask for **two** and nothing else in the tool asks for more than one. A read that fails twice is not attempted a third time, and its row is the row it always was — same status, same check name, same message, because a retry that hides a real failure is worse than no retry — with the attempts behind it added to the details. No attempt is classified: a read that failed instantly for a permission or a missing class is attempted again too, and costs nothing to attempt, where classifying it would mean reading a message the operating system writes in its own language (#14 is that lesson).

**The read before the window.** `Get-TcpCounterSnapshot -WarmUp`, on the **baseline** snapshot only: one throwaway read per class, in a pass of its own before either counter is read, its reading discarded, its failure neither an error nor a measured attempt. The pass of its own is the point, and it took a review round to get there (PR #40, round 3): interleaved with the measured reads, TCPv6's warm-up fell after TCPv4's baseline stamp and so inside TCPv4's window — and a warm-up that is merely **slow**, which is the start-up cost the feature exists to absorb, would have lengthened that window with no failure behind it to explain the seconds. The ending snapshot takes none — inside the window it would lengthen the very thing it is there to protect. Whether the first read of a session is the one that fails is the question this item leaves open, so the warm-up's failures are recorded (`WarmUpFailures`, kept apart from the measured `FailedAttempts`) and shown in the row of the protocol they belong to.

**The trace, which the retry could not do without.** Every attempt that failed is kept with the seconds it spent, *even where a later attempt succeeded* — the case the item named, where a read that timed out and then worked handed back a clean counter and no record, so nothing could explain the seconds it had spent. A row for a counter that could not be read names the attempts behind it; a row whose window carried a read that **failed** names those seconds and those reads. Nothing else in a window is itemised - a read that was merely slow, or the checks that run between the two samples, lengthen it without a line of their own (PR #40, round 13), which is why the row prints the duration it truly measured rather than an accounting of it. A row that says a counter could not be read carries that protocol's failed reads from **both** snapshots when the other snapshot wrote no row of its own for it, because a protocol without a reading has no quality row and that row is the only other place they are named (PR #40, round 4); each line says which snapshot it belongs to, so a baseline failure can never read as an ending one.

**Three ways the guarantee still leaked, all found in review round 5 and all closed.** A query that returns **nothing**, or an instance without the counter fields, is a read that failed as surely as one that threw — and that check sat outside the retry loop, so a timeout got a second attempt and an empty answer did not. It is inside the attempt now (`-RequireProperty`), which the pre-window read does not ask for, its reading being discarded. The **counter-reset** row returned before the evidence lines were appended, so a read that failed and was redeemed vanished from a run whose counters had reset; every row of a protocol now carries them. And a **baseline where both classes failed** was thrown away by its own step guard: `Invoke-CheckStep` caught the throw, wrote its generic step-error row and returned `$null`, taking four attempts, their seconds and any pre-window failures with it, and leaving the analysis to say only that complete data was unavailable. The snapshot is returned whatever it holds, and one row per read that failed is written out of it. **The acceptance validator had to learn the new shape** (PR #40, round 9): `Test-ResultSet` still expected a step-error row and one generic row on a machine where neither class could be read — the shape 1.2.7 produced — so an end-to-end run on exactly the machine this path exists for would have been rejected as malformed. It now expects one row per read that failed, per sample, and no step error at all; both protocols are named whatever their counters did; and `selftest_resultset.ps1` pins the new shape and rejects the old one (41 → 42 cases). **And the chain's own probe had to learn the retry too** (round 10): `Get-MachineFacts` asked each counter class once, so a transient failure there would have called a class unreadable that the run reads on its second attempt, and the result-set check would have rejected a correct report on exactly the machine this release is for. The probe now mirrors the shipped read — two attempts, the same two fields — and an AST assertion in `unit_tests.ps1` fails if the shipped call stops saying what the probe assumes. **The reset row was refined once more in round 7**: it prints the window it spans, so the note's *these N seconds* has something to refer to, and it no longer borrows the sentence about the deltas above — a row that reports an uncalculable delta has none. That sentence now belongs to the rows that do.

**And the version bump rewrote history until round 7 caught it.** Replacing every `1.2.7` label in the manuals also rewrote three provenance statements — the extra-TCP label's width, the stray positional value, and the summary's *All required checks passed* — which describe what changed in **1.2.7**, not in this release. Six files: both manuals, both formats, both languages, minus the two HTML twins that never carried the sentence.

**The duration, and the sentence beside it.** Each row's sample duration now comes from **that protocol's own two stamps**, and the configured minimum stands beside it — a minimum, which is what `Wait-ForMinimumTcpSample` enforces, not the target the old label implied. A row also says when its window carried a failed read, and the rule for which reads those are took a review round to get right (PR #40, round 1). A window is lengthened by a read that delayed the stamp closing it without delaying the stamp opening it: in the **ending** snapshot, every read at or before this protocol; in the **baseline** snapshot, every read *after* it — a stalled TCPv6 baseline read pushes TCPv6's own opening stamp and the rest of the run alike, but not TCPv4's, so it lands squarely inside TCPv4's window. If one of them ever fails the way the counters do, this is the paragraph to come back to.

**The cost, stated rather than discovered.** On a machine whose counters answer, the two pre-window reads are the whole addition and they cost milliseconds. On one where every read runs out of time, a run's six reads spend up to **80 seconds** between them against 32 before — the price of not losing the measurement, and the manuals now say a counter read that runs out of time is tried once more before the tool gives up on it.

### 39 — A measurement that could not be taken outranks a measurement that failed

`Get-OverallStatus` counts every row outside the `IT` scope: one `FAIL` gives **Problem Detected**; otherwise one `ERROR` gives **Test Incomplete**; otherwise one `WARN` gives **Attention Required**. So a supplementary quality statistic that could not be read — the retransmission counters of #38 — produces the same verdict as a check whose absence leaves the verdict genuinely unknown, and it **outranks a real warning**: a run that could not read one counter reads as worse than a run with measured packet loss. The walk produced exactly that on 2026-09-08: every connectivity check passed, one CIM read timed out, and the report said *Test Incomplete* on a healthy network. The user manual's own section 4 already has to tell the reader that Test Incomplete "is not proof of a network fault" — a document apologising for a verdict is a sign the verdict is doing the wrong work. The distinction to draw is between a check whose absence leaves the verdict unknown (adapter enumeration, the gateway, DNS) and a quality measurement that could not be taken while every required check passed; the first is what *Test Incomplete* is for, the second is worth reporting without overriding "everything I could test passed". One shape that would do it: a verdict weight per check, so that rows marked as quality report their `ERROR` as they do now but do not set the `ERROR` verdict, with the summary naming the measurement that was not taken. This is a decision before it is a change — what *Test Incomplete* is for — and the change reaches both scripts, the unit and report-stage tests, the four manual files' verdict tables and the six guide copies. It is the same family as #27, where "no default route exists" reached the reader as "the route table could not be read": something the tool could not measure, reported as if something were wrong. Acceptance: a run where every required check passes and only a quality measurement could not be taken reads as healthy with that measurement named in the summary; a run where a check that decides the verdict could not run still reads *Test Incomplete*; the manuals' verdict tables quote the new rule; tests cover both. — *raised by the owner during the user-manual walk, 2026-09-08: "網路是正常的但是出現 Unable to Check … 是不是容易讓 end user 誤認網路有問題？"*

**A second instance, sharper, from the same walk (2026-09-08).** The IT panel was given `8.8.8.8` as its extra TCP target, without a port. The tool did the right thing and said so — *Ignored extra TCP target '8.8.8.8': expected host:port.* — as a Startup Notice, which is a `WARN`, so the run ended **Attention Required** and its summary told the person *Warnings to review … Send the report to IT as it is*. Every network check had passed. The verdict was answering a question about the operator's typing, and the advice it produced was the wrong advice: the action was to correct the field and run again, not to send anything to anybody. The row itself must exist — silently dropping a target somebody asked for would be worse, and both manuals document the behaviour correctly (the IT deployment manual names the message; the user manual states the general rule that a Startup Notice on its own turns the verdict to Attention Required) — so what is in question is not the row but its weight. This case is cleaner than the one above: an unreadable counter is at least a fact about the machine, while a malformed field is a fact about the last thirty seconds of typing. **And it has a control.** Thirteen minutes later the same panel was given the same values with `:443` added to that one field, on the same machine and the same network: every other input identical, and the verdict was *Overall Healthy* with the summary *Everything passed*. The difference between “send this report to IT” and “nothing to see here” was a port number in a text box — which is as close to a measurement of this item as the walk could produce.

**Decision, 2026-09-09 — what *Test Incomplete* is for, and which rows lose their weight in the verdict.** Taken by the owner after the inventory below was made. It is the decision this item says has to come before the change, and it also settles the branch [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample) says belongs beside it.

**The rule.** *The overall result is decided by what the run measured. A supplementary statistic that could not be taken, a sample too coarse for the threshold applied to it, and a fact about this run's own input each keep their row, their badge and their place in the counts, are named in the summary, and do not change the overall result. Everything else keeps its weight, **optional targets included**: an optional target that answered badly is a measurement, and it goes on turning the verdict to Attention Required exactly as it does today.* Put the other way round: the verdict answers what the machine is like, not what the last thirty seconds of typing were like.

**The first draft of that sentence said *decided by the required checks*, and round 5 found it at P1** (PR #37). It named an axis the inventory beneath it does not use, and the tool is full of optional checks that measure something and rightly move the verdict: an optional DNS lookup that resolves nothing is a `WARN`, partial loss or high latency on an optional ping target is a `WARN`, a connectivity group of optional members that all failed is a `WARN`, and `tests/report_stage_tests.ps1` pins the DNS and group cases as *attention* outcomes. An implementer following the sentence would have demoted every one of them; one following the table would not. **Required versus optional is not the axis; measured versus not measured is.**

**Which rows lose their weight — by the branch that writes them, never by their tag.** The inventory is part of the decision, because this item's own two instances are not the whole of it:

**The table above is the whole inventory; what follows it is commentary. Two of its rows name branches that do not exist yet** — the row each target check must start writing, and the undersized ping outcome, which is [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample)'s to create. They are in the inventory because **the marking is opt-in**: a branch left out of it keeps its weight by default, so a branch that arrives later without a line here arrives weighted — and #51's own acceptance already asks for a single lost packet to report its count with no verdict. The two changes have to agree on this row or one undoes the other, and the report-stage tests cover it from both sides.

**A dropped extra target never reaches the check that would have tested it** (PR #37, round 11, P1). `Set-RunOptions` writes its Startup Notice and then `continue`s — the target is never added to `$config.Tests.TcpTargets`, so `Test-TcpTargets` never sees it and the invalid-configuration branch listed above can never fire for it. The row the second condition demands in the TCP section is therefore a **new branch on a different code path**, the option-parsing one, and not the configured-invalid-target branch it might be mistaken for; under opt-in marking it would have arrived weighted. Extra TCP targets are the only ones this can happen to, because they are the only extra targets with a syntax rule to fail (`Test-TcpTargetSyntax`, v1.2.7's #45). **Whether the change writes two weightless rows — the notice and the section row — or moves the notice into the section as one is the change's call**; what this decision requires is that the target's own section shows something, and that neither row carries weight.

**The ping row carries two measurements under one status, so the undersized rule reaches only half of it** (PR #37, round 12, P1). `Test-PingTargets` classifies loss and latency in a single `if`/`elseif` chain into one `$status` on one row — critical loss, warning loss, critical latency, warning latency. The successful replies' average is a measurement in its own right and keeps its weight by this decision's own rule, so demoting the whole row because the **loss** sample was too coarse would throw away a latency verdict that was measured properly, and a target answering at 300 ms could sit inside a run that reads *Overall Healthy*. Either the row splits into a loss result and a latency result, or it keeps its weight with its status **recomputed from the latency alone**; the change picks, and what it may not do is demote the row as a unit.

**Those two options are not equivalent, and the weaker one needs its exact wording** (PR #37, round 13, P1). The first draft of this paragraph said the row could simply *keep its weight whenever latency alone would have crossed a threshold* — but the chain evaluates critical loss before either latency branch, so a row that keeps its weight keeps the status the **loss** produced. A required target at 25 % loss and a 150 ms average is a `FAIL` today (25 ≥ the critical 20), and preserving that row's weight would end the run at *Problem Detected* on the strength of one packet, while the measurement that was sound warranted a warning at most (150 ≥ the warning 100, below the critical 250). The severities differ, so the retained status has to be **recomputed**, not preserved. Splitting the row does this by construction, which is why it is the option to prefer.

**And that chain already costs something today, before any of this.** Because it is `elseif`, a row whose loss crosses first never evaluates the latency branches: a target at 25 % loss and 300 ms average reports the loss and its status says nothing about the latency, though the message text prints the average beside it. That is the same one-row-two-claims shape, losing information in the shipped tool rather than in this decision — found while checking what the demotion would take with it, and left here for whoever writes the change to decide whether it deserves an item.

**And the adapter comparison says one thing at two statuses** (PR #37, round 9, P1). Its counter-reset branch — *The adapter counters were reset during the test, possibly because the adapter reconnected or restarted; a reliable delta cannot be calculated* — is the same claim as `Compare-TcpCounters`' reset branch, which was in this inventory from the start while its adapter twin was not; the marking being opt-in, it would have stayed weighted and gone on turning a healthy run into Attention Required. The two branches also carry **different badges for that one claim**: the TCP one is an `ERROR`, the adapter one a `WARN` on a physical adapter and an `INFO` on a virtual one. This decision does not touch either badge — it removes a verdict, never a badge — but the inconsistency is written down here rather than left for the next reader to rediscover, and whoever writes the change decides whether it deserves an item of its own.

**Everything else those same functions write keeps its weight, which is what a list of tags obscured** (PR #37, round 2). `Compare-TcpCounters` puts `tcp-retransmissions` on its rated `PASS`/`WARN`/`FAIL` row as well as on its failures; the adapter comparison puts `adapter-errors` on every measured delta; a required TCP or HTTP target's connection failure carries `tcp` or `http`. Demoting those three tags as units would have let a measured retransmission rate, a measured adapter error count and a failed required target coexist with **Overall Healthy** — contradicting this decision's own closing paragraph two screens below. **The tag is not the unit and never was**: it feeds the language-neutral fingerprint, which is a different job. The marking is applied where the row is created, and nothing selects rows by tag afterwards.

**Inside the input-fact family — and only there — the tool already has the axis, and it is `Required`.** `Test-PingTargets` and the checks beside it already turn that flag into `FAIL` versus `INFO`, so the split follows the flag that exists rather than inventing a second one. **What the flag decides is which rows a target gets, not whether one row changes weight** — corrected in round 17, after round 7 split the row and this paragraph was left saying otherwise. Every invalid target, required or not, gets the weightless input notice; a **required** one additionally gets a weighted row saying that a check which decides the verdict did not run. The flag does **not** separate a measured optional failure from a measured required one, because both of those are measurements and both keep their weight. That is what keeps the second condition below honest: the reader meets the same input notice in the target's own section either way, and the verdict moves only when a required check genuinely did not run.

**And the same typo is convicted twice, which round 3 found at P1** (PR #37). `Test-ConfigurationSemantics` collects an invalid `TcpTargets` host or port, an invalid `HttpTargets` URL and a blank `DnsNames` host — and, once the validation gains `PingTargets`, a blank or malformed ping address too — into the same `$errors` list as the `Expected.*` values and `DhcpEnabled`, and all nine writers land in a **single aggregate row** — *The configuration file contains N invalid value(s). The program will continue, but related results may not be meaningful.* — tagged `config`, which this decision keeps weighted. The invalid target then produces its own row in its own section as well, because validation reports it and the run continues. So an optional TCP target with a typo would be demoted in the row that names it and convicted in the row that does not: still *Test Incomplete*, and the promise of this decision undelivered.

**A verdict cannot attach to part of a row, so that row has to be split before anything is demoted.** The two families in `$errors` are not the same claim. `AllowedIPv4Addresses`, `AllowedIPv4Cidrs`, `AllowedPrefixLengths`, `AllowedDefaultGateways`, `RequiredDnsServers` and `DhcpEnabled` are the inputs of the company-standard comparison, and a malformed one makes those rows meaningless — that is the `config` row this decision keeps weighted, and the reason it keeps it. An invalid `TcpTargets`, `HttpTargets`, `DnsNames` or `PingTargets` entry costs exactly one measurement and follows the same `Required` axis as every other target. (This paragraph first said such an entry *is already reported by the check that would have made it*. That was false, and round 4 below says how.) The change reports the two separately, and the aggregate row stops carrying both.

**And the other aggregate row was left behind — round 3's finding on the other list** (PR #37, round 14, P1). `Test-ConfigurationSemantics` builds **two** aggregate `config` rows, not one: *Configuration Validation* from `$errors`, which round 3 split, and *Configuration Thresholds* from `$warnings`, which nobody had looked at. Its nine writers divide by the same question. **Weighted:** the test values and the count thresholds that fall back to built-in defaults, and the three ordering checks — every one of them changes what the other rows were judged against. **Weightless:** a `Checks.<flag>` that is not a boolean, where *the check is disabled*, and `Checks.TracerouteHops` out of range, where the default is used.

**The second family is absurd as it stands, which is the sharpest argument for the split.** All six flags name IT-scope diagnostics — Wi-Fi radio, routes, gateway neighbour, proxy, traceroute, drivers — and `Get-OverallStatus` excludes IT-scope rows from the verdict. So **the check itself cannot move the verdict, while the notice saying it was switched off can**: a malformed boolean in a configuration file turns a healthy machine's run into Attention Required, and no measurement anywhere is affected. The shape of the miss is round 9's — one aggregate split and its twin left alone — and both rows now split by the same question: does this change what the other rows mean, or does it cost one thing that was never measured?

**Round 10's assertion put the earlier prose in debt, and this pays it** (PR #37, round 15, P1). Declaring the table the whole inventory obliged every branch that had been settled in a paragraph to appear in it, and two had not: the `step-error` rows of the four collector steps, decided in round 6, and — found by auditing the rest of the table against the paragraphs rather than waiting for another round to find it — the input notice a **required** invalid target owes, decided in round 7 and contradicted by a sentence left standing from round 4. All three are fixed here. The audit was mechanical: every sentence in this decision that claims a row is weightless, checked against a row of the table. It now finds none unmatched.

**And one rule that the audit above did not have and now does: the four target families move together** (PR #37, round 16, two P1s). Ping arrived late three times — it was the only family the configuration never validated (round 6), it was left out when round 15 broadened the input notice to required targets, and it was left out of the aggregate row's weightless half even though round 6 had already said its validation was coming. Each miss was small and each would have left a run at Attention Required or *Test Incomplete* for a typo. **So wherever this decision names one target family it means all four — ping, DNS, TCP, HTTP — and a prescription that names three is a defect in the prescription**, whatever the code happens to do today. The historical paragraphs above keep their original lists, because they record what was found and when; every prescription now names four.

**The round-15 audit checked one direction only, and round 17 is what it missed.** That audit matched every sentence claiming a row is *weightless* against a row of the table, which is why it found the two branches that were never tabled — but a sentence claiming a row **keeps** its weight is just as capable of contradicting the inventory, and one did: the `Required` paragraph above still described a single row whose weight the flag decides, three rounds after round 7 had replaced it with two rows. **So the audit runs in both directions**: every claim about a row's weight, weightless or weighted, against the table and against the two-row split. A prescription that survives an audit only because the audit was pointed the other way is the same defect this decision is about, in the method rather than in the tool.

**Round 4 corrected the table's fourth row: for the targets it named, the branch it named does not exist** (PR #37, P1). `Test-TcpTargets` writes *The configured host or port is invalid* **only when the target is required** and otherwise moves on; `Test-HttpTargets` writes *The configured URL is blank* only when it is required; and `Test-DnsNames` writes nothing at all for a blank host, required or not. The demotion had been aimed at rows that are never produced, and round 3's justification for splitting the configuration row — that such an entry is already reported by the check that would have made it — was false for every optional target and for DNS in both cases.

**What that changes.** The split of the configuration row stands, on the other ground it was given: an invalid target costs one measurement rather than invalidating the comparison. What does not stand is the assumption that the reader would still see it. **Four rows are missing today** — an invalid optional TCP target, an invalid optional HTTP target, a blank optional DNS host, and a blank **required** DNS host, which is a gap independent of this decision: it produces no DNS row at all, and the only trace of it is a line in the details of the aggregate configuration row. So the second condition above is not a formality here; it is the entire safety of the split.

**And it fixes the order of the change.** The rows have to exist before the configuration row is split, or an optional typo moves from *convicted twice* to *mentioned nowhere the reader looks* — which is worse than what this decision set out to fix. A required target's existing row becomes the weighted one saying its check did not run, an optional one gains a weightless row, and DNS gains both. (Round 7 refines this: the required target gains the weightless input notice as well, beside the weighted row that says its check did not run.)

**The ping targets are validated nowhere, and their one branch carries two different claims** (PR #37, round 6, P1). `Test-ConfigurationSemantics` validates `TcpTargets`, `HttpTargets` and `DnsNames` and never touches `PingTargets`, so a blank or malformed ping address travels intact into `Test-PingTargets`, resolves to nothing, and becomes a **weighted** `WARN` — *No testable target was found* — turning an optional typo into Attention Required, which is this rule's own counter-example. **But the same branch also carries a machine fact:** `AUTO_GATEWAY` resolves to nothing when there is no IPv4 default gateway, and the branch's own detail line says what that means — *usually the local link is down*. That is a measurement, not a typo, and it keeps its weight. So the branch splits by **what failed to resolve** rather than by the flag alone: a configured address that is blank or malformed is a fact about the input; a placeholder that found no gateway is a fact about the machine. `PingTargets` joins the semantic validation too, where its absence is a gap of its own — the only target family the configuration never checks.

**A required target named wrongly is two claims on one row, and this decision's own pattern says split it** (PR #37, round 7, P1). For a blank or malformed **required** TCP, HTTP, DNS or ping target, the single row — the one that exists, or the one round 4 requires to start existing — carries both *this was typed wrongly*, which the rule says cannot move the verdict, and *a required measurement did not happen*, which has to keep its weight. Leaving both on one weighted row contradicts the rule; following the rule literally would let a run read *Overall Healthy* with a required check that never ran. So the run writes **two** rows: a weightless input notice naming the target and the mistake, in the section where that target belongs, and a weighted row saying the required check did not run. It is the same cut as everywhere else in this inventory, which is why the pattern below is written as a rule and not as an observation.

**Seventeen rounds** (PR #37, rounds 1 to 17). Round 1 found `startup` carrying two families; round 2 found the same true of the other three tags, at P1; round 3 found that even a branch is not always the unit, because the configuration validation folds nine separate findings into one row; round 4 found a branch that is not there at all. The first three are about **granularity** — a verdict attaches to a claim, and each draft named something coarser than the claim: first the label, then the function, then the row. The fourth is the same habit at its limit: a claim about the code that was written from the outside rather than from the branch. The fifth is the mirror of all of them — the rule's own opening clause naming a different axis from the inventory it introduces, so that this time the sentence was wrong and the table was right. The sixth returned to granularity twice over: `step-error` is one tag across every step, and the ping check's no-testable-target branch is one branch across two claims. The seventh found the rule applied to one consumer of the rows and not to the others — the verdict marked, the fingerprint left reading tags and statuses on its own — and one more row carrying two claims, this time a required target that was named wrongly. The eighth caught the error in **both** directions at once: a rule written too wide, which would have suppressed the explanation of a badge that stays on the page, and an inventory written too narrow, which stopped at the branches that exist today and left out the one #51 creates. Same cause, both ways — a statement pitched at a level that does not match the claim it is about. The ninth found the inventory incomplete **by symmetry**: one counter-reset branch was in it from the first draft and its twin, which says the same sentence about a different counter, was not. The tenth was not a reasoning error at all but a formatting one — a paragraph inserted between the table's rows ended the table, so its last row rendered as prose and the inventory looked complete without it — and it belongs beside the others because it reached **the same outcome by a different route**: a branch left weighted because the document failed to say it was weightless. The eleventh returned to the cause: a dropped extra target never reaches the check that would have tested it, so the row it owes is a new branch on the option-parsing path, and the inventory had marked only the notice. The twelfth found the shape once more, this time where two independent measurements share one status — loss and latency on the ping row — so that demoting the row for the coarser of them would have taken the other with it. The thirteenth found the remedy offered for it carrying the defect back in: of the two options written for that row, the weaker one preserved a status the coarse measurement had produced, so the verdict this decision removes would have returned under the name of the one it keeps. The fourteenth was round 9's shape and round 3's subject at once — the configuration validation builds **two** aggregate rows, one from its errors and one from its warnings, and only the first had been split. The fifteenth is the debt of round 10: once the table was declared the whole inventory, every branch settled in a paragraph and never tabled became a branch an implementer would leave weighted, and two were. The sixteenth found the same debt owed by the *previous round's own fix*: broadening one row to required targets and adding one family to the validation left the ping family behind in both places, which is why the rule above now says the four families move together. The seventeenth found the audit that was supposed to end this pointed in one direction only, so a paragraph still prescribing one row where round 7 had prescribed two survived it untouched. That is this decision's own subject turned on itself, seventeen times across seventeen rounds: a status attached at the wrong level, in a document written to stop exactly that. **The pattern is worth carrying into the change itself** — wherever this tool writes one row, one tag or one branch for two different claims, a verdict cannot be attached to it until it is split, and the inventory above is now a list of exactly those splits. It is fixed by naming what makes each row weightless rather than by patching whatever unit the last round broke, which is why the table above names branches and why the paragraphs above name the two families inside the configuration row.

**`adapter-errors` came out of the inventory and appears in no item on this page.** It is the same shape as the retransmission counters — a before/after comparison whose ending value went missing — and it turns a healthy machine's run into *Test Incomplete* exactly as [#38](#38--the-retransmission-counter-read-fails-intermittently-and-takes-the-verdict-and-the-runs-length-with-it) does. A change written for the retransmission counters alone would have left it standing, and nothing would have found it until a walk did.

**What keeps its weight, and why.** `step-error`, where a whole check threw and the thing it was going to measure is simply absent — **except the four quality-collector steps, whose `step-error` rows are in the inventory above** (round 18 found this sentence still saying otherwise, with the carve-out living only in the paragraph after it). `config` and `config-file`: a configuration that could not be loaded changes the thresholds every other row was judged against, which is the definition of a verdict that cannot be trusted rather than of a statistic that is missing. `expected-standard` where the DHCP state could not be read, because that is a comparison against the organisation's own standard that did not happen, and it is IT's to see. Those three were considered and deliberately left alone; moving them needs evidence of its own. **Where this paragraph and the table above differ, the table is the decision.** It is the inventory; prose that restates it can fall out of step with it, as this sentence did, and three rounds of this review were spent on exactly that.

**`step-error` is one tag over every step, and four of those steps are quality collectors** (PR #37, round 6, P1). `Invoke-CheckStep` writes a `step-error` row for any action that throws, so a quality collector that fails **completely** produces two weighted rows and not one: the TCP baseline step throws when neither counter class can be read, and `Compare-TcpCounters` then writes *Complete before-and-after TCP counter data is unavailable*; an adapter snapshot that throws produces a `step-error` and then the missing-baseline row. Demoting only the second of each pair leaves the run *Test Incomplete* exactly as before — this decision failing at the one case it was written for, [#38](#38--the-retransmission-counter-read-fails-intermittently-and-takes-the-verdict-and-the-runs-length-with-it)'s own. **The step carries the weight, not the tag.** `Invoke-CheckStep` already takes a `-Scope` and passes it to the row it writes, so it takes the marking the same way: the four collector steps — the TCP counters before and after, the adapter statistics before and after — declare themselves, and the `step-error` rows they produce inherit it. Every other step's `step-error` keeps its weight untouched.

**The Startup Notice rows are two families under one tag, and the first draft of this inventory missed it** (PR #37, round 1). `Run-AllChecks` builds identically tagged rows from `$script:StartupMessages` and `$script:RunOptionMessages` in one loop, and only the second is a fact about this run's input — it has exactly one writer, the dropped extra TCP target. The first is a fact about the environment the run is in, and it **keeps its weight**: the report directory was not writable and a fallback was used; the graphical interface could not start and console mode was used; and the one that decides this, *This copy is running from inside a compressed folder. Extract the ZIP to a real folder first, or the reports will be written to a temporary location that disappears.* Demoting the tag as a whole would let a run say **Overall Healthy** while the report it is telling the person to send is being written somewhere it will not survive. This was the first of the two rounds that produced the rule above: the dropped-target notices need a tag of their own, or marking where they are added, and the change has to say which.

**The shape.** The marking is opt-in — every row keeps its weight unless it is named — so that a check added later cannot become weightless by default, which is the failure nobody would notice. `Get-SummaryCounts` is not touched: the badges, the totals and the numbers are exactly what they are today. The row objects go into the JSON whole, so the marking appears as one more field on every row — and **that is a contract question this change answers rather than assumes** (PR #37, round 7). `docs/design-v1.2-triage-wizard.md` says a consumer reads only documented fields and that *the field list is frozen in the technical guide*, so the guide is the contract and the guide is what must gain the field — not the design note this paragraph first named. Whether a **newly documented** field is additive under `SchemaVersion: 2` or takes a bump to 3 is the decision to state: additive is defensible on the design note's own words, since a consumer that reads only documented fields is unaffected by one it does not read, and no consumer exists yet — the wizard is not built. Whichever is chosen, the release entry says so and the guide's field list gains the field in the same change, because a frozen list that grows in silence is not frozen.

**The verdict is not the only thing derived from those rows** (PR #37, round 7, P1). `Get-FingerprintSummary` computes its own predicates straight from tags and statuses and consults nothing else: `$qualityIssue` over `ping-target`, `ping-gateway`, `tcp-retransmissions` and `adapter-errors` at `WARN` or `FAIL`, and `$otherProblem` over every other non-`IT` row at `WARN` or `FAIL`. So a demoted below-minimum retransmission row would leave `Get-OverallStatus` saying *Overall Healthy* while the fingerprint key stayed `quality` and the report's own *What to tell IT* section said **Connected, but quality is poor** about the same run — and a demoted input notice would set `$otherProblem`, which suppresses the `quality` key in turn. **Every predicate that draws a conclusion excludes weightless rows — and only those.** `Get-OverallStatus` and the fingerprint's predicates conclude; `Get-SummaryCounts` and `Get-ReportNoticeFlags` describe what is on the page, and they go on reading every row that is on it. Round 8 found the first draft of this sentence saying *every predicate that reads the result set*, which would have taken the `Unable` flag with it — the flag whose only job is to explain an *Unable to Check* badge whenever one remains in the report. A weightless row keeps its badge, so suppressing the explanation would have put back the unexplained badge that v1.2.7 removed as #40, in mirror image: that item was a report explaining a badge nowhere on the page, and this would have been a badge on the page with nothing to explain it. **So: what describes the page follows the rows on the page; what draws a conclusion follows the weights.** The report-stage tests, which assert on fingerprint keys and on both halves of the notice, are where both are proved. The summary notice this decision promises is *additional* to the exclusion and never a substitute for it.

**The condition the owner attached, and it is not optional.** A target that was not measured must leave a row where its result would have been. Today a dropped extra TCP target produces a Startup Notice under *Program Environment* — 「已忽略額外 TCP 目標「8.8.8.8」：格式應為 host:port。」 — and the *TCP Connection* section shows **nothing at all**: the reader looks where the answer belongs and finds absence, which reads as a check nobody configured rather than one that was thrown away. Taking the verdict off that notice without putting a row where the measurement should have been would hide the mistake instead of demoting it. The un-measured target therefore gets its own row, in its own section, saying that it was not measured and why — which is what the `tcp` and `http` rows already do for a target the configuration file got wrong.

**Blocking it where it can be blocked comes first.** v1.2.7 (#45) already refuses a malformed extra TCP target in the IT panel before the run starts, names it with an example value, and does not start; a second press runs without that target, deliberately, so that nobody being guided over the phone is stranded behind a dialog. What is left unblocked is the configuration file and the command line, which is IT's own path — and that is exactly where the row above has to appear.

**The second decision: #51's small-sample branch falls under the same rule.** A retransmission observed in a sample too small to give a rate reports its count and its numbers and does not turn the verdict. **This reverses what the 1.2.5 documents release decided** — that entry states that a warning about a sample too small to give a rate is not proof of a problem, and left it a `WARN`, which on its own turns the verdict to Attention Required — and the release that implements this must say so in its own entry rather than changing the behaviour quietly. The reason for reversing it is that the rule a person can hold in their head is one sentence, and *"a measurement that could not be taken does not move the verdict, but a measurement too small to mean anything does"* is not one sentence.

**What the decision does not touch.** A measured rate keeps its verdict entirely: 251 retransmissions out of 2906 sent segments is still `FAIL`, and measured loss over a sample large enough for the threshold is still what it is. This decision moves the verdict off rows that could not measure or could not mean; it removes no number from any report.

**Acceptance, added to the sentence above:** the un-measured target has a row in the section where its result would have been; the summary names both what could not be taken and what was dropped, and says that neither changes the result; and the manuals' verdict tables carry the rule as one sentence in both languages.

**Status, 2026-09-09 — v1.2.7 changed how the second instance is reached, not whether it exists.** #45 shipped in v1.2.7, so the IT panel now refuses `8.8.8.8` before a run is spent on it. The Startup Notice that turns the verdict is still there — a second press of *Start Test* runs without the target and writes it, and the configuration file and the command line reach it directly — so the instance stands as written above; what changed is that the graphical path now costs a correction rather than a run.

**Status, 2026-09-10 (1.2.8) — implemented, and the decision above is what it implements.** The marking is a `Weightless` switch on `Add-CheckResult`, opt-in one branch at a time, and one more field on every row. `Get-OverallStatus` and **every predicate of `Get-FingerprintSummary`** read the weighted rows only; `Get-SummaryCounts` and `Get-ReportNoticeFlags` read every row on the page, so a weightless row keeps its badge and the explanation of it. `Invoke-CheckStep` carries the marking the way it carries `-Scope`, and the four quality collectors declare it while the two analysis steps beside them do not.

**Two implementation choices the decision left open, both stated here rather than discovered later.** The Startup Notice rows are marked **where they are added** rather than given a tag of their own, so that every tag a document names goes on meaning what it meant — the loop is split, environment notices keep their weight, and the run's own input notices lose it. And the ping syntax rule is consulted **before the address is resolved**, not after resolution found nothing: the first draft guarded only the no-testable-target branch, and `http://example.com` sailed past it into a real ping, reporting *100% loss* — a typo turned into a measurement, which is the opposite of this item.

**The rows the inventory said did not exist yet.** Every configured target that cannot be tested now writes a weightless input notice in the section where its result belonged — TCP and HTTP wrote one only when the target was required, DNS wrote nothing at all, and ping was validated nowhere — and a **required** one adds the weighted row saying the check did not run. `Test-ConfigurationSemantics` gained `PingTargets` and split both aggregate rows: the standards and thresholds keep their weight, while the target entries and the option values that could not be used as written go to two new weightless rows, so the same typo is no longer convicted twice. Each dropped extra target leaves a row in its own section, which is the condition the owner attached and the reason the notice may be demoted at all.

**What a run does now, measured on the reference machine.** An extra TCP target given as `8.8.8.8` and an extra ping target given as `http://example.com`: **Overall Healthy**, with the dropped target named in the TCP section, the ping address refused before a packet was sent, and the summary line *These were not measured or could not be used as given, and none of them changes the result: Extra TCP 8.8.8.8.* A **required** TCP target configured with `Port=0`: **Test Incomplete**, with the input notice and the weighted row saying the required check did not run. The verdict answers what the machine is like, and still says so when a required measurement is missing.

**The contract.** `Weightless` is additive under `SchemaVersion: 2` rather than a bump to 3, on the design note's own rule that a consumer reads only documented fields; the technical guides' field list gains it in the same change, because a frozen list that grows in silence is not frozen.

**This release reverses what 1.2.5 decided about the small sample**, as the decision requires it to say: a retransmission observed in a sample too small to give a rate reported its count and turned the verdict to Attention Required on its own. It now reports the same numbers and leaves the verdict to what was measured.

**Tests.** Report-stage scenario K, 22 assertions in each language (128 → 150 × 2, and 160 × 2 with the row counts each fixture asserts first), every one paired with its opposite — the same row unmarked — so what is proved is the marking and not the fixture; run against the tree before this change, 11 of them fail. Unit gains the ping syntax table and the AST assertions that keep the marking where the decision put it: four collector steps by their progress points, the two analysis steps without it, `Get-OverallStatus` and the fingerprint reading the weights, `Get-SummaryCounts` and `Get-ReportNoticeFlags` not reading them at all (280 → 301 × 2). The chain's own expectations follow the new rows, and `selftest_resultset.ps1` still passes 42 / 42.


**Status, 2026-09-10 — implemented in PR #41, and the review of it ran to twenty-one rounds and forty-one findings, every one accepted.** The decision above survived the implementation unchanged; what the rounds found was that the decision's own boundary — *decided before anything was sent* against *attempted and answered* — is harder to draw than writing it down suggests. ### 41 — Nothing checks that the package's own file table is complete

`tests/doc_facts.ps1` checks one direction: every launcher or program file name a document quotes has to be in the package (check E1). The reverse is unchecked — a file that ships and that no document names goes unnoticed, and the document where that matters is the user manual's section 8, *The files in the package*, which walks the reader through the package file by file. 1.2.4 is the release that shows the risk rather than a hypothetical one: two manuals joined the package and both `README_*.txt` left it, and what kept section 8 right was a person editing four files by hand. Acceptance: a chain check that every file shipped at the package root and in each language folder is named by the user manual's file table, in both languages and both formats, with a named waiver list for what the table deliberately groups rather than enumerates (`docs\`, `tools\`, the `Reports\` folder the tool creates on first run) and a reason recorded for each waiver; a new shipped file that no table names fails the step; the negative self-test covers a missing name and a stale name, as `selftest_docfacts.ps1` does for the checks it already has. — *raised while asking which rows of the user-manual walk could be automated, 2026-09-08; it belongs beside backlog #33's tiers rather than inside them, because it reads the package listing rather than the scripts.*

### 42 — Nothing proves the tool changes nothing

"It changes nothing" is the tool's first promise to the person who runs it — section 1 of the user manual, the first answer of its FAQ, the opening of the IT deployment manual — and no test measures it. The chain runs the script and reads what it wrote; no step compares the machine before the run with the machine after. A regression that started writing a registry value, or a cmdlet call that flipped an adapter setting on the way to reading it, would be caught by a person noticing, or by nobody. The measurement is cheap and deterministic, which is what makes the gap worth closing: take `ipconfig /all`, `route print`, `netsh winhttp show proxy`, the WinINET proxy key under `HKCU`, `netsh advfirewall show allprofiles` and `Get-NetAdapter` before and after a console run, and compare. **The measurement has to subtract the machine, not ignore it.** A before-and-after pair on a live machine is not evidence on its own: a DHCP lease renews, an adapter or a VPN transitions, a route is refreshed, policy pushes a proxy or firewall change — and a step that failed on any difference would be blaming the tool for the weather, while an ignore list wide enough to swallow all of it would swallow the finding too. So the step takes **two pairs**: a control pair with no run between the snapshots, and a treatment pair with the run between them — and the control's job is to say **whether the machine is quiet enough to measure at all**. A control pair that differs at all means the machine is moving on its own right now, and the step reports *not measurable* and stops: on a machine that drifts, no arrangement of snapshots can separate the tool from the weather, and a step that guessed would be worse than one that declines. With a quiet control behind it, a difference in the treatment pair is the step's finding — **and the item stops trying to make it a proof**. Drift that lands inside the treatment interval and persists is indistinguishable, by any arrangement of snapshots, from a change the run made: a lease renewed, a policy pushed a proxy, a VPN rewrote a route. Three review rounds went into trying to design that away and it cannot be designed away, so the item chooses instead: **a treatment-only difference fails the step**, drift included, and the cost of being wrong is a re-run and somebody looking. That trade is only affordable where the step runs — the acceptance machines, quiet by construction, not a CI runner — and it is the right way round for a step whose whole purpose is to catch a tool that started writing to the machine: a false alarm costs minutes, and a missed regression ships. So a candidate is not yet a failure — it makes the step **repeat both pairs**. But the repeat **classifies a candidate; it never absolves one**, and the difference matters for the very regressions this item exists to catch: a run that sets a registry value or disables an adapter changes the machine once, and the repeated pairs then start from the already-changed state and produce no second difference at all. A rule that passed on “it did not repeat” would let exactly that through. So the step keeps the **first snapshot of the session as a baseline** and compares the final state against it as well as pair-wise: a difference that repeats is a change the run makes every time; one that does not repeat but is still there against the baseline was made once and left — **or came from outside during that interval**, which the step reports as the two possibilities it cannot separate rather than choosing between them. The classification is guidance for whoever investigates, not a verdict the step reaches on its own, and nothing is passed silently: every difference is reported with both pairs kept. Acceptance: the two-pair step over `ipconfig /all`, `route print`, both proxies, the firewall profiles and the adapter states, failing on any difference the treatment pair shows once the control pair has come back clean, drift included; a negative self-test in which the harness itself makes a change between the treatment snapshots — a temporary route, removed afterwards — and the step fails as it must; and the step run on the acceptance machines rather than on a CI runner, whose network state is nobody's to reason about. — *raised while asking which rows of the user-manual walk could be automated, 2026-09-08; the walk does it by hand as row W54, which is exactly the work this item would stop repeating.*

### 43 — The tool does not say when the reports are being written into a synced folder

The report is written beside the program, and the person is told where it went; nobody tells them that the folder is being copied to a cloud service as they read it. Measured during the user-manual walk on `win11-enUS`, 2026-09-08: the package was extracted to the Desktop, which Windows 11 backs up to OneDrive by default, so `en-US\Reports\` was a synced folder and every report — computer and user names, MAC and IP addresses, SSID and BSSID, DNS servers, proxy settings, routes, driver versions, profile paths — went to the cloud as it was written. Nothing about that is the tool's doing, which is exactly why the tool is the only thing in a position to say it: it knows the path it resolved, at the moment it resolves it, and the person is standing in front of it. The documents can only warn in advance — the 1.2.5 fix does that in the user manual's sections 1, 5 and 9 and in the IT deployment manual's deployment section — and a warning in advance is read once, months before the run that matters.

What it would take. The report directory is already resolved and already reported (`Initialize-OutputDirectory`, the *Report Directory* field of *Computer and Run Information*, and the Startup Notice row that fires when the usual folder cannot be written). ### 44 — The launcher's own timestamp cannot be read without knowing the machine's regional format

`LauncherError.txt` stamps itself with the shell's `%DATE% %TIME%`. On `DESKTOP-5M1K8VU` during the user-manual walk of 2026-09-08 that produced `Date/time: 08/09/2026 11:09:54.54` — a date the IT department receiving the file cannot resolve without knowing the machine it came from: 8 September, or 9 August. The machine is not exotic, and the reason it shows up there is worth keeping: its **display language is en-US**, which is why the walk ran the en-US package, while its **regional format is en-GB**, so `%DATE%` renders `dd/MM/yyyy`. A zh-TW machine renders `2026/09/08` and has no ambiguity at all. What produces the defect is the mismatch between display language and regional format, which is ordinary in a company and is exactly the shape of machine this project's second acceptance run already used (a zh-TW system with an en-US display).

**Why the obvious fixes are not available.** The file cannot use PowerShell to format a date: one of the reasons it is written is that PowerShell was not found, and another is that a policy refused to run the script. `wmic os get localdatetime` would give an unambiguous stamp, but WMIC is deprecated and absent from recent Windows images. Cutting `%DATE%` into pieces with substring expansion picks different fields on different formats — a defect fixing a defect.

**What is always present is `reg.exe`**, and the pattern the shell used is in `HKCU\Control Panel\International\sShortDate`. So the file does not have to reformat its date; it has to say which format the date is in: `Date/time: 08/09/2026 11:09:54.54 (this computer's short-date pattern: dd/MM/yyyy)`. Three rules, because this code runs on the path where something has already failed and this file is the last thing the person has: the lookup happens **before** the redirection block, never inside it; a lookup that fails omits the parenthesis and never blocks the write (`2>nul`, and a test that the variable was set); and nothing is converted or translated — the file states a fact about the machine it ran on.

**A second layer that costs nothing:** the file's own modified time is the authoritative stamp, and the receiving IT department's own Explorer renders it in the format they read. One sentence in the user manual's section 6 and one in the IT deployment manual say so, and they work for every file already written, including the ones sent before this change ships.

Acceptance: on a machine whose short-date pattern is `dd/MM/yyyy`, the file names the pattern; where the registry value cannot be read, the file is written exactly as it is today; six launchers in two languages, with `tests/launcher_check.ps1` asserting the line where the pattern is available and the unchanged shape where it is not; the `%TEMP%` fallback copy carries the same field. — *found by the user-manual walk on `win11-enUS`, 2026-09-08, where it was first recorded as an observation rather than a finding because the constraint — no PowerShell on this path — made it look unfixable.*

**Status, 2026-09-09 — confirmed in Chinese, and the proposed fix needs one more clause.** The zh-TW walk produced the file on a machine whose short-date pattern is `yyyy/M/d`, and the stamp reads `日期時間：週三 2026/09/09  5:39:17.42`. The date is unambiguous, as this item predicted for such a machine — but `%DATE%` here carries a localised weekday, 週三, which the short-date pattern does not describe. So the parenthesis proposed above is true and incomplete on a zh-TW machine, and the acceptance sentence must not be read as *the stamp matches the pattern*: what the file states is the pattern the date part is in, beside whatever else the shell chose to print. A test that asserts equality would fail on a machine where nothing is wrong. The second layer — the file's own modified time, rendered by the receiving department's Explorer — is untouched by any of this and remains the cheapest half of the fix.

### 47 — The evidence for a failure that writes no report depends on the person retyping what they saw

Raised by the owner at the end of the user-manual walk, and it is the argument that orders several of the items above: *強化收集錯誤狀況的 log 機制，因為發生問題時可能 user 也說不清楚* — the moment a person is least able to describe what happened is exactly the moment the tool stops helping them.

**What is already collected, so that this item does not re-invent it.** A run that reports: the rows, and in the JSON the technical diagnostics of any error, with script location and call stack. A script that refused to start under a restricted language mode: `NetworkHealthCheck_ENVIRONMENT_<time>.txt`, timestamped, naming the mode, the machine, the user, the folder, the PowerShell version, the culture and the operating system. A report that could not be written: the FATAL file with everything found before the failure. A launcher that stopped first: `LauncherError.txt` beside the launcher, or `NetworkHealthCheck_LauncherError.txt` in `%TEMP%` when that folder cannot be written, with the time, the computer, the user, the folder, the script and PowerShell paths, the reason and a suggested action.

**The two gaps are both in the launcher's case, which is the worst one to have them in.** *PowerShell's own message is not captured.* Under an execution policy that refuses the script, the sentence that says why — *…is not digitally signed…*, or whatever the engine printed — goes to the console and nowhere else, and `LauncherError.txt` tells the person to *read the message printed above the error in this window … and send it together with this file*. That instruction asks the person to transcribe the one piece of evidence IT actually needs, at the moment they are least equipped to. *And the file is overwritten.* A person who tries three times sends the third; `NetworkHealthCheck_ENVIRONMENT_<time>.txt` already shows the shape that keeps a history.

**The tension to resolve rather than ignore.** Capturing a child process's output in a batch file means redirecting it from the start, and redirecting it takes it off the screen — which is precisely what `Start-NetworkCheck-Console.cmd` exists to put there. So the answer is not one redirection everywhere: the console launcher must keep its live text and its pause, while the two window launchers print almost nothing to the console in a normal run and can afford to capture. Whatever is chosen, the run that succeeds must look exactly as it looks today.

**Three candidate mechanisms, so that the analysis is not done twice.** *(A) Redirect the error stream only.* `"%PS_EXE%" … -File "%SCRIPT%" 2> "%LOGFILE%"`, keeping the file when it is not empty and deleting it when it is. The engine's refusal — the sentence that says why the script did not run — is an error record and goes to stderr, so it lands in the file; everything the run prints as it goes keeps flowing to the console untouched. **An earlier version of this item proposed redirecting both streams and showing the file afterwards, on the premise that the console shows next to nothing in GUI mode. That premise is false**: `Write-UiLog` calls `Write-Host` unconditionally before it touches the GUI log box (`NetworkHealthCheck.ps1:562`), so the black window behind the tool prints every line of the run in every mode, and a full redirection would blank it — which is precisely what this item's own constraint forbids. Redirecting stderr alone costs nothing and breaks nothing, which is what makes it the first thing to try. **Keeping the file only when there is something in it matters for a second reason**: a file that appears beside the launcher after every successful run is a new shipped-looking artefact in the package folder, which the user manual's section 8 table would have to describe and #41's reverse check would have to waive. *(B) A tee through PowerShell*, `powershell -NoProfile -Command "& '%PS_EXE%' -File '%SCRIPT%' 2>&1 | Tee-Object -FilePath '%LOGFILE%'; exit $LASTEXITCODE"`, is the only way to keep the text live **and** capture it. An execution policy governs scripts and configuration files, not `-Command`, so this layer usually still runs in the `AllSigned` case — which is the case worth capturing — but it is the more fragile route: the exit code has to be carried back by hand, a restricted language mode can stop the wrapper too, and if PowerShell is missing altogether there is nothing to wrap. *(C) `Start-Transcript` inside the script* covers only the runs where the script starts, which is exactly the half that already writes its own evidence; useful as an addition, useless as the answer.

So the shape that fits the constraints is (A) for **all six launchers**, because redirecting stderr alone takes nothing off the screen and there is therefore no trade to make — the console launcher keeps its live text and its pause exactly as the manual promises them. (B) is what to reach for only if a failure turns out to write its explanation to stdout instead, where stderr redirection cannot see it. The log file follows `LauncherError.txt`'s rules — beside the launcher, else `%TEMP%` — and carries a timestamp in its name so that separate attempts do not overwrite each other, which is the same defect this item already names in the error report itself.

It composes with the items around it rather than replacing them: #46 names the file to send, this one makes sure the file has the evidence in it, #44 makes its timestamp readable by whoever receives it, and #37 is the case beyond the reach of all three — when the launcher itself is refused, nothing of ours runs at all.

Acceptance: a refusal that PowerShell explains on the console leaves that explanation in a file, beside the launcher or in `%TEMP%` under the same rules as the error report; **and `LauncherError.txt` itself stops overwriting**, which the redirected log does not fix on its own — the failures that never reach PowerShell, a missing program file or a missing PowerShell, produce no redirected output at all and today rewrite the same fixed name on every attempt, so the error report needs the timestamp as much as the log does; a successful run's console output and the console launcher's live text and pause are unchanged, proved by `tests/launcher_check.ps1` over the six launchers; the user manual's section 6 rows say *send these files* instead of asking the reader to copy text off the screen. — *raised by the owner during the user-manual walk, 2026-09-08.*

### 50 — The zh-TW console launcher's last line reaches the screen as a command

### 51 — A quality verdict can rest on a single packet, because the threshold is finer than the sample

The two chain runs of 2026-09-09 each failed one case on this project's own reference machine, and a third came out of an acceptance run the same hour. All three are quality rows, and the numbers are the item:

| Where | Sample | Events | Result |
|---|---|---|---|
| `gui zh-TW IT` | 125 s, **2906** sent segments | 251 retransmissions | 8.637 % → `FAIL` |
| acceptance, `-SampleSeconds 2` | 2 s, **84** sent segments | **2** retransmissions | 2.381 % → `WARN` |
| `package en-US IT` | **4** pings | **1** lost | 25 % → `WARN` (the public-IP target is optional) |

The first is not a sampling artefact: 251 events out of 2906 is a link that was really retransmitting, and a longer window would have said the same thing. **The other two hang on one packet each**, and that is what this item is about.

**The arithmetic, which is the defect stated exactly.** *Retransmissions:* `MinimumTcpSegmentsForRate` is 50 and `TcpRetransmissionWarningPercent` is 2, so at the smallest sample the tool will rate, **one retransmission is 2.0 % — the warning threshold itself**. The guard that exists to stop the tool rating a sample too small permits precisely the least informative case it could. At the 84 segments measured above, one retransmission is 1.19 % and two are 2.38 %: the verdict changed on a single packet. For one retransmission to be worth half the warning threshold the sample needs ≥ 100 segments; a quarter, ≥ 200. *Packet loss:* `PingCount` is 4, so the loss figure can only be 0, 25, 50, 75 or 100 %, against thresholds of 5 % (warning) and 20 % (critical). **One lost packet out of four is already past the critical threshold**, and the tool has no way to express "a little loss" at that count. One lost packet is a warning rather than critical from six pings, and stops being a warning at all only from twenty-one.

**What the project already says about this, and does not do.** The repository README's principles include *"A failed ping is a suspect, not a conviction — corroborate before acting"*, and the user manual tells the person to run the tool again while the problem is happening. The quality rows convict on one sample.

**Four candidate changes, cheapest first, so that whoever takes this is choosing rather than inventing.** *(1) A count floor on both classifications.* Requiring the rate **and** a small number of retransmissions (five, say) turns the 2-of-84 case into `INFO` with its numbers, and leaves 251-of-2906 exactly as it is. **It has to be both, and `TcpRetransmissionCriticalCount` is not already that floor** (PR #36, round 5): the classification reads `if ($rate -ge $criticalPercent -or ($retransDelta -ge $criticalCount -and $rate -ge $warningPercent))`, so the count is an *alternative* trigger for `FAIL`, never a condition of it — 3 retransmissions in the smallest rated sample of 50 is 6 %, which fails on the rate alone. A floor added only to the warning branch would leave that route open, and the same coarse sample would convict harder. *(2) Tie `MinimumTcpSegmentsForRate` to the threshold instead of fixing it at 50* — one retransmission out of `sent` is `100 / sent` per cent, so making it worth half the warning threshold takes `sent ≥ 200 / warningPercent`, which is **100 segments** at the shipped 2 %; a quarter takes `400 / warningPercent`, or 200. The formula is written out because the value 50 in the code is exactly `100 / warningPercent`, the point where one retransmission **is** the threshold — an off-by-one-factor away from the rule that would fix it, and the same slip was made and caught in this item's own first draft (PR #36, round 1). **And this candidate is not a change on its own** (round 2): below the minimum, `Compare-TcpCounters` already gives any retransmission at all a `WARN` — *The traffic sample is small, but N retransmission(s) were observed* — so raising the minimum from 50 to 100 would route the 2-of-84 case into that branch and leave it a warning. Whoever takes this must decide what a small sample carrying a retransmission means. That branch is deliberate: the 1.2.5 documents release wrote that a warning about a sample too small to give a rate is not proof of a problem, and left it as `WARN`, which on its own turns the verdict to Attention Required. The decision belongs beside [#39](#39--a-measurement-that-could-not-be-taken-outranks-a-measurement-that-failed)'s, and it lands in section 9 of the user manuals, which quotes all three small-sample messages. *(3) The same for loss.* **Raising `PingCount` alone does not do it** (round 3): with the shipped 5 % warning threshold one loss out of ten is 10 %, and `Test-PingTargets` classifies at the threshold whether or not the target is required, so the count would have to reach **21** before a single lost packet stopped being a warning — 21 timeouts against an unreachable target, inside a run the manual promises will take about ten seconds. So this candidate is really the rule *a single lost packet cannot warn below N packets*, with a count chosen for the measurement rather than for the threshold; the cost is asymmetric and belongs in the decision, because against a reachable target ten pings cost milliseconds and against a dead one they cost ten timeouts. *(4) Corroborate before concluding:* when a quality row would cross a threshold, take one more sample and require the crossing twice. It costs time only when something looked wrong, which is the case where time is worth spending, and it is what the manual already asks the person to do by hand.

**All three of the first candidates were caught prescribing something that does not achieve what this item asks** (PR #36, rounds 1 to 3): a minimum-sample formula that evaluated to the value already in the code, a higher minimum that would have routed the measured case into a branch that warns anyway, and a higher ping count that still warns on one loss. That is this item's own thesis turned on itself — a number in this area looks reasonable until the arithmetic is written out beside the code that consumes it — and it is the reason the candidates carry their numbers here rather than a sentence each.

**What this is not.** It is not [#38](#38--the-retransmission-counter-read-fails-intermittently-and-takes-the-verdict-and-the-runs-length-with-it), which is the counter failing to be read at all, and not [#39](#39--a-measurement-that-could-not-be-taken-outranks-a-measurement-that-failed), which is about how the rows that exist are weighed against each other. This one is a row that was measured, and measured on too small a sample for the threshold applied to it. It composes with both: #39's *Test Incomplete* and this item's false warning are the two ways a healthy machine ends up telling its owner to send a report to IT.

**What the evidence does and does not support.** Three cases, one machine, one day; the 8.637 % and the 25 % may well be real network events, and the tool reporting them is the tool working. What is not defensible is that a single packet can produce the same sentence.

Acceptance: a run whose sample is too coarse for the threshold applied to it reports the numbers without changing the verdict — in **both** branches, the rated one and the below-minimum one, since today the second makes any retransmission in a small sample a warning — proved by a test that feeds the counter comparison the cases its classification can actually take apart — one retransmission and several in a small sample, **and a below-floor sample whose rate alone fails today**, three retransmissions in fifty segments being 6 %, which must come out of the change carrying no verdict — asserting that the outcomes differ in status and not only in wording, since a change that guards the warning branch alone satisfies the first two cases and leaves the third (PR #36, round 6); the thresholds and any new floor live in the configuration file with the others and are validated with them; the **loss half is implemented and covered too** — a single lost reply at the default ping count no longer produces a warning on its own, proved by a test that feeds the measurement one loss at that count and at a count large enough for the threshold, because the ping row is half of what this item measured and an acceptance that asked only for a decision there would let #51 close with that half shipped (PR #36, round 4); and the manuals' description of the quality rows matches what ships. Whichever of the four is chosen, the row must keep saying what it measured: this item removes a verdict, never a number. — *raised by the owner on 2026-09-09, reading the two chain runs of the 1.2.7 release, each of which failed one case on this machine's own network.*

**Status, 2026-09-09 — the prescription changes shape: adaptive sampling, not a larger fixed count.** Raised by the owner asking why the tool does not simply test more times, and why the panel's ping count stops at 20. Those are two questions with different answers, and the second one is embarrassing.

**The cap of 20 is not a limit and has no recorded reason.** It is the spinner's default maximum in the IT panel — `$controls["PingCount"].Maximum = [math]::Max(20, $options.PingCount)`, whose own comment says that a configured value above the default range widens it instead of being clamped (v1.2.1) — and nothing beneath it enforces anything: the configuration validation checks only that the value is a whole number greater than zero, with **no upper bound**; the command-line `-PingCount` is a bare `[int]` with no `ValidateRange`; and `Test-PingTargets` clamps the lower bound alone, `[math]::Max(1, …)`. A configuration file that says 50, or `-PingCount 50`, already runs today, and the panel widens itself to show it. So the number that looked like a limit is a spinner default, and no document in the repository or the package says why it is 20.

**Why a larger fixed count does not fix this, part one: the cost is not in the count, it is in the timeouts.** `Invoke-PingMeasurement` sends sequentially with `PingTimeoutMs` 1200 and, unlike `ping.exe`, no delay between echoes. Per ping target, with the shipped settings:

| Per ping target | 4 pings (shipped) | 21 pings |
|---|---|---|
| every reply arrives | ≈ 0.1 s | ≈ 0.5 s |
| one reply lost | — | ≈ 1.6 s |
| nothing answers | 4.8 s | **25.2 s** |

Two ping targets ship, so the last row doubles. **The expensive case is the target that answers nothing — which is the case that needs the fewest pings**, because 100 % loss is conclusive at four and no larger count makes it more so. Raising the count uniformly pays the whole cost in exactly the situation where the extra samples buy nothing.

**Part two, and it matters more: 21 back-to-back pings measure half a second of the network.** With no delay between echoes the whole burst lands inside a fraction of a second, so a larger count buys more samples *of one instant* rather than a longer view. What a person is usually trying to catch — a connection that is intermittently unstable — needs **span**, not count. The retransmission window has the mirror of the same problem: extending it is dead time, since `Wait-ForMinimumTcpSample` sleeps, and the counter is system-wide, so a longer window buys more segments that still cannot be attributed to anything ([#52](#52--the-retransmission-statistic-cannot-say-whose-traffic-it-measured)).

**The shape that follows, which is candidate (4) made specific.** *Ping:* start at the configured count; if every reply arrives, stop, so that a healthy run does not get slower; if some are lost but not all, continue to a count at which one packet can no longer decide the classification, and **spread those over the run rather than sending them back to back**, since the sample window already spans the whole run and the extra span therefore costs no wall-clock time; and if nothing answers at all, do not extend — 100 % loss is conclusive and further timeouts buy nothing. (This clause first promised an early stop that would be *faster than today*. It would not be, and the two halves contradicted each other: the base sample always completes, which is what makes `PingCount` a starting count, so an unreachable target costs exactly what it costs today. The saving is against a **raised fixed count**, never against the shipped one — PR #37, round 6.) *Retransmissions:* extend the window once when the sample is below the floor **and** a retransmission was observed, which is the ambiguous case and only that; an idle machine with no retransmissions takes the existing INFO branch and is not extended.

**What it costs, stated so that the choice is visible.** The run's length stops being a fixed number — the manuals already describe it that way (*about ten seconds … up to a minute or so … because every test waits for its time limit before giving up*), so what they need is their numbers checked rather than a new paragraph. `PingCount` stops being the number of pings and becomes the starting number, so a companion ceiling joins it in the configuration file and in its validation, and the panel's two spinners have to say which is which. And the change is larger than the count floor of candidate (1): it reaches `Invoke-PingMeasurement`, the classification, the sample window and the configuration surface, where the floor reached two thresholds.

**What it does not change.** 251 retransmissions out of 2906 sent segments is still `FAIL`. The verdict decision recorded under [#39](#39--a-measurement-that-could-not-be-taken-outranks-a-measurement-that-failed) is what handles the samples that are still too small after the extension, because an idle machine that sends twelve segments in a whole run cannot be sampled into significance by any amount of waiting. The two compose: adaptive sampling makes the small-sample branch rarer, and #39's rule makes what is left of it harmless.

**The acceptance sentence above gains these clauses:** a run on a healthy machine is no slower than today's, measured on the reference machine rather than argued; a run against a target that answers nothing ends no later than today's, and far sooner than a raised fixed count would have made it; a run that loses a single packet either reports a rate computed over a sample large enough for the threshold or reports the count with no verdict, never a 25 % that rests on one packet; the extension fires only in the ambiguous case, proved by a test that feeds the classification a small sample carrying a retransmission and a small sample without one; and whichever counts ship, the panel's spinner maxima and the configuration's validated range say the same thing as the code that consumes them — which is what this Status line found was not true of 20.

### 52 — The retransmission statistic cannot say whose traffic it measured

`Compare-TcpCounters` reads `Win32_PerfRawData_Tcpip_TCPv4` and `Win32_PerfRawData_Tcpip_TCPv6`, which are **system-wide** cumulative counters, and the row's own Details line says so in both languages: *This is a system-wide statistic for the entire computer during the test, not for a single application.* The sample window wraps the whole run — the baseline is taken at progress 10, the ending value at progress 89, and `Wait-ForMinimumTcpSample` pads the gap to at least `RetransmissionSampleSeconds` — so what the row reports is every TCP segment the computer sent during the run, to every destination, over every interface: the tool's own checks, a mail client, a background update, a remote session, all of it.

**What that costs.** On a large sample the figure is still worth having: 251 retransmissions out of 2906 sent segments is a link that was really retransmitting, whoever's traffic it was. On a small one the reader cannot tell whether two retransmissions belonged to the network being diagnosed or to a background process talking to a server on another continent — and [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample) shows that the small sample is the ordinary case on an idle machine with the shipped eight-second window. This project has the sharpest instance of it in its own record: the 125-second IT-window samples of the v1.2.3 validation had measured the traffic of the session that was driving the tool. The counter cannot separate the diagnosis from the diagnostician.

**Why this is not #51.** #51 is about a threshold finer than the sample, and its answer is a bigger or better-timed sample. This item is about what the sample contains, and more of it does not help: a longer window over a system-wide counter is more unattributable traffic, not less. The fix is a different measurement rather than a different number — a connection the tool opens itself to a known target, whose retries and round-trip behaviour it can measure and attribute, reported as what it is: a figure about that target, over that interface, at that moment. It does not replace the system-wide counter, which is worth keeping as the *what was this computer doing* statistic; it stands beside it, and each says which of the two it is.

Acceptance: a run produces at least one retransmission-or-retry figure that names the target it was measured against and states its sample size; the system-wide row keeps every number it prints today and says plainly that it is system-wide, so that the two can never be read as one; the report and the manuals distinguish them in a sentence each; and the new measurement's cost is stated in the run's own time budget the way the ping and TCP checks' costs are. — *raised by the owner on 2026-09-09, out of [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample)'s discussion of why a small sample is worth so little.*

### 54 — The host-name predicate's character space is closed by example rather than by rule

### 56 — The shipped thresholds have no recorded basis, and the standards that exist do not supply one

**Twelve numbers decide what the quality rows say, and nothing in this repository records where any of them came from.** The whole `Thresholds` block: `PacketLossWarningPercent` 5, `PacketLossCriticalPercent` 20, `LatencyWarningMs` 100, `LatencyCriticalMs` 250, `TcpRetransmissionWarningPercent` 2, `TcpRetransmissionCriticalPercent` 5, `TcpRetransmissionCriticalCount` 50, `MinimumTcpSegmentsForRate` 50, `AdapterErrorWarningDelta` 1, `AdapterErrorCriticalDelta` 10, `AdapterDiscardWarningDelta` 1 and `AdapterDiscardCriticalDelta` 100. Every one of them classifies a row carrying one of the four quality tags `Get-FingerprintSummary` reads, and every one of them appears fully formed in the initial commit `99f8275`, whose message never mentions thresholds — confirmed by `git log -S` on each of the twelve names. Every later commit touching any of them changed type handling alone: culture-invariant parsing, whole-number and Int32 rules.

**The search that found nothing, so that nobody repeats it.** On 2026-09-10, for the retransmission and packet-loss values: `healthcheck/VALIDATION.md`, `docs/`, `sop/`, every manual and guide copy in both languages, the two scripts' comments, `tests/`, and `git log -S` per name. Extended the same day to the latency and adapter values when this item was widened, with the same result for all twelve: the only prose about any of them is the IT deployment manual's threshold table, which states the **rule** each value feeds (*on the average of the replies that came back*, *receive plus send errors added during the sample, per adapter*) under the heading *the defaults are generic starting points*. A rule is not a basis. There is no RFC, vendor guideline, measurement, calibration run or owner decision behind any of the twelve.

**Ten are magnitude choices; two are policies that explain themselves.** `AdapterErrorWarningDelta` and `AdapterDiscardWarningDelta` are both 1, which is not a calibrated magnitude but the policy *any at all is worth showing* — defensible on its face, and it needs recording as a decision rather than calibrating. The other ten are magnitudes, and each of them is a number somebody chose: 5 and 20 per cent of lost replies, 100 and 250 milliseconds, 2 and 5 per cent of segments, 50 segments twice, 10 errors and 100 discards.

**One of the ten is a quantity mismatch as well as a missing basis**, which is [#57](#57--the-retransmission-rates-denominator-is-not-the-quantity-any-published-figure-refers-to) showing up in a different row. `LatencyWarningMs` and `LatencyCriticalMs` are applied to the **average round-trip time** of the ICMP replies that came back, while **two** published figures are in the neighbourhood and neither is that quantity. *Y.1541's own Table 1* is the closer of the two, and the first draft of this paragraph left it out (PR #43, round 4): it bounds the **mean one-way IP transfer delay** at 100 ms for classes 0 and 2, 400 ms for 1 and 3 and 1 s for 4, and bounds the delay variation at 50 ms for classes 0 and 1. Converting a one-way bound to a round trip needs only the factor of two a symmetric path implies, with no endpoint allowance at all, so unlike the other figure the arithmetic here is possible. What forbids adopting the number is the scope the table states for itself: a public IP network between the measurement points that delimit it, evaluated over a suggested minute — neither a LAN nor an eight-second burst of four echoes. *G.114's 150 ms*, which the Cisco guidance below cites, is further away still, being **one-way mouth-to-ear** delay: it includes packetization, codec and jitter-buffer time at both ends, so turning it into a network round-trip budget needs an explicit allowance for those endpoint delays, and nobody in this project has made one. **The first draft of this paragraph made that conversion backwards** and concluded that 250 ms of round trip was stricter than the voice budget (PR #43, round 2): endpoint delays *consume* the 150 ms rather than adding to it, so the network's share is under 150 ms one-way and its round trip under 300 ms, not over — which leaves the comparison able to fall either way, on an allocation that does not exist. That is this item's own thesis biting the hand that wrote it, and it is left on the record for the same reason [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample) keeps its three rejected candidates: a number in this area looks reasonable until the arithmetic is written out beside it. Neither threshold was derived from either figure: `G.114` appears nowhere in this repository, `Y.1541` nowhere in it outside this item, and the only `150 ms` anywhere in it is an example inside this page's own #39 discussion.

**What the shipped documents say about them is only ever a disclaimer**, and none of the three singles out a value: the IT deployment manual's section 3.5 (*the defaults are generic starting points*), the technical guide's limitation 9 (*thresholds require calibration; defaults are not guaranteed for Wi-Fi, VPN, satellite, international WAN, data center or high-throughput servers*), and the field manual (*thresholds are generic until someone sets them*). So the documents are not wrong. What is missing is a sentence saying that these particular numbers were chosen without a basis, because a reader who sees *2 % warning* in a threshold table may reasonably infer that 2 % came from somewhere.

**And none of the documents that would be expected to supply one does, which is the part worth writing down once.** That is a claim about the documents examined rather than a proof that no such standard exists anywhere: the table below **is** the examined set, and anyone who finds a published general threshold should add it to that table before adding it to a threshold. The published documents divide into two kinds, and neither kind contains a general rule of the form *above X % the network is faulty*. Verified against their sources on 2026-09-10:

| Source | What it actually defines | Verified against |
|---|---|---|
| RFC 7680, *A One-Way Loss Metric for IP Performance Metrics (IPPM)*, Internet Standard, STD 82, January 2016 (obsoletes RFC 2680) | How to measure one-way packet loss, including how long to wait before a packet counts as lost | `rfc-editor.org/info/rfc7680` |
| RFC 6534, *Loss Episode Metrics for IP Performance Metrics (IPPM)*, Standards Track, May 2012 | Loss **episode** frequency and average duration, on the stated ground that the impact of loss is sensitive not just to the average rate but to how losses are distributed | `rfc-editor.org/info/rfc6534` |

**Two things read out of Y.1541's own Table 1 sharpen this item more than the 10–3 figure does.** Its General notes require that *an evaluation interval of 1 minute is suggested for IPTD, IPDV and IPLR and, in all cases, the interval must be recorded with the observed value* — a standards body saying that a loss percentage without its interval is not a comparable figure, which is [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample)'s thesis stated by someone else. And its NOTE 4 gives the 10–3 a stated basis: *partly based on studies showing that high quality voice applications and voice codecs will be essentially unaffected by a 10–3 IPLR*. The one standards number in the table carries its reason and its interval. Ours carry neither. Note also its scope, which is why it cannot simply be adopted: the objectives apply to **public IP networks, between the measurement points that delimit the end-to-end IP network**, and say nothing about a LAN or an air interface.

**The decision, which is what this item is.** Three roads, and the cost of each is that it forecloses the others until someone revisits it. *(1) State them for what they are* — operational defaults chosen without an external basis, configurable, and named as such in the threshold tables rather than only in a general disclaimer. Cheapest, and it makes every later change honest. *(2) Calibrate* — measure this fleet and set the numbers from what it does, which is what the technical guide's limitation 9 already tells the deployer to do and which no run in this project has ever done. *(3) Keep them and record that keeping them was a decision*, with the date and the reason, so that the numbers stop being unexplained even though they do not change. What must not happen is a fourth road: replacing 2 and 5 with someone else's suggested grading and inheriting the same silence about where those came from.

**A discipline this item generalizes rather than introduces** (PR #43, self-audit after round 5, where the first draft claimed the repository had never cited an external document). Every citation carries the source it was verified against and the date it was checked, and **an unverified citation may not be the basis of any threshold, any document sentence or any test**. The practice already exists in one place: [`application-control.md`](application-control.md) cites Microsoft's *Requirements to use AppLocker* with that page's own date beside the KB it names, because a vendor page that moves would otherwise leave a claim with nothing behind it. What is new here is applying it to the numbers a verdict rests on. The reason is on record: the one citation drafted here from memory rather than from its source was doubted for the wrong reason — RFC 6534 was suspected of not being about loss episodes, and it is exactly that, Standards Track, which the fetch settled in one call. Doubt is cheap and checking is cheaper than either being wrong or hedging in a shipped document.

Acceptance: the decision taken and recorded, whichever of the three it is, with the date and the reason; all twelve values named individually wherever a document presents them as a table, with the two that are policies distinguished from the ten that are magnitudes, so that no reader has to infer a provenance the repository does not have; what the standards do and do not supply stated once, in one place, with every citation carrying its source and check date; and the technical guides' limitation 9 pointing at that place instead of leaving *calibration* as advice with no explanation of why it is necessary. Not in scope: changing any value, which is road 2's work and needs measurements this project has not made. — *raised by the owner asking on 2026-09-10 what the basis for the 2 % retransmission warning is, and by the answer being that there is none; the standards were verified against their sources the same day, after an outside summary of them was offered and checked.*

**Decision, 2026-09-10 — road (1): the twelve are operational defaults, and every document that presents them says so beside the value.** Road (3) records the decision where only this page can see it and leaves the shipped threshold tables reading like engineering values, which is the appearance this item objects to. Road (2) is the better long answer and cannot be taken now: it needs fleet measurements no run in this project has made, so choosing it would turn this item into one that waits on machines while the tables stay unexplained until they arrive. And road (1) forecloses road (2) less than the paragraph above suggests — a later calibration becomes a documented improvement to a value already labelled as chosen without an external basis, rather than a silent change to one that looked authoritative. What ships with it is the split this item found: `AdapterErrorWarningDelta` and `AdapterDiscardWarningDelta` are the policy *any at all is worth showing*, named as a policy, and the other ten are magnitudes with nothing behind them, named per value rather than under a table-wide disclaimer.

**What the decision does not do.** It changes no number: all twelve ship exactly as they are today, and a deployer who has calibrated their own values is unaffected. It also does not close the item. The acceptance asks that all twelve be named individually *wherever a document presents them as a table*, which is a change to the packaged IT deployment manual and both technical guides in two languages; this page carries no version and those documents do, so the edit rides with the next documents change — the same one [#57](#57--the-retransmission-rates-denominator-is-not-the-quantity-any-published-figure-refers-to)'s and [#58](#58--a-required-checks-failure-is-evidence-about-the-gateways-own-stack-not-necessarily-about-the-path)'s wording needs — and the item closes there rather than here. — *decided by the owner on 2026-09-10.*

### 57 — The retransmission rate's denominator is not the quantity any published figure refers to

`Compare-TcpCounters` divides the delta of `SegmentsRetransmittedPersec` by the delta of `SegmentsSentPersec`, both from `Win32_PerfRawData_Tcpip_TCPv4` and `TCPv6`. Two of the four things a published retransmission rate specifies are satisfied: the figure is one **direction** (segments sent, outbound only) and numerator and denominator share one **window**. The other two are not. Every **connection** on the machine is aggregated, which is [#52](#52--the-retransmission-statistic-cannot-say-whose-traffic-it-measured). And the denominator counts **every segment sent, pure acknowledgements included**, because an acknowledgement is a segment.

**That last one has a direction, so it is not merely a definitional quibble.** On a machine that is mostly receiving — browsing, a download, a Teams call — outbound segments are dominated by pure acknowledgements, which inflates the denominator and makes the printed percentage **smaller** than a data-segment rate over the same traffic. A tool reading 2 % is therefore reporting something whose data-segment equivalent is higher, and the 2 % threshold is being applied as though the two were the same number. [RFC 4898](#56--the-shipped-thresholds-have-no-recorded-basis-and-the-standards-that-exist-do-not-supply-one) keeps them apart on purpose — `tcpEStatsPerfSegsOut` against `tcpEStatsPerfDataSegsOut`, *segments sent containing a positive length data segment* — and RFC 6349's TCP Efficiency is a third quantity again, counted in bytes with the retransmitted bytes inside the denominator. The tool's figure is a fourth. The IT deployment manual's threshold table is more careful here than this item's first draft allowed — it says *retransmitted ÷ sent segments over the sample, computer-wide, for TCPv4 and TCPv6 separately*, which is literally what the code does, so the aggregation is disclosed. What no document says is that *sent segments* includes the acknowledgements, or that the resulting percentage is therefore not comparable with a published retransmission rate.

**What this source cannot supply, and the choice that leaves.** The counter class exposes only `Segments/sec`, `Segments Received/sec`, `Segments Sent/sec` and `Segments Retransmitted/sec` (confirmed on the reference machine through `Get-Counter -ListSet TCPv4`), so **there is no data-segment counter to divide by**, and `Get-NetTCPConnection` carries endpoints, state and `OwningProcess` and **not one counter field**, verified there too. The per-connection counters that would give a data-segment rate are RFC 4898's, reached on Windows through TCP ESTATS in the Win32 API. **That is P/Invoke, which this project decides about rather than a wall it hits** — the same decision [#61](#61--on-a-wi-fi-only-machine-nothing-distinguishes-the-air-from-what-is-behind-the-ap) carries for the wireless retry counters, and this paragraph's first draft called it impossible while #61, two items later in the same change, called it a trade-off (PR #43, round 5). `Add-Type` runs in an ordinary FullLanguage session — the tool's own WinForms load is one — and is refused in a constrained language mode, so such a branch would be present on most machines and absent under the strictest application control.

**But `Add-Type` working is not what makes the measurement available, and the scoped round 6 established what does.** Extended statistics on a TCP connection are **disabled by default**, and `SetPerTcpConnectionEStats`, the call that enables them, *can only be called by a user logged on as a member of the Administrators group* — a standard user receives `ERROR_ACCESS_DENIED`, and a member of that group without a `requestedExecutionLevel` of `requireAdministrator` needs an elevated shell (Microsoft's `iphlpapi` documentation, verified 2026-09-10). That collides with the two properties this tool leads with. The repository `README.md` promises *no install, no admin rights* in the same sentence as *one double-click*, and enabling collection is a **write to the machine** rather than a read of it. Microsoft's own guidance makes that write persistent: *we recommend that your application refrains from disabling statistics on connections*, because since Windows 10 version 1709 some counters do not reset when statistics are disabled and re-enabled, and a second application monitoring the same connection can be confused by it. So the tool could not tidy up after itself — which is squarely what [#42](#42--nothing-proves-the-tool-changes-nothing) exists to prove it never has to.

**So the item has two ways to close, and they are not balanced.** Recording the decision not to compute a data-segment rate, and saying plainly which number is printed instead, costs nothing and contradicts nothing. Taking the Win32 path means either abandoning *no admin rights* for one measurement, or shipping a branch that is dead for exactly the users this tool was written for — and it means writing state to the machine that does not undo itself. Either is a legitimate answer as long as it is the recorded one. What the item forbids is presenting today's approximation as the only thing possible, which is what it did until round 5.

**One sub-question is open and must be settled before any document sentence is written.** Whether `Segments Sent` excludes segments containing only retransmitted bytes, as the TCP MIB's `tcpOutSegs` does. If it does, the denominator excludes the numerator's segments, which is the opposite of RFC 6349's convention and changes the arithmetic at high rates. It could not be read on the reference machine: the English `Perflib\009` key does not exist on a zh-TW installation, `Perflib\0404` carries no `Counter` or `Help` values, and `Get-Counter -ListSet` exposes a description for the counter set only. Confirm against Microsoft's counter documentation, and record the answer here.

Acceptance: **the sub-question above answered from Microsoft's documentation and recorded first**, because the sentence the row and the manuals have to carry depends on that answer and this item must not prescribe it (PR #43, round 3) — what is established today is that acknowledgements are counted and that every connection is aggregated; whether segments carrying only retransmitted bytes sit inside the denominator is not, and an acceptance demanding the words *all segments* could be met only by publishing a sentence that may be false; then the row and both manuals stating what the printed percentage actually divides by, in one sentence each, in both languages, that sentence following the documented semantics rather than this paragraph; the figure no longer named in a way that invites comparison with a published retransmission rate, whichever wording that takes; a unit test pinning the arithmetic against the definition the row states, so the sentence and the computation cannot drift apart; and, if the Win32 path is weighed at all, the decision naming what it actually costs — the Administrators group, the collection that is off until something turns it on, and the turning-on that Microsoft advises against undoing — so that it is refused or accepted on those terms rather than on whether `Add-Type` runs. Not in scope: per-target attribution, which is #52. Computing a data-segment rate is **in** scope as one of the two ways above, and leaves it only if the decision recorded is to decline the Win32 path — this sentence said the rate could not be computed at all until the self-audit after round 5, two paragraphs after that round had made it an option. — *raised on 2026-09-10 while checking an outside summary of the measurement standards against the code; RFC 4898 and RFC 6349 were verified against their sources the same day.*

**Status, 2026-09-10 — the sub-question is answered: `Segments Sent` does exclude segments containing only retransmitted bytes, and the reference machine could read it after all.** Two sources agree, and the first of them corrects the paragraph above. *The operating system's own counter help text, read on the reference machine:* `System.Diagnostics.PerformanceCounterCategory` exposes each counter's `CounterHelp`, and returned it in English here — a path the paragraph above did not try, having gone to the `Perflib` registry keys and to `Get-Counter -ListSet`, neither of which carries it. The keys are as that paragraph recorded, re-checked on 2026-09-10: `Perflib` holds `0404` and `_V2Providers` and no `009`, and `0404` carries no `Counter` value, so the strings this API returns are not being read from there. **What the machine is, stated because the paragraph above calls it a zh-TW installation and that is half of it:** its UI culture is `en-US` while its system locale and its user language list are zh-Hant-TW. The English is therefore the machine's own display language, and nothing here says what a zh-TW display language would return. It gives *Segments Sent/sec* as the rate at which segments are sent, including those on current connections, but "excluding those containing only retransmitted bytes", and *Segments Retransmitted/sec* as segments transmitted "containing one or more previously transmitted bytes". *Microsoft's published counter documentation:* the archived *TCP Object* reference (Windows Server 2003 technical reference, page dated 2009-10-08, last updated 2021-11-12, checked 2026-09-10) states the same exclusion for Segments Sent/sec, adds that it is a subset of Segments/sec, and gives Segments/sec as the sum of Segments Received/sec and Segments Sent/sec.

**Three consequences, and the first is a correction to this item's own wording.** *(a)* The answer is **not** that the denominator excludes the numerator. It excludes segments containing *only* retransmitted bytes, while the numerator counts every segment containing *one or more* previously transmitted bytes — so a segment carrying new bytes alongside retransmitted ones falls in both, and only a pure retransmission is in the numerator and out of the denominator. The sentence above, written before the answer was known, would have overstated it, and a document sentence built on it would have been wrong in the case where a sender repacketises. *(b)* `Segments/sec` is not an alternative denominator, since it is Received plus Sent and therefore counts the other direction as well. *(c)* Two biases now sit in the printed percentage and they point opposite ways — excluding pure retransmissions makes it **larger** than a ratio that keeps them in the denominator, which is the direction RFC 6349 takes for bytes, while the acknowledgements this item already recorded make it **smaller** — and neither has been quantified on any run of this tool. So the row may state what its denominator counts; it may not claim which way the figure errs.

**Decision, 2026-09-10 — the first of the two ways to close: no data-segment rate is computed, and the figure that prints says what it divides by.** A third road looked open for one paragraph and turns out not to be there: adding the retransmission count back to `Segments Sent`, to recover a denominator of every segment sent, in RFC 6349's direction, for one line of arithmetic. It fails on consequence *(a)* above — which this decision's own first draft had written and then contradicted two paragraphs later, found in round 1. A mixed segment, new bytes beside retransmitted ones, is counted by **both** counters, so `Sent + Retransmitted` is not every sent segment once: it is every sent segment plus the mixed ones a second time, and the counter class exposes nothing that says how many of the retransmissions were pure. The sum is an upper bound whose excess is unmeasurable, not a denominator. Had it been constructible it would still have moved a percentage that has already shipped, to land on a quantity that is not what any published figure refers to because the acknowledgements stay in it — but that is now the second argument against it rather than the first. The Win32 path stays refused for the reason round 6 recorded: it needs Administrators group membership, which contradicts a property this tool ships. — *decided by the owner on 2026-09-10.*

### 58 — A required check's failure is evidence about the gateway's own stack, not necessarily about the path

`AUTO_GATEWAY` is the first ping target and the only one shipped with `Required = $true`, so its failure is a required-connectivity failure and decides the overall result. But an ICMP echo addressed to a device's **own** address is answered by that device's own stack, and network devices commonly deprioritize or rate limit the traffic they must handle themselves rather than forward. So loss or latency measured against the gateway's address does not establish that the gateway is dropping or delaying **forwarded** traffic, which is what the row is read as saying.

**The asymmetry is the useful part, and it is already written down — in the one document the person in front of the machine does not have** (PR #43, round 5, correcting this item's first draft, which said nothing stated it). `sop/support-engineer-field-manual.md` says it for the `gateway-unreachable` fingerprint: *a gateway that forwards traffic but drops ICMP to its own address lands here with the rest of the network working*, to be read *once the ping is corroborated*, under SOP Rule 3 — *a failed ping is a suspect, not a conviction* — with instructions to look for a passing target that was off-subnet by a route through that same gateway. That is the rule, and it is stated well.

**What this item is about is that it has gone nowhere else.** No packaged document carries it: not the end-user manuals, not the IT deployment manuals, not the technical guides, in either language. And the tool that produces the verdict does not act on it. A gateway that answers promptly is good evidence the local path works, because a reply came back over that path; a gateway that answers badly is ambiguous three ways — the path, the device's control-plane policy, or the device simply being busy — and the tool treats the second case as a conclusion, on the one required target most likely to fail on a machine whose owner is complaining. So this is propagation and behaviour, not discovery, and the wording already exists to propagate.

**It lands hardest where the tool is used most.** On a machine with only Wi-Fi ([#61](#61--on-a-wi-fi-only-machine-nothing-distinguishes-the-air-from-what-is-behind-the-ap)) the gateway is usually the only near-end target there is, so the ambiguous measurement is also the only one available for deciding whether the air works. [#60](#60--there-is-no-near-end-baseline-so-no-measurement-can-be-attributed-to-a-segment) is the other half: a same-subnet target that is not the gateway is answered by an ordinary host, over the same local path, without the control-plane question.

Acceptance: a decision recorded either way on whether the gateway ping stays `Required`, with its reason — keeping it is defensible, since a machine that cannot reach its own gateway usually does have a problem, and the point of this item is that the reason be written rather than assumed; the asymmetry stated in both manuals' reading guidance, in both languages, **derived from the field manual's `gateway-unreachable` wording rather than formulated afresh**, so the two cannot drift apart, and a failed gateway row is read as *investigate the local path, and also consider that the device may not answer for itself*; and, if the check stays required, the row's own details and the *What to tell IT* summary saying what the failure does and does not establish, with a test asserting that sentence is present when the row fails and absent when it passes. — *raised on 2026-09-10, from the control-plane caveat in an outside summary of loss measurement; it applies to this tool's one required ping target, which the engineer's field manual qualifies and no packaged document or code path does.*

**Decision, 2026-09-10 — the gateway ping stays `Required`, and the reason is that a machine which cannot reach its own gateway usually does have a problem worth reporting.** The alternative 1.2.8 made available — [#39](#39--a-measurement-that-could-not-be-taken-outranks-a-measurement-that-failed)'s `Weightless` marking, so the row reports without deciding — trades a signal that is right most of the time for one that is never wrong and says less; on the Wi-Fi-only machine this item names, where the gateway is the only near-end target there is, it would leave the sole local measurement unable to move anything. Tying the conclusion to [#60](#60--there-is-no-near-end-baseline-so-no-measurement-can-be-attributed-to-a-segment)'s near-end target is more correct than either and is not available: that target is optional and absent by default, so the rule would degrade to *no near-end target, no conclusion* on precisely the ordinary machine that will never configure one. What this decision settles is what the failure is allowed to **mean**, not whether it counts.

**So what the item still owes is entirely words, and its acceptance already names them.** The asymmetry — a gateway that answers promptly is good evidence that the near-end path works, while a gateway that does not answer is not proof that it is broken, since the device may rate-limit or deprioritise ICMP addressed to its own control plane — carried into both packaged manuals' reading guidance in both languages, derived from `sop/support-engineer-field-manual.md`'s `gateway-unreachable` wording rather than written afresh so that the two cannot drift, and into the failed row's own details and the *What to tell IT* summary, since the check stays required. When [#60](#60--there-is-no-near-end-baseline-so-no-measurement-can-be-attributed-to-a-segment) ships, its row refines that reading without reopening this decision. — *decided by the owner on 2026-09-10.*

### 59 — No ping says which adapter it left by

`Invoke-PingMeasurement` records `LossPercent`, `AverageMs`, `MinimumMs`, `MaximumMs` and one detail line per attempt carrying the milliseconds and *reply from* the responding address. It never records the **source** address or the interface the echo left by. So on a machine with a wired and a wireless adapter both up — a docked laptop, which is exactly the machine most likely to be in trouble — the report cannot say which of the two the gateway row measured, and neither can the person reading it.

**The fact is one call away and costs no traffic.** `Find-NetRoute -RemoteIPAddress` returns the source address and the `InterfaceAlias` the route table would choose; measured on the reference machine, `1.1.1.1` resolves to `Wi-Fi` with source `192.168.1.106`. Nothing needs to be sent, no new target is required, and no external executable is involved — which matters, because binding a **source** rather than reading the chosen one would need `ping.exe -S`, and that is a departure this item does not ask for ([#60](#60--there-is-no-near-end-baseline-so-no-measurement-can-be-attributed-to-a-segment) carries it).

**It is the cheapest half of attributing a measurement to a segment.** It does not say which segment is faulty. It says which segment the route table selected for the measurement, which is the precondition for every other item in this group.

**What the field may claim, which is less than the obvious wording.** `Find-NetRoute` answers what the system would choose **when the lookup runs**, and `Invoke-PingMeasurement` then sends its probes unbound, so on the multi-homed machine this item is about — a dock, a roam, a VPN coming up — the route can change between the two and the row would be wrong if it claimed the echoes had used what the lookup returned (PR #43, round 2). The row states a selection, not an observation. Binding each probe to a source would make it an observation, and that needs `ping.exe -S`, which is [#60](#60--there-is-no-near-end-baseline-so-no-measurement-can-be-attributed-to-a-segment)'s to carry and not this item's.

Acceptance: every ping row naming the source address and interface the route table selects for that target, worded as a selection rather than as the path the echoes took, in both languages; the lookup taken both before and after that target's probes with the row saying so when the two disagree, which is the before-and-after shape the adapter counters and [#61](#61--on-a-wi-fi-only-machine-nothing-distinguishes-the-air-from-what-is-behind-the-ap)'s BSSID already use and which turns that objection into a measurement rather than a caveat; the same treatment on the CIM fallback path as every other NetTCPIP call in this tool — the datum reported as unavailable rather than the row failing, which is closed item #5's shape and what [#32](#32--the-report-records-the-dhcp-mode-but-not-the-dhcp-server)'s acceptance already requires of a different fact; a unit test for each of the four shapes (resolved, changed between the two lookups, unresolved, cmdlet absent) in both languages; and the manuals' description of the ping rows mentioning the field **and what it does not claim**, since a report field no document explains is how #46 happened. — *raised on 2026-09-10, out of asking whether ping can be segmented by LAN, WLAN and WAN: it cannot, but a measurement that does not say which adapter it used cannot even be placed.*

### 60 — There is no near-end baseline, so no measurement can be attributed to a segment

The shipped ladder has two rungs, the gateway and `1.1.1.1`, and every rung includes everything before it. That makes the ladder **cumulative rather than segmented**: differencing latency between rungs is weak, and **differencing loss is not valid at all** — loss is not additive, and the two rungs are different traffic sent at different instants, so *3 % to the public address and 0 % to the gateway* does not yield *3 % in the WAN*. The tool prints both numbers and no document says they cannot be subtracted.

**The missing rung is a target on the same subnet that is not the gateway.** It exercises the local path — the air, the access point, the switch — while being answered by an ordinary host rather than by a device's control plane ([#58](#58--a-required-checks-failure-is-evidence-about-the-gateways-own-stack-not-necessarily-about-the-path)), and without the WAN in the measurement at all. With it, the ladder has a near end, a boundary and a far end, and the differences between them mean something.

**The tool cannot guess one, but it already collects the candidates**: the neighbour table it reads for the gateway's MAC, the DHCP server address that [#32](#32--the-report-records-the-dhcp-mode-but-not-the-dhcp-server) would record, and the local subnet the adapter already reports. Confirming that a candidate is a stable host that answers ICMP is a person's judgement, not a probe's, so this ships as a configured target with a documented way of choosing one — not as detection. The three-way comparison that separates wireless from wired properly — a wired client and a wireless client against the **same** local host, then both against the same external target — needs a second machine and a source-bound probe, so its method belongs in `sop/` with the escalation material and not in a tool that runs on one machine.

**What must not be built, because it is what everyone reaches for first.** Per-hop loss from TTL-limited probes. An intermediate hop's reply is an ICMP error generated by that device's control plane, and ICMP error generation is rate limited by design, so per-hop percentages routinely show loss at a hop that is forwarding perfectly. Only loss that persists to the final destination is evidence. This tool's traceroute already declines to compute such percentages — one probe per hop, `INFO`, `Scope = "IT"`, path information rather than a rate — and that restraint is correct and must survive this item.

Acceptance: a configured near-end target, optional and absent by default, measured with the same ping path as the others and reported as its own row naming which segments it does and does not traverse; the manuals and the IT deployment manual saying how to choose one and why the gateway cannot serve as it; a stated rule — in the documents and not only in a comment — that rung differences may be read as *the problem appears beyond this point* and never as a per-segment loss figure; the `sop/` method for the three-way comparison, with its prerequisite of a wired host and its use of a source-bound probe; nothing computing per-hop loss; and the run's cost stated, since this adds a target. — *raised on 2026-09-10, out of asking whether ping can be segmented into LAN, WLAN and WAN.*

### 61 — On a Wi-Fi-only machine nothing distinguishes the air from what is behind the AP

The common case is a laptop with no wired option, so the comparison [#60](#60--there-is-no-near-end-baseline-so-no-measurement-can-be-attributed-to-a-segment) describes is unavailable and the question has to be answered from one path. It can be, partly — the air leaves signs at layers the wired side does not — and **the tool already collects three of those signs and compares or computes none of them**.

*The BSSID is recorded once.* A roam during the run is therefore invisible, although a roam is exactly the air-side event that explains a run with good signal and bad numbers. The pattern that suggests itself is in the same script — the adapter-counter step takes a before and an after and has a branch for *the counters were reset, possibly because the adapter reconnected* — but **the counters are the wrong model to borrow, and a before and an after is not enough on its own** (PR #43, round 5). A counter only goes up, so two readings bracket everything that happened between them; a BSSID does not, so a client that roams A → B → A inside the run leaves the two samples equal and the roam invisible. Catching a transient roam needs sampling inside the probe window, or the WLAN AutoConfig operational log with its own availability and permission questions — or the limit stated outright, which is the one thing that must not be skipped.

*The gateway's MAC and the BSSID both print, and nothing compares them.* `Add-GatewayNeighborResult` reads `LinkLayerAddress` from `Get-NetNeighbor` with an `arp -a` fallback; the Wi-Fi row carries the BSSID. If they are equal the access point **is** the gateway, which means there is no addressable boundary between the air and the wire and no path comparison is possible on that network — the single most useful thing to know before trying. A different vendor prefix suggests separate devices and therefore that a boundary exists. It is a hint and must be published as one: an all-in-one's radio MAC and bridge MAC commonly differ by an octet or a locally-administered bit, so inequality proves nothing.

*Every attempt's milliseconds are in the details text, and only the average, minimum and maximum are computed.* No variability figure exists, and variability with little loss is the air's signature, because 802.11 retries are absorbed as delay rather than surfacing as loss. This clause is bound to [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample): at the shipped four pings a variability figure means almost nothing, so it ships with a stated minimum sample or it does not ship.

**The discriminator that would settle it outright is obtainable, and this item's first draft said it was not** (PR #43, round 3). The 802.11 MAC retry rate is what separates the two, because the wireless layer can retry and succeed, leaving IP and TCP with no loss to report and only the delay as a trace. Windows does expose it: `WLAN_PHY_FRAME_STATISTICS` carries `ullRetryCount` and `ullMultipleRetryCount`, reached through the Native Wifi API's statistics query on `WLAN_STATISTICS`, in `wlanapi.h` since Windows Vista — verified against Microsoft's documentation on 2026-09-10, where the field names are those two and not the plausible-looking pair the review offered, which is this page's citation rule ([#56](#56--the-shipped-thresholds-have-no-recorded-basis-and-the-standards-that-exist-do-not-supply-one)) earning its keep on the second day it existed. What the measurement needs is P/Invoke, and **this project has already taken that decision once**, in [the v1.2 design note](design-v1.2-triage-wizard.md), for the Wi-Fi RF data: *`netsh` parsing (locale-sensitive but dependency-free) vs the native WLAN API through P/Invoke (robust but adds unmanaged code to a script that is reviewed for being plain PowerShell)*, resolved in favour of `netsh` with a documented limitation.

**And one question this item must settle before it repeats #57's mistake.** Whether the statistics query needs elevation at all is not established here. #57's Win32 path turned out to require membership of the Administrators group and a write to the machine that Microsoft advises against undoing (round 6), and none of that was visible from *the API exists*. The same distance separates *`WlanQueryInterface` is documented* from *this tool can call it as the user who double-clicks it*, and this item may not assume the answer in either direction.

**That answer cannot simply be inherited, for two reasons.** For the RF data `netsh` was a working dependency-free alternative, so the choice was between two ways of getting the same facts; for the retry counters there is no `netsh` equivalent, so the choice is between unmanaged code and not having the measurement at all. And P/Invoke fails closed exactly where this tool has taken the most care: `Add-Type` is refused in a constrained language mode — *Definition of new types is not supported in this language mode*, recorded in `healthcheck/VALIDATION.md` — which is the WDAC and AppLocker environment backlog #18 built the language-mode guard for. A retry-counter branch would therefore be absent on the machines under the strictest application control and present everywhere else, and the manuals would have to say so. Whether a given driver populates the counters at all is a third question, and only a measurement answers it.

**And if they are read, they have to be read the way this tool reads every other counter** (PR #43, round 4). `ullRetryCount` counts *MSDU/MMPDUs successfully transmitted after one or more retransmissions* and `ullMultipleRetryCount` those *successfully transmitted after more than one*, so the second is a **subset** of the first and neither is a denominator for the other. Both are cumulative, and the documentation does not say what resets them — which is a thing to establish rather than assume. A single reading on an interface associated for hours describes those hours, while this item needs a rate for **this run**: the before-and-after delta `Compare-TcpCounters` already takes, with the same branch for a counter that went backwards because the association dropped. The denominator needs stating too, and it has [#57](#57--the-retransmission-rates-denominator-is-not-the-quantity-any-published-figure-refers-to)'s shape all over again: `ullTransmittedFrameCount` counts *successfully transmitted* frames, so frames abandoned after the retry limit are not in it but in `ullFailedCount` beside it. And `WLAN_STATISTICS` carries one `WLAN_PHY_FRAME_STATISTICS` per PHY with `dwNumberOfPhys` of them, so which PHY, or how they aggregate, is part of the measurement rather than a detail of it.

**Two things stay true whichever way that decision goes.** The Wi-Fi adapter's own error and discard counters are frequently empty, and closed item #10 already recorded that a zero-traffic adapter's *0 errors* is vacuous evidence — the same vacuum applies to a wireless adapter that reports nothing. And the human checks — a second station on the same access point, a change of position or band, and connecting a cable once if any port exists at all — remain the fastest discriminators there are, and belong in `sop/` rather than in the tool.

Acceptance: the BSSID sampled at least before and after the run with a row when it changed, in both languages, and a transient A → B → A roam either detected or **explicitly disclosed as undetectable**, since two equal samples do not exclude one; the access-point-is-the-gateway comparison reported as a hint with its uncertainty stated, never as a topology claim; a latency variability figure for each ping row **or** a recorded decision not to compute one until #51 provides the sample, with the minimum sample named either way; the manuals' Wi-Fi reading guidance carrying the layer signatures and stating that a wireless retry rate is neither a TCP retransmission rate nor a ping loss rate; the elevation question answered from Microsoft's documentation **before** the decision rather than after it; an explicit decision on the retry counters, recorded either way — read them through P/Invoke and state what happens to that branch under application control and for a user without administrative rights, or decline them and state why — with the technical guides' limitations carrying whichever it is rather than calling the measurement unavailable; if they are read, a rate for **this run** and not for the association's history — before-and-after samples with the reset branch, a stated denominator that accounts for the frames abandoned after the retry limit, a stated rule for the PHY array, and the two retry counters neither added together nor divided into each other; and the `sop/` discrimination flow for a machine that has only Wi-Fi. — *raised by the owner on 2026-09-10 asking how to tell Wi-Fi from LAN when only Wi-Fi is up — the case the three-way comparison cannot reach.*

**Status, 2026-09-10 — the elevation question is answered, in the order this item demanded: the documentation first, then a measurement, because the documentation turns out to be silent rather than permissive.** *What Microsoft states:* neither the `WLAN_INTF_OPCODE` reference (checked 2026-09-10) nor the `WlanQueryInterface` reference (page dated 2024-03-18, checked 2026-09-10) attaches any privilege note to `wlan_intf_opcode_statistics`, which is described only as the opcode used to query driver statistics; and the page that does name the restricted calls, *Changes to API behavior for Wi-Fi access and location* (page dated 2025-05-30, checked 2026-09-10), does not list it. The calls that return `ERROR_ACCESS_DENIED` to a caller without the user's precise-location consent are `WlanGetAvailableNetworkList`, `WlanGetNetworkBssList`, `WlanScan`, and `WlanQueryInterface` **when the opcode is `wlan_intf_opcode_current_connection`**. Silence about a privilege is not a statement that none is needed — that distance is exactly what round 6 measured on [#57](#57--the-retransmission-rates-denominator-is-not-the-quantity-any-published-figure-refers-to) — so it was measured here as well.

*What was measured, on the reference machine, 2026-09-10:* Windows 11 Pro build 26200, in a process running **without elevation**, its token carrying no Administrators membership, which is the condition under which #57's `SetPerTcpConnectionEStats` path fails. `WlanOpenHandle`, `WlanEnumInterfaces` and `WlanQueryInterface` with `wlan_intf_opcode_statistics` each returned `ERROR_SUCCESS`. The buffer was 1088 bytes with `dwNumberOfPhys` 6, which is exactly the size the documented layout predicts for six PHYs — 24 bytes of leading counters, two `WLAN_MAC_FRAME_STATISTICS` of twelve `ULONGLONG` each, 8 for `dwNumberOfPhys` and its alignment, then six `WLAN_PHY_FRAME_STATISTICS` of eighteen `ULONGLONG` each, the three structures read from their own reference pages on 2026-09-10 rather than from memory. The size also picks the variant: `WLAN_STATISTICS` declares `PhyCounters` as an inline array in one form and as an array of pointers in the other, and 1088 is the inline one. So the offsets were confirmed by that arithmetic — `ullRetryCount` fourth in the PHY structure, `ullMultipleRetryCount` fifth — and by the counters at them advancing monotonically, rather than assumed. The Intel Wi-Fi 6E AX211 driver does populate them: over three seconds `PhyCounters[0]` moved transmitted +36, retry +15, multiple-retry +7, ACK-failure +52, received +49, failed +0.

**What that settles, and what it must not be read as.** It settles access: the measurement can be taken by the user who double-clicks the launcher, on one machine, one driver, one adapter. It settles nothing else. The probe read `PhyCounters[0]` of six, so the ratio between those particular numbers is **not** the interface's retry rate, and nothing here licenses reading it as one.

**A gate this item does not carry, found in the same page, and it lands on the half that looked free.** The BSSID is what `wlan_intf_opcode_current_connection` returns, and that opcode is on the list above. The tool does not call it — it parses `netsh wlan show interfaces` — and nothing establishes that the command is exempt. On the reference machine, unelevated, `netsh` still returns a non-empty BSSID; precise location there is set to *Allow* at both machine and user scope, which is the uninformative case, showing that the path works with consent rather than without it. What would settle it is a machine with precise location denied, which the campaign VMs can be set to, and it is the same run that would answer whether the shipped tool loses the field. [#62](#62--the-wi-fi-row-infers-its-connected-state-from-the-bssid-so-a-withheld-bssid-reports-a-connected-radio-as-disconnected) is what the tool does today when it is missing, and it was raised by this reading.

**The read-or-not decision stays open, deliberately.** Two things are unsettled and both have the shape of the mistake round 3 caught in #57: how six PHYs' counters combine into one figure for one interface, and what a retry **rate** divides by, given that `ullMultipleRetryCount` is a subset of `ullRetryCount` and neither is a denominator for the other. Deciding to read them today would prescribe the answer to a question nobody has asked yet; that decision belongs with the implementation, after [#51](#51--a-quality-verdict-can-rest-on-a-single-packet-because-the-threshold-is-finer-than-the-sample) settles what a sample has to be worth. — *the documentary half answered on 2026-09-10 from the three pages named above; the measurement taken the same day on the reference machine.*

### 62 — The Wi-Fi row infers its connected state from the BSSID, so a withheld BSSID reports a connected radio as disconnected

`ConvertFrom-NetshWlanOutput` parses `netsh wlan show interfaces` **by shape rather than by label**, deliberately: the labels are localized and their order differs between Windows 10 and Windows 11 builds, which the function says in its own comment. The shape it keys on is the MAC address. In a block the first MAC-shaped value is the adapter's own address and the second is the access point's BSSID, so `$bssidIndex` is the index of `$macs[1]` and is set only where the block carries **two** MAC-shaped values — and everything else hangs from it: `Connected` is `($bssidIndex -ge 0)`, the SSID is the value on the line *before* it, and the channel, band, receive and transmit rates and profile are all parsed inside the same guard. The function is byte-identical in the two shipped scripts, 102 lines in each.

**So one absent field does not degrade the row, it inverts it.** With no second MAC the interface is not reported as connected without a BSSID; it is reported as not connected at all, and the row that ships then says *No connected Wi-Fi interface (wired connection, Wi-Fi off, or no wireless adapter)* — three causes, none of them the true one — while its own details line still reports how many wireless interfaces `netsh` returned, which on such a machine is one. The report tells the person that the machine is not on Wi-Fi while it is, and contradicts itself one line further down.

**Windows documents one mechanism that withholds a BSSID, and it is a setting rather than a fault.** Since the change described in *Changes to API behavior for Wi-Fi access and location*, `wlanapi` calls that carry BSSIDs return `ERROR_ACCESS_DENIED` to a caller without the user's precise-location consent; [#61](#61--on-a-wi-fi-only-machine-nothing-distinguishes-the-air-from-what-is-behind-the-ap) records the list and the check dates. This tool does not call `wlanapi` — it runs `netsh` — and whether `netsh` is exempt is **not established**: the reference machine has precise location set to *Allow*, so the non-empty BSSID observed there proves only that the path works with consent. The defect does not depend on that question. Any condition under which the second MAC does not appear — a build, a locale that formats it differently, a policy, a driver that reports no association — produces the same inversion, and the privacy setting is the one such condition Windows documents.

**What limits it.** The row is an IT-scope `INFO` row: it never moves the verdict, and [#39](#39--a-measurement-that-could-not-be-taken-outranks-a-measurement-that-failed)'s rule keeps it that way. The cost is a false sentence in the section of the report written for the person who will act on it, on the machine type [#61](#61--on-a-wi-fi-only-machine-nothing-distinguishes-the-air-from-what-is-behind-the-ap) is about.

Acceptance: the connected state no longer derived from the presence of the BSSID — the candidates being `netsh`'s own state field, `Get-NetConnectionProfile`, and `wlan_intf_opcode_interface_state`, which the location page does not list, and this item chooses between none of them, since the parser is shape-driven for a reason the fix has to keep; where a BSSID is genuinely unavailable, the row reporting the connection with that field marked unavailable, which is closed item #5's shape, rather than reporting no connection; the existing message's three causes no longer offered as exhaustive; unit tests in both languages over a captured block with two MAC-shaped values and the same block with the second removed; and a measurement on a machine with precise location denied, recording what `netsh wlan show interfaces` prints there, which is the run [#61](#61--on-a-wi-fi-only-machine-nothing-distinguishes-the-air-from-what-is-behind-the-ap) needs anyway. — *raised on 2026-09-10 while answering #61's elevation question; what found it was the location-consent page's list of what is withheld without consent, read against the parser that consumes the field.*

## Adding and closing an item

**Adding.** An item is added when something is found that will not be fixed in the change that found it: a review finding deferred, a measurement that cannot be made on the machines at hand, a decision with a cost. Give it the next unused number, state what is wrong in the terms of the code or the machine that makes it wrong, name where the evidence is, and end with the acceptance sentence — what would have to be true for the item to be closed — and an origin note saying what raised it and when. A finding that can be fixed in the change that found it is not a backlog item; a wish with no acceptance sentence belongs in the roadmap table of the repository `README.md` instead.

**Closing.** An item is closed by the change that closes it, in the same commit that ships it: move its line to the closed table with the release or the date that closed it, and leave its number where every other document already cites it. The reason it is closed is proved in `healthcheck/VALIDATION.md`, in that release's entry — this page says only which release did it, so that the claim lives in one place. An item can also turn out to have been closed by a release that never named it: #23 by #28, two days later. Then its closed line names both dates — the release that did the work, and the day it was recognised — so that neither is read as the other, and whatever that release did not cover becomes an item of its own rather than a remainder nobody wrote down.

**Neither.** When an item has moved on without being closed — part of it done, its premise overtaken, a measurement arrived — add a dated **Status** line at the end of the item rather than rewriting it, so that what it said when it was raised stays readable beside what is true now.
