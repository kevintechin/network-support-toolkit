# The thresholds NetworkHealthCheck ships with — what stands behind each value, and what the standards supply

This page is kept in the repository rather than in the package for the same reason as [`application-control.md`](application-control.md) beside it: it is a record that may grow between releases while a shipped document may not. The technical guides' limitation 9 and the IT deployment manual's threshold table link here by the tag of their release; the current version of this page is on the `main` branch. It answers one question a reader of a threshold table is entitled to ask — *where did 2 % come from?* — and the answer, established on 2026-09-10 and shipped in 1.2.11 (backlog #56), is that **none of the shipped values has an external basis**: no standard, no vendor guideline, no measurement, no calibration run and no recorded decision stands behind any of them. They are operational defaults somebody chose, and every document that presents them as a table now says so beside each value. No value changed.

## The values, one by one

The `Thresholds` block of `NetworkHealthCheck.config.json`, as shipped. Every value below classifies a row carrying one of the quality tags the fingerprint reads (`ping-target`, `ping-gateway`, `tcp-retransmissions`, `adapter-errors`); what each rule does with its value is in the IT deployment manual's section 3.5 and the technical guide's section 4.

| Key | Shipped | Kind | What stands behind it |
|---|---|---|---|
| `PacketLossWarningPercent` | 5 | magnitude | Nothing. Present in the initial commit `99f8275`, whose message does not mention thresholds |
| `PacketLossCriticalPercent` | 20 | magnitude | Nothing; as above |
| `LatencyWarningMs` | 100 | magnitude | Nothing; as above. The two published figures in the neighbourhood are not this quantity — see *What the published documents define* |
| `LatencyCriticalMs` | 250 | magnitude | Nothing; as above, and the same caveat |
| `TcpRetransmissionWarningPercent` | 2 | magnitude | Nothing; as above — and the percentage it is applied to is the tool's own ratio, not a published one (see *What the retransmission percentage divides by*) |
| `TcpRetransmissionCriticalPercent` | 5 | magnitude | Nothing; as above, and the same caveat |
| `TcpRetransmissionCriticalCount` | 50 | magnitude | Nothing; as above. Since 1.2.10 it qualifies a verdict the rate has reached and never creates one (closed item #63) |
| `MinimumTcpSegmentsForRate` | 50 | magnitude | Nothing; as above — and it is exactly `100 ÷ TcpRetransmissionWarningPercent`, so at this floor one retransmission is the warning threshold itself (closed item #51), which is why the floor below exists |
| `MinimumTcpRetransmissionsForVerdict` | 5 | magnitude | Added in 1.2.10 with its reasoning recorded (closed item #51): a rate needs enough events behind it, and the floor suppresses nothing above `(floor − 1) × 100 ÷ warning percentage` sent segments, two hundred at the shipped values. No external basis either |

Every value but the thirteenth appears fully formed in the initial commit, confirmed with `git log -S` on each name; every later commit touching any of them changed type handling alone — culture-invariant parsing, whole-number and Int32 rules. The commit history is the evidence, and this paragraph is here so that nobody has to reread it.

## The search that found nothing, so that nobody repeats it

Made on 2026-09-10 for the retransmission and packet-loss values, and extended the same day to the latency and adapter values: `healthcheck/VALIDATION.md`, `docs/`, `sop/`, every manual and guide copy in both languages, the two scripts' comments, `tests/`, and `git log -S` per name. The only prose about any of them was the IT deployment manual's threshold table, which states the **rule** each value feeds under the heading *the defaults are generic starting points*. A rule is not a basis. The three shipped disclaimers — that table's heading, the technical guide's limitation 9 (*thresholds require calibration*) and the field manual's *thresholds are generic until someone sets them* — were not wrong; what was missing was a sentence saying that these particular numbers were chosen without one, because a reader who sees *2 % warning* in a table may reasonably infer that 2 % came from somewhere.

## What the published documents define

None of the documents that would be expected to supply a general threshold does, and this is the part worth writing down once. It is a claim about the documents examined, not a proof that no such standard exists anywhere: the table below **is** the examined set, and anyone who finds a published general threshold should add it here, with its source and the date it was checked, before adding it to a threshold. The published documents divide into two kinds — how to *measure*, and *objectives* for a named service class over a named scope — and neither kind contains a rule of the form *above X % the network is faulty*. Verified against their sources on 2026-09-10:

| Source | What it actually defines | Verified against |
|---|---|---|
| RFC 7680, *A One-Way Loss Metric for IP Performance Metrics (IPPM)*, Internet Standard, STD 82, January 2016 (obsoletes RFC 2680) | How to measure one-way packet loss, including how long to wait before a packet counts as lost | `rfc-editor.org/info/rfc7680` |
| RFC 6534, *Loss Episode Metrics for IP Performance Metrics (IPPM)*, Standards Track, May 2012 | Loss **episode** frequency and average duration, on the stated ground that the impact of loss is sensitive not just to the average rate but to how losses are distributed | `rfc-editor.org/info/rfc6534` |
| RFC 6349, *Framework for TCP Throughput Testing*, **Informational**, August 2011 | TCP Efficiency, in section 4.2, as (transmitted − retransmitted) / transmitted × 100 over **bytes**, where transmitted includes the retransmitted bytes | `rfc-editor.org/info/rfc6349` |
| RFC 4898, *TCP Extended Statistics MIB*, Proposed Standard, May 2007 | Per-connection counters that keep `tcpEStatsPerfSegsOut`, `tcpEStatsPerfDataSegsOut` (*segments sent containing a positive length data segment*), `tcpEStatsPerfSegsRetrans` and `tcpEStatsPerfOctetsRetrans` apart | `rfc-editor.org/info/rfc4898` |
| ITU-T Y.1541 (12/2011), *Network performance objectives for IP-based services*, Table 1, page 9 | Bounds per QoS class on four parameters, not one: mean **IPTD** 100 ms (classes 0 and 2), 400 ms (1 and 3), 1 s (4); **IPDV** 50 ms (0 and 1); **IPLR** 1 × 10⁻³ (0 to 4); **IPER** 1 × 10⁻⁴ — with `U`, unspecified or unbounded, for class 5 throughout | the ITU PDF, read directly |
| Cisco, *Quality of Service for Voice over IP* | *The default G.729 codec requires packet loss far less than 1 percent to avoid audible errors. Ideally, there should be no packet loss for VoIP* | `cisco.com/c/en/us/td/docs/ios/solutions_docs/qos_solutions/QoSVoIP/QoSVoIP.html` |

**Two things read out of Y.1541's own Table 1 sharpen the point more than the 10⁻³ figure does.** Its General notes require that *an evaluation interval of 1 minute is suggested for IPTD, IPDV and IPLR and, in all cases, the interval must be recorded with the observed value* — a standards body saying that a loss percentage without its interval is not a comparable figure, which is closed item #51's thesis stated by someone else. And its NOTE 4 gives the 10⁻³ a stated basis: *partly based on studies showing that high quality voice applications and voice codecs will be essentially unaffected by a 10⁻³ IPLR*. The one standards number in the table carries its reason and its interval; ours carry neither. Note also its scope, which is why it cannot simply be adopted: the objectives apply to **public IP networks, between the measurement points that delimit the end-to-end IP network**, and say nothing about a LAN or an air interface.

**The latency values are a quantity mismatch as well as a missing basis.** `LatencyWarningMs` and `LatencyCriticalMs` are applied to the **average round-trip time** of the ICMP replies that came back, while the two published figures nearby are neither. Y.1541's Table 1 bounds the **mean one-way IP transfer delay** at 100 ms for classes 0 and 2; converting a one-way bound to a round trip needs only the factor of two a symmetric path implies, but the table's own scope — a public IP network between the points that delimit it, over a suggested minute — is neither a LAN nor an eight-second burst of a few echoes. G.114's 150 ms, which the Cisco guidance cites, is further away still: it is **one-way mouth-to-ear** delay, which the endpoint delays (packetization, codec, jitter buffer) *consume*, so the network's share is under 150 ms one-way and its round trip under 300 ms — and nobody in this project has made the allocation that would turn that into a threshold. The first draft of this reasoning made the conversion backwards (PR #43, round 2), and it is kept on record for the same reason closed item #51 keeps its rejected candidates: a number in this area looks reasonable until the arithmetic is written out beside it. Neither threshold was derived from either figure.

## The decision, and what it forecloses

Three roads were open, and taking any one of them forecloses the others until someone revisits it. **(1) State them for what they are** — operational defaults chosen without an external basis, configurable, named as such in the threshold tables rather than only in a general disclaimer. **(2) Calibrate** — measure this fleet and set the numbers from what it does, which is what limitation 9 already tells the deployer to do and which no run in this project has ever done. **(3) Keep them and record that keeping them was a decision**, with the date and the reason, so that the numbers stop being unexplained even though they do not change. What must not happen is a fourth road: replacing 2 and 5 with someone else's suggested grading and inheriting the same silence about where those came from.

**Road (1) was taken on 2026-09-10.** Road (3) would record the decision where only the backlog could see it and leave the shipped tables reading like engineering values, which is the appearance the item objected to. Road (2) is the better long answer and could not be taken then: it needs fleet measurements no run in this project has made, so choosing it would have left the tables unexplained until they arrived. And road (1) forecloses road (2) less than it seems — a later calibration becomes a documented improvement to a value already labelled as chosen without an external basis, rather than a silent change to one that looked authoritative. **Changing a value from here:** record the measurement or the source it rests on in this page first, add any published document to the table above with its source and check date, then change the number in the configuration, the IT deployment manual's table and the technical guides in the same release.

## What the retransmission percentage divides by

Established on 2026-09-10 for backlog #57, and shipped in the row's own details in 1.2.11. `Compare-TcpCounters` divides the delta of `SegmentsRetransmittedPersec` by the delta of `SegmentsSentPersec`, both from `Win32_PerfRawData_Tcpip_TCPv4` and `TCPv6`. Two sources agree on what those counters count:

| Source | What it says | Verified |
|---|---|---|
| The operating system's own counter help text, read through `System.Diagnostics.PerformanceCounterCategory` (`CounterHelp`) on the reference machine — UI culture `en-US`, system locale zh-Hant-TW | *Segments Sent/sec* is the rate at which segments are sent, including those on current connections, but **excluding those containing only retransmitted bytes**; *Segments Retransmitted/sec* is the rate at which segments are transmitted **containing one or more previously transmitted bytes** | 2026-09-10, on that machine; what a zh-TW display language returns was not measured |
| Microsoft, *TCP Object* counter reference (Windows Server 2003 technical reference; page dated 2009-10-08, last updated 2021-11-12) | The same exclusion for Segments Sent/sec, which is a subset of Segments/sec; Segments/sec is the sum of Segments Received/sec and Segments Sent/sec | 2026-09-10 |

Three consequences. *(a)* The denominator does **not** exclude the numerator: it excludes segments containing *only* retransmitted bytes, while the numerator counts every segment containing *one or more* previously transmitted bytes, so a segment carrying new bytes beside retransmitted ones falls in both, and only a pure retransmission is in the numerator and out of the denominator. *(b)* `Segments/sec` is not an alternative denominator, since it is Received plus Sent. *(c)* Two biases sit in the printed percentage and they point opposite ways — the acknowledgements counted in the denominator make it **smaller** than a data-segment rate over the same traffic, while excluding pure retransmissions makes it **larger** than a ratio that keeps them in (RFC 6349's direction, for bytes) — and neither has been quantified on any run of this tool. So the row states what its denominator counts and does not claim which way the figure errs.

**What was decided, and what was refused.** No data-segment rate is computed, and the figure that prints says what it divides by. Adding the retransmission count back to `Segments Sent` to recover *every segment sent* is not constructible: a mixed segment is counted by both counters, so `Sent + Retransmitted` is every sent segment plus the mixed ones a second time, and the counter class exposes nothing that says how many retransmissions were pure — an upper bound with an unmeasurable excess, not a denominator. The Win32 path to a data-segment rate — RFC 4898's per-connection counters, reached through TCP extended statistics — is refused on what it costs, verified against Microsoft's `iphlpapi` documentation on 2026-09-10: collection is off by default, `SetPerTcpConnectionEStats` can only be called by a member of the Administrators group, and Microsoft advises against disabling statistics again once enabled, because since Windows 10 version 1709 some counters do not reset. That is a persistent write to the machine by an elevated user, in a tool whose first promises are *no admin rights* and *changes nothing*.

## The retransmission figure of the TCP connection rows: the sockets' own count, and the timeout the times fall back to

Not a threshold of this tool. Since 1.2.12 (backlog #52) each TCP target that answers is connected to `PingCount` times, and the row reports, per connection, how many times the socket had to send its SYN again — the socket's own count — with the connection times beside it. Only where a socket cannot be asked do the times stand in, read against the operating system's **initial retransmission timeout**, the timer after which a connection request is sent again; either way the boundary is the one Windows applies to its own SYNs, not a magnitude somebody picked. What the tool reads, and what it assumes where nothing is reported:

| Source | What it says | Verified |
|---|---|---|
| Microsoft, *SIO_TCP_INFO Control Code* (Winsock reference; page dated 2019-05-20, updated 2021-06-22) | Retrieves the TCP statistics for a specified socket into a `TCP_INFO_v0` (version 0 in the input DWORD; version 1 gives more fields); *unlike retrieving TCP statistics with the GetPerTcpConnectionEStats function*, it *does not require elevated privileges to use* | 2026-09-12 |
| Microsoft, *TCP_INFO_v0* (mstcpip.h; page dated 2018-12-05, updated 2024-02-22) | `SynRetrans` is *the total number of retransmitted synchronize control flags (SYNs)*; `RttUs` *the current estimated round-trip time for the connection, in microseconds*; minimum supported client Windows 10 version 1703, server Windows Server 2016 | 2026-09-12 |
| Microsoft, *Set-NetTCPSetting* (NetTCPIP module reference; page dated 2016-12-20, updated 2025-05-14) | `InitialRtoMs` "specifies the period, in milliseconds, before connect, or SYN, retransmit"; acceptable values 300 through 3000 ms in increments of 10; alias `InitialRto` | 2026-09-12 |
| Microsoft, *TCP_INITIAL_RTO_PARAMETERS* (mstcpip.h; page dated 2024-04-02) | The per-socket form of the same parameters, Windows 8 and later: the initial RTT estimate "is used to compute the retransmission timeout", and `MaxSynRetransmissions` is the number of retransmissions attempted before the connection setup fails | 2026-09-12 |
| The reference machine (Windows 11 26200, unelevated) | `SIO_TCP_INFO` with version 0 returns 88 bytes for a connected `TcpClient` socket — state 4 (established), MSS 1452, `RttUs` 6301 on a 7 ms handshake to `1.1.1.1:443`, `SynRetrans` 0 — and the loopback the same shape at 70 µs; a 16-byte output buffer is refused with a fault. `Get-NetTCPSetting` returns the six templates with no `InitialRtoMs` property on the object at all; `netsh int tcp show global` reports *Initial RTO : 1000* and *Max SYN Retransmissions : 4*; the registry's `Tcpip\Parameters` key holds no `InitialRto` value; `Get-NetTransportFilter`, which would say which template a connection gets, is refused with *Access is denied* | 2026-09-12 |

So the tool asks each connected socket for its `TCP_INFO_v0` — `SynRetrans` at byte 84 and `RttUs` at byte 20 of the 88, the layout the reference documents and the machine returned — and where any socket of a target could not be asked, reads the Internet template's `InitialRtoMs` where the cmdlet reports one, assumes 1000 ms where it does not (the reference machine's case), and reads the times against it, saying which of the two it got, with `netsh int tcp show global` as the manual check. **What each reading claims and what it does not.** The socket's count is the stack's own record of SYNs it sent again for that connection; it does not say *why* a SYN went unanswered — a dropped SYN, a listener's full backlog and a SYN-ACK lost on the way back all count the same — and it does not see the peer's retransmitted SYN-ACKs. The time-based fallback is a proxy and the row calls it one: a handshake at or above the timeout is where a retransmitted SYN would show, but the time is measured at the socket, so it also holds whatever ran before the SYN — a neighbour lookup — and after the reply — the scheduling of the waiting thread — and is rounded to the millisecond, so a connection near the boundary can read as a retransmission that did not happen (PR #53, round 1); and a handshake below the timeout rules a retransmission out only if the timeout read is the one the connection used, which the tool cannot confirm — the template a connection gets is not readable without administrator rights, and an assumed value is an assumption, so a connection on a 1000 ms timeout can retransmit and complete in 1500 ms under a displayed 3000 (round 2). Where an administrator changed the timeout without the cmdlet reporting it, the assumed 1000 ms is wrong and the row's own words say it was assumed; which template Windows applied to the connection cannot be read without administrator rights, so the Internet template — one of the two Windows ships — is the one asked, and a row that read a value names the template it came from. No threshold sits on either figure: the row decides nothing.

## The spread of a ping row's replies, and the minimum sample its sentence names

Not a threshold of this tool: nothing is decided at it, one sentence changes. Since 1.2.13 (backlog #61's other half) every ping row with two or more replies carries the **sample standard deviation** of the round-trip times that arrived — a description of how unevenly they came, which is the air's signature where loss is small, because an 802.11 retry is absorbed as delay — and the sentence names the sample it was taken over. Below **nine replies** it says the figure describes those replies rather than the link; at nine or more, that it describes this run's variability towards that target. No threshold sits on the figure, because none has a stated basis; the row's status, the verdict and the JSON schema are untouched.

**Where nine comes from.** For normally and independently distributed values the standard error of the sample standard deviation s is σ √(1 − c₄²), with c₄(n) = √(2 / (n − 1)) · Γ(n / 2) / Γ((n − 1) / 2) (the source below); the large-sample form of the same quantity is σ / √(2 (n − 1)). Relative to σ that is 60.3 % at n = 2, 38.9 % at n = 4, 26.2 % at n = 8, **24.6 % at n = 9**, 15.7 % at n = 21 and 13.1 % at n = 30 (the approximation: 70.7 %, 40.8 %, 26.7 %, 25.0 %, 15.8 %, 13.1 %). The **quarter** is the chosen precision — an operational default with no external basis, like every value on this page — and n = 9 is the first sample at which the exact figure, and the approximation with it, falls below it. The normal assumption does not hold for round-trip times, whose distribution is skewed; a burst of long replies makes the figure larger, not smaller, which is what the figure is for, so the assumption failing does not make the figure lie — it makes the *uncertainty* estimate approximate, which is why nine is a reading aid and not a gate.

**What the timer's resolution does.** `PingReply.RoundtripTime` is an `Int64` of milliseconds, so on a link that answers in a millisecond or two the replies are a run of 1s and 2s, and their standard deviation is the timer's resolution and not the link's variability: thirty replies to the reference machine's gateway 250 ms apart gave 0.4 ms, the first four of them 0.5 ms, four replies of a shipped run 1.7 ms (1 to 5 ms) and four to `1.1.1.1` 1 ms (6 to 8 ms) — measured 2026-09-12. The sentence says so every time.

| Source | What it says | Verified |
|---|---|---|
| Wikipedia, *Unbiased estimation of standard deviation*, section *Results for the normal distribution* | "the standard error of s is σ√(1 − c₄²)", for normally and independently distributed data, with c₄(n) = √(2 / (n − 1)) · Γ(n / 2) / Γ((n − 1) / 2) | 2026-09-12 |
| Microsoft, *PingReply.RoundtripTime Property* (.NET API reference; page dated 2025-07-01, updated 2026-05-27) | "Gets the number of milliseconds taken to send an Internet Control Message Protocol (ICMP) echo request and receive the corresponding ICMP echo reply message"; property value an `Int64` "that specifies the round trip time, in milliseconds"; a failed request reports 0, which is also a valid value for a successful one | 2026-09-12 |
| The reference machine (Windows 11 26200, Windows PowerShell 5.1, .NET Framework 4.x) | `[System.Net.NetworkInformation.PingReply].GetProperty('RoundtripTime').PropertyType` is `System.Int64`; the figures above from `Invoke-PingMeasurement` and a 30-probe measurement 250 ms apart | 2026-09-12 |

So the tool computes the sample standard deviation (n − 1) over the replies that arrived, rounds it to a tenth of a millisecond, prints it with the count, the average and the two ends, states the resolution, and names nine — and decides nothing.

## The rule for citations

Every citation on this page carries the source it was verified against and the date it was checked, and **an unverified citation may not be the basis of any threshold, any document sentence or any test**. The practice already existed in one place — `application-control.md` cites Microsoft's *Requirements to use AppLocker* with that page's own date beside the KB it names — and this page applies it to the numbers a verdict rests on. The reason is on record: the one citation drafted from memory in the work that produced this page was doubted for the wrong reason (RFC 6534 was suspected of not being about loss episodes, and it is exactly that), which one fetch settled. Doubt is cheap and checking is cheaper than either being wrong or hedging in a shipped document.
